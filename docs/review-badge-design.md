# レビュー未確認バッジのデザイン（`! N`）v1

ステータス: 実装済み（2026-08）

この文書は、タイトルバー左端のレビュー未確認件数バッジを `● N` から `! N` へ
変更した経緯・評価・切り替え方法を残す。別案に戻したくなったときは
「切り替え方法」の2箇所を書き換えるだけでよい。

## 1. バッジの意味とスロットの文脈

- `app.file_review_count()` は、最後に確認済みとした世代（baseline）から NOW までの
  **レビューマーク数**を返す。連続する変更行は1グループに数え、削除位置は別に数える。
  つまり `n` / `N` ジャンプのターゲット数そのものである。
- タイトル左端のスロットは状態で遷移する:
  1. `⚡` — 外部編集を検知（`r` 待ち、または `i` で無視）
  2. `! N` — 未確認のレビューマークが N 箇所（`r` 再読込後など）
  3. `BASELINE` / リビジョンラベル — 履歴表示中
- ファイルピッカー（Ctrl+o）の各行にも同じマークが出る（`⚡` と `! N`）。
  グリフはタイトルと揃える必要がある（並べて見るため）。

## 2. 問題

`● N` は「●」が箇条書き記号（markdown リストの bullet）と同形で、
タイトルバーの先頭要素として「リストの始まり」にしか見えなかった。
「N 件の未確認」という状態バッジとして読めない。

## 3. 調査（慣習）

- **lazygit**: ステータスパネルで `↑N` / `↓N`（リモートとの前後関係）。方向グリフ+数。
- **vim 系 statusline**（gitgutter / lightline-gitdiff / fugitive）:
  `+N ~N -N`（追加・変更・削除のカウント）。差分カウントの定番だが、
  合算数を1つで表す用法はない。
- **mutt / notmuch / Thunderbird**: 未読・新着は `N` や `N new` の語彙。
  `!` は「フラグ付き（要対応）」の古典的マーカー。
- **通知バッジ一般**（macOS / iOS / GitHub）: ピル型の数字、または「記号+数」。

## 4. 候補と評価

80 桁タイトルのモック（`▌ 3` 右端はコメント数インジケータ、変更対象外）。

```
現行   │ ● 3 …/aozora-plan.md  1/3 files  y copy · s send ▌ 3 │
案1    │ ! 3 …/aozora-plan.md  1/3 files  y copy · s send ▌ 3 │  ← 採用
案2    │ 3 new …/aozora-plan.md  1/3 files  y copy · s send ▌ 3 │
案3    │ ▌ 3 …/aozora-plan.md  1/3 files  y copy · s send ▌ 3 │
案4    │ ▸ 3 …/aozora-plan.md  1/3 files  y copy · s send ▌ 3 │
案5    │ ~ 3 …/aozora-plan.md  1/3 files  y copy · s send ▌ 3 │
```

| 案 | 即読性 | グリフ衝突 | 幅（1桁時） | 備考 |
|---|---|---|---|---|
| 1 `! 3` | 高い（注意バッジの定番） | なし | 5（現行と同じ） | **採用** |
| 2 `3 new` | 最も自明 | なし | 6（+1） | 「new」は `a` で確認済みにするまで残る性質とズレる |
| 3 `▌ 3` | 中 | **タイトル右端のコメント数 `▌ N` と同グリフ** | 5 | 同一バー内で意味が2つになり混乱。却下 |
| 4 `▸ 3` | 中（n/N の移動先を示唆） | **ピッカーのカーソルマーク `▸` と同グリフ**（`▸ b.rs ⚡ ▸ 3` が並ぶ） | 5 | 却下 |
| 5 `~ 3` | 低（git 慣習の知識前提） | なし | 5 | 合算数は変更+削除なので `~` は内容を誤って示す。却下 |
| 6 `▲ 3` | 低（方向の連想が邪魔） | なし | 5 | 却下 |
| 7 数字のみピル型 | 低（「何の数か」が読めない） | なし | 3 | 却下 |

## 5. 採用案 `! N` の理由

1. **箇条書き誤読が消える**: `!` はリスト記号の語彙に存在しない。
2. **「要対応 N 件」と即読める**: メールのフラグ・通知バッジと同じ慣習。
3. **幅が現行と同一**（` ! 3 ` = 5 桁）: `title_metrics` の path 予算
   （`path_max = path_area_end - change_w - file_count_w - 1`）は計測値ベースなので
   元々どの幅でも壊れないが、ゼロインパクトであるに越したことはない。
4. **色の意味論を維持**: 黄色=注意（`⚡` と同系）。エラーは赤のまま。
5. **スロットの語彙と整合**: `⚡`（記号）→ `! N`（記号+数）→ `BASELINE`（語）の順に
   自然に並ぶ。

## 6. 変更箇所と切り替え方法

変更したのはバッジ文字列を生成する2箇所と、その説明だけ。レイアウト構造は無変更。

- `src/chrome.rs` — `scoped_change_badge()` の `format!(" ! {count} ")`
- `src/overlay.rs` — ファイルピッカー行の `review_mark` の `format!(" ! {review_count}")`
- `README.ja.md` / `README.md` — 該当記述
- テスト: `src/chrome.rs` の `review_badge_is_one_neutral_span`

別案（例: `3 new`）へ切り替える場合もこの2箇所（とテスト・README）だけ直せばよい。
`title_metrics` はバッジ幅を実測するので、文言が変わってもレイアウト計算は追従する。
