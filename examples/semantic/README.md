# Semantic Reading Layer のデモ

```sh
akapen examples/semantic/demo.md --semantic examples/semantic/demo.json
```

view モードで `-` / `+`（`=` も可）が Reading Budget ±1、`<` / `>` が ±10。
現在値はステータス行に `READ 73%` として出る。

`--semantic` を渡さなければ、この 4 つのキーは**束縛されない**。READ の
読み出しも `?` ヘルプの行も出ず、akapen はこの層が無かったときと完全に
同じ動きをする。

見え方の強さは 2 つのフラグで調整できる（既定は実機で選んだ値）。

```sh
akapen examples/semantic/demo.md --semantic examples/semantic/demo.json \
  --mark-blend 0.22 --dim-blend 0.60
```

- `--mark-blend` — MARKED の背景をページからテキスト色の方へどれだけ
  持ち上げるか。既定 0.22（dark で `rgb(68,70,89)`）
- `--dim-blend` — DIM の前景をページの方へどれだけ寄せるか。既定 0.60
  （dark の本文なら `rgb(205,214,244)` → `rgb(99,103,125)`）

DIM は `Modifier::DIM`（SGR `2`）ではなく**実際の色**である。SGR `2` は
無視する端末が多く、MARKED と見分けがつかなかったため。

## 見どころ

`## 結論` の下の 1 行:

```
採用する方式は差分配信である。詳細は付録にまとめた。
```

これは **1 つの source 行**だが、前半は Unit `u3`（ESSENTIAL）、後半は
Unit `u4`（DETAIL）に属する。

| READ | 前半「採用する方式は差分配信である。」 | 後半「詳細は付録にまとめた。」 |
| ---- | -------------------------------------- | ------------------------------ |
| 100% | MARKED                                 | NORMAL                         |
| 75%  | MARKED                                 | DIM                            |
| 30%  | MARKED                                 | DIM                            |

`## 補足` の行も同じ作りで、`つまり、…` が Unit `u9`
（SUPPORTING かつ `REDUNDANT_WITH(u3)`）、`念のため繰り返しておく。` が
Unit `u10`（DETAIL）。READ 75 % では前半 NORMAL・後半 DIM になる。

Budget を下げていくと落ちていく順は DETAIL → REDUNDANT → CONTEXT →
SUPPORTING → ESSENTIAL。目安:

| READ | DIM になっているもの                                     |
| ---- | -------------------------------------------------------- |
| 100% | なし（ESSENTIAL に薄いマーカーが乗るだけ）               |
| 75%  | DETAIL 4 つ（付録 / 念押し / 数値の目安 / 余談）         |
| 73%  | それに加えて REDUNDANT な「補足」。CONTEXT はまだ全部残る |
| 30%  | ESSENTIAL 3 つと、いちばん短い SUPPORTING 以外すべて     |

## 外部コマンドに判断させる（`--semantic-cmd`）

fixture ではなく、**外部コマンドに意味判断を返させる**経路もある。

```sh
akapen examples/semantic/demo.md \
  --semantic-cmd "python3 examples/semantic/annotate-doc.py"
```

`annotate-doc.py` は Jev を呼ばない**決定論的な参照実装**である。目的は
API キー無しでパイプライン全体を端から端まで動かせることで、判断そのものは

```text
見出し               -> ESSENTIAL
見出し直後の 1 Atom  -> SUPPORTING
それ以外             -> DETAIL
直前の文と語が重なる -> REDUNDANT_WITH
```

という素朴なヒューリスティクスでしかない。実際の Jev（LLM ではなく
System One モデル。`docs/design/jev.md` 参照）への question 設計はここには無い。

### プロトコル

akapen → コマンド（stdin、JSON 1 行）:

```json
{"version": 1,
 "source": "<文書全文>",
 "atoms": [{"index": 0, "kind": "heading", "range": {"start": 0, "end": 12}, "text": "## 見出し"}]}
```

コマンド → akapen（stdout、JSON）:

```json
{"version": 1,
 "units": [{"id": "u1", "atoms": [0], "reading_tier": "essential", "relations": []}]}
```

**コマンドは range を返さない。** 返すのは Atom の index だけで、
`SemanticDocument` は akapen 自身の `atomize()` の出力から組み立てられる。
だから外部コマンドが壊れた位置を返して文書の違う場所を装飾する、という
事故が**原理的に起きない**。`--semantic` 経路で必要だった
`source_sha256` の照合も、この経路では要らない。

返ってきた JSON は全項目を検証し、1 つでも失敗したら**レスポンス全体を
捨てる**（部分適用は何もしないより悪い）。弾かれるのは version 不一致 /
範囲外の atom index / unit id の重複 / 存在しない relation 先 / 未知の
reading_tier / 未知の relation。同じ Atom を複数の Unit が主張した場合は
**先勝ち**で、後の Unit からその index を落とす。

### 非同期

コマンドは**別スレッド**で走る。外部プロセスの起動とネットワーク往復を
挟むので、同期実行すると UI が固まるため。解析中はステータス行が

```text
L1/42 · READ 100% · 解析中…
```

になる。解析中に文書が変わったら、古い方の結果は**世代カウンタで破棄**
される（変わった後の文書に変わる前の判定を当てない）。タイムアウトは
60 秒。異常終了・タイムアウト・JSON 不正はステータス行に理由を出すだけで、
直前の注釈（同じ文書のもの）は保持される。

`--semantic` と `--semantic-cmd` は排他である。

### 自分のコマンドを書く

stdin から 1 つの JSON を読み、stdout へ 1 つの JSON を書くだけでよい。

```sh
akapen doc.md --semantic-cmd 'python3 ./jev-annotate.py'
akapen doc.md --semantic-cmd './my-annotator.ts'
```

Jev を繋ぐなら、このコマンドが**アダプタ**になる。担うのは

```text
atoms → Jev の question 群 → Jev の typed answer → units
```

で、Jev は TypeSafe の System One モデル（**LLM ではない** — typed な
question を state に対して並列評価して構造化された値を返す）である。
primitive と呼び出し方は `docs/design/jev.md` を参照。

API キーの管理は akapen の責務ではない — コマンドが自分の環境で解決する
（Jev なら `TYPESAFE_API_KEY`）。

## ファイル

| ファイル              | 中身                                                     |
| --------------------- | -------------------------------------------------------- |
| `demo.md`             | 日本語の設計メモ（AI が書きがちな、長く重複する文書の見本） |
| `demo.json`           | それに対する `semantic-reading` の `SemanticDocument`     |
| `build-demo-json.py`  | `demo.json` の生成スクリプト                              |
| `annotate-doc.py`     | `--semantic-cmd` プロトコルの参照実装（Jev を呼ばない）   |

**byte range は手で書かない。** `demo.md` を編集したら必ず

```sh
python3 examples/semantic/build-demo-json.py
```

を走らせ直すこと。`demo.json` は `source_sha256` で `demo.md` の中身を
名指ししているので、再生成を忘れると akapen は fixture を拒否して
「この fixture は別の文書のものです」と言う（`src/semantic.rs` の
`DigestChecked`）。テスト
`semantic::tests::the_demo_fixture_names_the_current_demo_md` でも落ちる。

スクリプトは Reading Policy の keep 順と累積 % の表も出力する。テストが
使う budget の閾値はその表から取っている。

## crate のテスト fixture との違い

`crates/semantic-reading/tests/fixtures/sample.{md,json}` は crate 単体の
テスト用で、**1 行の中で表示状態が切り替わる箇所を持たない**（同じ行に
並ぶ 2 つの Atom が同じ Unit に属しているため、常に同じ状態になる）。
こちらの demo はそれを実証するために別に用意したもので、crate 側の
fixture とは独立している。

## Jev に判定させる（`jev-annotate.py`）

`annotate-doc.py` が判断をしない参照実装なのに対し、`jev-annotate.py` は
**本番の判定器**である。同じ `--semantic-cmd` プロトコルを喋り、判断は Jev
（TypeSafe の System One モデル。**LLM ではない** — `docs/jev.md`）へ委譲する。

```sh
TYPESAFE_API_KEY="$(security find-generic-password -s typesafe-jev -w)" \
  akapen examples/semantic/demo.md \
  --semantic-cmd 'python3 examples/semantic/jev-annotate.py'
```

### 鍵は環境変数 `TYPESAFE_API_KEY` だけ

スクリプトはキーチェーンも `op` も見ない。**起動時に 1 回取り出して環境変数で
渡す**のが正しい形である。理由は 2 つ。akapen は再解析のたびにこのコマンドを
起動し直すので毎回 `security` や `op read` を叩くのは無駄（`op` なら生体認証が
毎回出る）。そして akapen は OSS なので、macOS 固有の手段を埋めると他 OS で
動かない。

取り出し方はどれでもよい。

```sh
# macOS キーチェーン
export TYPESAFE_API_KEY="$(security find-generic-password -s typesafe-jev -w)"

# 1Password（akapen のプロセスに限って渡す）
op run --env-file=.env -- akapen doc.md --semantic-cmd '…'

# pass
export TYPESAFE_API_KEY="$(pass show typesafe/api-key)"

# 平文（使い捨ての実験だけ）
export TYPESAFE_API_KEY=sk-…
```

未設定なら非ゼロ終了し、ステータス行に何をすればよいかが 1 行で出る。鍵は
stdout にも stderr にも出さない。`TYPESAFE_BASE_URL` / `TYPESAFE_DEFAULT_MODEL`
も SDK と同じ名前で効く（`--model` / `--timeout` でも指定できる）。

### 3 ラウンド構成

Tier の question は Unit について聞くものだが、Unit は境界判定の答えから
生まれる。**1 ラウンドでは原理的に組めない。**

```text
ラウンド1  state=文書全文, questions={ 散文どうしの境界を Choice } → Unit を確定
ラウンド2  state=文書全文, questions={ Unit ごとの Tier(Choice) }
             → 誰に redundancy を聞くか / 誰の核を聞くかが確定
ラウンド3  state=文書全文, questions={ SUPPORTING 以上の redundancy(Noul) と、
                                        ESSENTIAL な Unit の核(Choice) }
```

ラウンド 3 も畳めない。Jev は question を**並列・独立に**評価するので、
ラウンド 2 の時点では「どの Unit が ESSENTIAL か」をまだ誰も知らない。

**redundancy はラウンド 2 ではなく 3 で聞く。** 全 Unit ではなく、Tier が
SUPPORTING 以上の Unit だけに聞く — `policy::decorate` は REDUNDANT な Unit の
Tier を `weakened()` で 1 段落とすだけなので、もともと下にいる CONTEXT /
DETAIL は聞いても表示が変わらない。これで question が実測 55〜95 % 減り、
28.2 KB のこの README 自身が context window に入るようになった
（ラウンド 2 が 62,523 → 50,895 tokens、天井の 95 % → 78 %）。

akapen 側のプロトコルは 1 往復（atoms in / units out）のままで、3 ラウンドは
このスクリプトの内部事情である。

### 境界は「構造は聞かない。散文どうしだけ聞く」

設計書「Jevに判断させないもの: **syntax parsing**」のとおり、見出し・コード
ブロック・リスト項目・引用が絡む境界は**パーサが既に知っている**。demo.md の
境界 26 件のうち 17 件がそれで、Jev に聞くと質問を浪費したうえ誤りが増えた。

| 方式 | demo.json と一致 | 質問数 |
| ---- | ---------------- | ------ |
| 全部 Jev に聞く（文面 v1「話題が同じか」） | 20/26 | 26 |
| 全部 Jev に聞く（文面 v2「一緒に読む必要があるか」） | 17/26 | 26 |
| 構造ルール + 散文だけ v2 | **21/26** | **9** |

（上 2 行はプローブでの実測、最下行はこのスクリプトでの実測。内訳は構造ルール
15/17・Jev 6/9。外したのは文書冒頭のタイトル、コードブロックを含む段落、
散文どうし 3 件。）

ローカルの構造ルールは上から順に当てる。

| # | 条件 | 判定 |
| - | ---- | ---- |
| 1 | 次が `heading` | NEW_UNIT |
| 2 | 現在が `heading` | SAME_UNIT（見出しは直後の内容に付く） |
| 3 | どちらかが `code_block` / `table` | NEW_UNIT（単独の Unit） |
| 4 | どちらも `list_item` | SAME_UNIT |
| 5 | どちらも `sentence` | **Jev に聞く** |
| 6 | それ以外 | NEW_UNIT（既定。引用と散文の間など） |

規則 4 と、規則 2 が規則 3 に勝つこと（`## 見出し` + コードブロックは 1 つの
Unit）と、`block_quote` が規則 6 で単独になることは、**demo.md に現れないので
測っていない**。箇条書きを 1 つにまとめるのは、著者が既にまとまりとして束ねた
構造であり、半分だけ DIM になったリストは読み物として壊れるため。

### redundancy は方向を指定する

「これより**前**の箇所ですでに述べられた内容の言い直しか」と聞く。対称に
「重複しているか」と聞くと結論まで拾う（実測で結論の Unit が 0.71 を出し、方向
ありに直すと 0.36 へ落ちた）。設計書が「**既読内容との** redundancy」と書き、
Duggan & Payne の satisficing が逐次的なモデルであることと整合する。

Noul は「言い直しか」までしか答えないので、`REDUNDANT_WITH` の**参照先**は語の
重なりでローカルに選ぶ。現在の `policy::keep_order` は `is_redundant()` しか見て
いないため、参照先の選び方は表示に効かない。

### confidence は記録するだけ

`conf < 0.5 なら NEW_UNIT に倒す`は**採用していない**。実測で閾値が値の真上に
乗り、実行ごとに答えが揺れた。捨てもせず、返す JSON に載せる。

```json
{"version": 1,
 "units": [{"id": "u3", "atoms": [3, 4], "reading_tier": "essential", "relations": [],
            "jev": {"tier_choice": "essential", "tier_confidence": 1.0,
                    "redundancy_noul": 0.37}}],
 "jev": {"rounds": [{"questions": 9, "elapsed_s": 0.73, "usage": {…}}],
         "boundaries": [{"after_atom": 4, "decision": "new_unit", "by": "jev",
                         "confidence": 0.8}]}}
```

`jev` は akapen のプロトコルに無いフィールドで、**読み飛ばされる**（未知の
フィールドは拒否しない）。使い道は実測してから決める。

### demo.md での実測

| | ラウンド 1 | ラウンド 2 | ラウンド 3 |
| - | --------- | --------- | --------- |
| question 数 | 9（境界 26 件のうち散文どうしだけ） | 16（Unit 16 の Tier） | 6（redundancy 5 + 核 1） |
| 所要 | 0.71 秒 | 0.72 秒 | 0.51 秒 |
| input tokens | 3,197 | 4,329 | 1,642 |

合計 9,168 input tokens ＝ **約 $0.0004**（出力トークンは無料）。1 回の解析で
往復は 3 回。Budget の上げ下げでは Jev を呼ばない。

### 大きな文書での実測（2026-09-21）

demo.md は 1,664 バイトしかない。**日常的に開く大きさの文書で測り直した。**
どれも 2 回ずつ（45,650 バイトのものは 7 回）、`--timeout 120` で走らせている。

| 文書 | バイト | Atom | R1 質問 | R1 秒 | R1 tokens | R2 質問 | R2 秒 | R2 tokens | 全体 |
| --- | ---: | ---: | ---: | ---: | ---: | ---: | ---: | ---: | ---: |
| `demo.md` | 1,664 | 27 | 9 | 0.69 | 3,197 | 31 | 0.69 | 6,088 | 1.50〜1.55 秒 |
| `design/semantic-reading-layer.md` | 9,857 | 221 | 36 | 0.82 | 12,390 | 301〜305 | 1.45 | 49,609 | 2.33〜2.45 秒 |
| `design/jev.md` | 15,656 | 149 | 71 | 1.03 | 26,067 | 163〜169 | 1.23 | 38,139 | 2.30〜2.48 秒 |
| `gotchas.md` | 24,280 | 181 | 121 | 1.52 | 46,389 | 153〜159 | 1.42 | 46,107 | 2.88〜3.27 秒 |
| 実業務の `CLAUDE.md` | 45,650 | 218 | 21 | 1.00 | 23,935 | 67 | 1.36 | 60,518 | **2.42〜2.63 秒** |

**時間は問題ではない。** 45,650 バイトで 2.5 秒、akapen の `COMMAND_TIMEOUT`
（60 秒）には 18 倍の余裕がある。

### 本当の上限は context window（≒ 65,536 input tokens）

大きな文書で先に当たるのは**時間ではなく大きさ**である。超えると 2 秒台で
HTTP 400 `max_tokens_exceeded` が返る（待っても変わらない）。

| 条件 | input tokens | 結果 |
| --- | ---: | --- |
| 実業務の `CLAUDE.md` そのまま（45,650 B） | 60,518〜63,152 | OK（**天井の 92〜96 %**） |
| 同じ文書を 1.04 倍（47,556 B） | 64,851 | OK |
| 同じ文書を 1.06 倍（48,470 B） | — | **失敗** |
| state 固定で question を増やす二分探索 | 65,033 | OK |
| 同上 | 約 65.5k | **失敗** |

天井は `65,536`（2^16）と読めるが、**TypeSafe の公式値は未確認**である。設計書
`docs/design/jev.md` も「context window は需要に応じて変わりうる」と書いている。
バイト数での上限（この日本語文書では約 2.6 バイト/token）は文書の言語に依存する
ので、**上限は tokens で言うこと**。

ラウンド 2 が重かったのは、`state`（文書全文）に加えて**各 Unit の本文を Tier と
redundancy で 2 回引用していた**ためである。redundancy を SUPPORTING 以上へ
絞ってからは引用が原則 1 回になり、この README で 62,523 → 50,895 tokens に
下がった。**この表の数字は絞り込み前のものである。**

### リクエスト分割 — 64k の側を外す（2026-09-21 の実測）

**1 リクエストに収まらない文書を、リクエストを分けて通す。** 実装は
[`send_in_chunks`](jev-annotate.py) で、**3 ラウンドすべてが同じものを使う**。
ラウンド 2 専用にしていない — 実測では 58 KB のこの README は**ラウンド 1・2・3
のどれもが単独で天井を超える**ので、1 つのラウンドだけ直しても通らない。

#### 制約は 2 つあって、分割で外せるのは片方だけ

| 制約 | 値 | 分割で外せるか | 実装 |
| --- | ---: | --- | --- |
| 1 リクエスト全体 | 64k tokens | **外せる** | `RequestBudget.whole` がチャンクの切れ目を決める |
| `state` + 最長の question | 32k tokens | **外せない** | `RequestBudget.pair` が question 単位で拒む |

`state` は**どのチャンクにも丸ごと乗る**（設計書「全文を Context として扱う」）。
だからリクエストを増やしても `state + その question` は小さくならない。
**分割後の本当の天井は 32k 側である。**

#### 新しい天井 — 3 つある。使えるのは**いちばん低いもの**

「`state` が 32k に収まるか」は正しいが、**実用の天井はそれより低い**。
`state` が収まっても、**question を置く余地が残らなければ何も聞けない**。

`docs/handoff-archive.md` の先頭を切り詰めた**合成の文書**で測った
（この文書の混ざり方は 0.366 tokens/byte）。

| 天井 | `state` tokens | この文書でのバイト数 | 何が起きるか |
| --- | ---: | ---: | --- |
| **実用（この実装）** | ~29,700 | **約 80 KB** | ここまでは全 question が送れる |
| API が受け付ける限界 | ~31,000 | 約 83 KB | 実装のマージンが拒む（下） |
| `state` だけが収まる限界 | 32,609 | 約 89 KB | question が 1 つも置けない |

実測:

| prefix | `state` tokens | `pair` 予算 | 結果 |
| ---: | ---: | ---: | --- |
| 64,998 B | 23,808 | 6,912 | OK |
| **80,000 B** | **29,672** | **1,048** | **OK** — 376 Unit / 11 リクエスト / 14.5 s / 送れなかった question 0 |
| 83,259 B | 30,808 | **−88** | **失敗**（この実装が拒む） |
| 89,072 B | 32,609 | — | `state` + 最小の question でも API が失敗 |

**80 KB は `docs/gotchas.md`（65 KB）より大きい。** ただし
「`state` が 32k に収まる限り通る」は**字義どおりには成り立たない** —
83,259 B の `state` は 30,808 tokens で 32,768 に収まっているのに通らない。
「収まる」と「通る」のあいだに **約 3k tokens（この文書で 6〜9 KB）の差**が
ある。question を置く余地が要るからで、**実用の天井は `state` の天井より
低い**。

**83 KB では API 自体はまだ通る。** `state` + 本物の Tier question 1 つを
直接投げると `usage` は 30,967 で、32,768 まで **1,801 tokens 残っていた**。
拒んでいるのはこの実装で、内訳は `CORE_QUESTION_MARGIN`（2,048）と
question の見積もりの 1.4 倍ぶんである。**約 3 KB を取りこぼしている** —
分かったうえでそのままにしてある（マージンが吸っているのは見積もり誤差で、
削ると 400 側に倒れる）。

#### 崖であって坂ではない — だから 1 つも聞けないときは失敗させる

Tier question の固定費はほぼ一定（実測 181 / 見積もり 257）なので、`pair`
予算がそれを下回った瞬間に**全部の question が同時に送れなくなる**。
80 KB で 0 件、83 KB で 530 件全部、という落ち方をする。

**ここを塞ぐ前は、83 KB の文書が exit 0 で「530 Unit すべて `detail`」を
返していた。** `state` は 32k に収まるので probe は通り、足りないのは
question のぶんだけ — **いちばん気づきにくい壊れ方**である。いまは
[`annotate`] が失敗させる:

```text
jev-annotate: 文書が大きすぎます。state が 30808 tokens あり、32k の枠に
question の余地が 0 tokens しか残らないので、Tier を 1 つも聞けません。
```

`UNANSWERED_TIER` は**個別の巨大な Unit のための落とし先**であって、文書
全体の落とし先ではない。「それらしく見えるが何も判定していない注釈」を
返さないのは、`apply_boundary_answers` が黙って埋めないのと同じ理由である。

#### `state` の tokens/byte は文書ごとに違う — 1 つの係数で外挿しない

5 文書を実測した（`ask_jev` に最小の question だけを付けて `usage.input_tokens`
を読み、空 `state` の floor 282 tokens を引いた値）。

| 文書 | バイト | `state` tokens | tokens/byte | 32k 枠に対して |
| --- | ---: | ---: | ---: | ---: |
| `examples/semantic/demo.md` | 1,664 | 583 | 0.350 | 2 % |
| `docs/design/semantic-reading-layer.md` | 9,857 | 3,357 | **0.341** | 10 % |
| `examples/semantic/README.md` | 58,032 | 23,147 | **0.399** | 71 % |
| `docs/gotchas.md` | 65,225 | 24,169 | 0.371 | 74 % |
| `docs/handoff-archive.md` | 106,518 | — | — | **超過** |

幅は **0.341〜0.399** で、いちばん低い文書といちばん高い文書で **17 % 違う**。
同じ 32k 枠を、`design` の混ざり方なら 96 KB まで、この README の混ざり方なら
82 KB までしか使えない。**この 2 つは外挿である**（実測したのは上の 89 KB
だけ）。

かつてここには「日本語なら 85 KB 前後と外挿できる」と書いてあった。**当たって
いたが、当て方が悪い** — 1 つの係数で外挿すると、どの文書に当たるかで 14 KB
ぶれる。

**リクエスト数と input tokens は probe を含む。** 含めないと 7 % 少なく出る

- **小さい文書は 1 リクエストのままである。** `demo.md` と `design` は 3 ラウンド

- `handoff-archive.md` は**分割しても通らない**。`state` だけで 32k を超える

- リクエスト数の内訳は「probe 1 + チャンク」である。`README.md` は 3+3+1、
  `gotchas.md` は 4+3+2

#### 分割のコストは `(チャンク数 − 1) × state` ちょうど

| 文書 | 総 input | うち繰り返した `state` | 割合 |
| --- | ---: | ---: | ---: |
| この `README.md` | 343,900 | 115,735（余分な 5 回） | 34 % |
| `docs/gotchas.md` | 446,903 | 169,183（余分な 7 回） | 38 % |

「余分な回数」は `state` を載せた回数（probe + 全チャンク）から、分割が
要らなければ済んだ 3 回を引いたもの。

それ以外は増えない。**`state` を切り詰めて安くする案は採らない** — 設計書が
「全文を Context として扱う」と決めていて、それは分割の話ではなく設計の話で
ある。

#### 並列化は次のタスクにしない（いまは要らない）

いちばん遅い `gotchas.md` で **12.7〜13.0 秒**、akapen の `COMMAND_TIMEOUT`
（60 秒）に 4.6 倍の余裕がある。1 リクエストあたりは最遅でも 1.5 秒。

**ただし以前の「3 ラウンド × 20 秒 = ちょうど 60 秒」という理屈はもう
成り立たない。** リクエストは 10 本になりうるので、`DEFAULT_TIMEOUT` が
そのまま効けば 200 秒である。天井に張り付く文書を足すときは、1 リクエストの
タイムアウトではなく**リクエストの総数**を見ること。

#### 分割は意味的に中立か — 実測

Jev は question を state に対して**並列・独立に**評価するので、question を
複数のリクエストに分けても各 question の答えは変わらない**はず**である
（`docs/design/jev.md`）。**「はず」で済ませずに測った。**

測り方は `docs/gotchas.md` 5.1 に合わせた。**ラウンド 1 は 1 度だけ走らせて
Unit の組を固定し**、同じ Tier question の集合を条件ごとに複数回送っている
（境界の揺れを Tier の揺れに混ぜないため）。**床と変種はラン数を揃えてある**
（`docs/gotchas.md`「揺れの幅どうしを比べるときは、ラン数を揃える」）。

| 文書 | Unit | ラン | 床 | 変種 | 変種の中身 | 判定 |
| --- | ---: | ---: | --- | --- | --- | --- |
| `demo.md` | 17 | 8 | **100.0 %** | **100.0 %** | 分割(5) × 非分割 | 床の中 |
| `design/…` | 172 | 4 | 91.3〜95.9 % | 90.7〜95.9 % | 分割(5) × 非分割 | **重なる** |
| この `README.md` | 306 | 4 | 97.4〜98.4 % | 96.7〜99.0 % | 細かい分割(5) × 本番の分割(3) | **重なる** |
| `docs/gotchas.md` | 244 | 4 | 93.9〜95.1 % | 92.2〜96.3 % | 細かい分割(5) × 本番の分割(3) | **重なる** |

**4 文書とも床と重なる。** Jev の独立性の理解は、少なくともこの範囲では
正しかった。判定は `docs/gotchas.md`「退行の判定 — 基準の版と同じラン数で、
幅が重なるかを見る」に従っている（**重なれば退行ではない**）。**「床の中」に
完全に入っているのは `demo.md` だけ**で、その床は幅ゼロなので判定に使えない。

**変種の幅が両側に広いのは、組の数が違うためでもある。** 床は同条件どうしの
組み合わせで 6 組（4 ランなら C(4,2)）、変種は 4 × 4 = **16 組**である。
組を増やせば観測の最小も最大も外へ動くので、3 文書とも変種の下限が床の下限を
わずかに割り、上限も床の上限を超えている。**下限だけを取り出して劣化と
読まないこと** — 「ラン数を揃える」（`docs/gotchas.md`）と同じ罠が、
組の数でも起きる。

**`README.md` と `gotchas.md` で見ているものは違う。** この 2 つは非分割が
そもそも通らないので、比べているのは「分割したかどうか」ではなく
**「切れ目の位置を変えたかどうか」**である。分割そのものの中立性を見られる
のは非分割が通る `demo.md` と `design` だけで、`README.md` / `gotchas.md` は
**切れ目の位置に対する安定性**である。

**`demo.md` の床は床になっていない。** 8 ランすべてが 100 % で、**幅がゼロ**
である。幅で判定する方式は幅がないと働かないので、`demo.md` は
「下回っていない」としか言えない。実際、これより前に 4 ラン で測ったときは
床 100 %・変種 94.1〜100 %（17 Unit のうち 1 つが違う）で、**同じ規則では
「床を下回る」と読めてしまった**。8 ランでは再現していない。
`docs/gotchas.md`「2 ランの床を床と呼ばないこと」と同じ罠で、**床がゼロ幅の
文書でも判定しないこと**。

#### 見積もりは実測の 1.5 倍に出る（分かっていて、そのままにしてある）

`question_tokens` は器 68 tokens（実測）+ 本文 0.5 tokens/byte で見積もる。
Tier question の実測は 181 tokens で、見積もりは 257 を返す（1.42 倍）。
定型文が日本語で実レートが 0.376 tokens/byte しかないためである。

結果として**チャンクは必要より少し多く割れる**。この README のラウンド 2 は、
見積もりで予算 40,059 まで詰めて 3 チャンクになったが、実際の input は 1 チャンク
49,613 tokens（うち `state` 23,429）で、**question は予算の 65 % しか使って
いない**。2 チャンクで収まったはずで、余計に払ったのは `state` 1 回ぶん
（23,429 tokens ＝ 総量の 7 %）である。

**直していない。** 見積もりが小さすぎると 400 で落ちるので、倒すなら多い側で
ある。詰めるなら「**question の本文は `state` からの引用なので、その文書の
実測 tokens/byte がそのまま使える**」という手があり、`state` を実測している
文書（大きい文書＝まさに詰めたい文書）ではその値が既に手元にある。ここは
測っていない。

#### 送れなかった question の落とし先

`state` + その question だけで 32k を超える question は、**どう分割しても
送れない**。ラウンドごとに落とし先を決めてある。

| ラウンド | 送れなかったとき | なぜ安全側か |
| --- | --- | --- |
| 1（境界） | **NEW_UNIT** に倒す | SAME だと Unit がさらに大きくなり、ラウンド 2 も送れなくなる。NEW なら Unit は小さいまま |
| 2（Tier） | **`detail` + `core_atoms: []`** | 下の `UNANSWERED_TIER` の項 |
| 3（redundancy） | 聞かない | REDUNDANT にならないだけ。既存の「CONTEXT / DETAIL には聞かない」と同じ状態 |
| 3（核） | 聞かない | Unit 全体が MARKED。絞り込めないだけで注釈としては壊れない（従来どおり） |

**境界だけが落ちる帯がある。** 境界 question は Atom 2 つを引用するので、
Atom 1 つぶんの Tier question より先に予算を割る。その帯では**全境界が黙って
NEW_UNIT になる**（失敗はしない）。`jev.unsent.boundary` に件数が出るので、
Unit 数が急に増えたときはそこを見ること。5 文書では 0 件だった。

ラウンド 2 だけ従来の落とし先が無かった。**選んだのは既定値
`detail` + `core_atoms: []`** で、理由は 4 つ:

1. `core_atoms: []` は「核を持たない」＝ **MARKED にならない**（プロトコルの
   3 値）。だから既定の Tier が決めるのは「**いつ沈むか**」だけで、
   「読む価値が高い」と嘘をつく経路は最初から無い
2. `detail` を選んだのは `policy::decorate` の打ち切り方のためである。
   `keep_order` は Tier を第 1 キーに長さの昇順で並べ、`decorate` は**最初に
   予算へ入らなかった Unit で `break` する**。送れないほど巨大な Unit を上位
   Tier に置くと、そこで打ち切られて**その下の Unit が丸ごと巻き添えで沈む**。
   `detail` なら順序の最後尾なので、被害はその Unit 自身に閉じる
3. **Unit を落とす案は却下した。** `decorate` の `total` は全 Unit のバイト長の
   合計なので、Unit を消すと Budget の分母が黙って縮み、「Budget 50 %」が指す
   量が文書によって変わる
4. **文書全体を失敗させる案も却下した。** 核の既存の落とし先と作法を揃えた。
   1 つの巨大な Unit のために文書全体の注釈を失うほうが損失が大きい

**実測では 5 文書とも 0 件だった。** この経路に来るには 1 つの Unit の本文が
18 KB 前後になる必要がある。**動いたところを見ていない落とし先である**
（テストでは人工的に踏ませてある。`UnansweredTierTest`）。

#### 確認したこと

`examples/semantic/dump-request` で本番と同じ要求 JSON を作り、アダプタを akapen
抜きで単体実行した。凍結した 5 文書のコピー（`shasum -a 256` を控えてある）を
before（分割前のコミット `2203d93`）と after で各 2〜3 回。`state` の tokens は
5 文書 + 二分探索の 6 点。Tier 一致率は 4 文書 × 床と変種 × 4〜8 ラン。天井の
二分探索は `docs/handoff-archive.md` の先頭を切り詰めた**合成の文書**。表示は
`decorate-report` を `docs/gotchas.md`（65 KB、248 Unit）に当て、Budget
100/80/60/40/20/1 % が単調に沈むことを見た。

**していないこと**: akapen 本体の TUI で開いていない（`decorate-report` は
`policy::decorate` そのものだが、画面では見ていない）。並列化は測っていない。
`handoff-archive.md` の全文は一度も通していない（通らないので）。

### 何が時間を使っているかの切り分け

2 軸を独立に振って測った（どちらも同じ 1 リクエスト）。

| 条件 | question 数 | input tokens | 所要（中央値） |
| --- | ---: | ---: | ---: |
| 往復の床（極小 state・1 question） | 1 | 277 | 0.58 秒 |
| **state 固定**（45,650 B）・question を変える | 1 | 17,750 | 0.91 秒 |
| 〃 | 20 | 21,876 | 1.03 秒 |
| 〃 | 87 | 63,152 | 1.42 秒 |
| **question 固定**（同じ 20 個）・state を変える | 20 | 5,167 | 0.68 秒 |
| 〃 | 20 | 13,201 | 0.81 秒 |
| 〃 | 20 | 21,876 | 1.00 秒 |

question を 1 → 87（87 倍）にしても 0.91 → 1.42 秒にしかならない。**question の
個数そのものは、時間にはほぼ効かない** — 「全 question を並列・独立に評価する」
が実際にそう動いている。両軸を通すと `約 0.55 秒 + 1.3 マイクロ秒/token` で
説明がつき、question 数の単独の寄与は誤差に埋もれる。

ただし **tokens では question 数はタダではない**。question 1 つにつき定型文
（instructions の枕と `criteria`）が約 116 文字乗る。時間ではなく**天井**に
効くのはこちらである。

### Atom を細かくするとどうなるか

`atomize` がリスト項目を文へ割るようになると Atom 数が増える。**同じ文書・同じ
state で、question の粒度だけを変えて測った**（`atomize.rs` は触らず、計測側で
割っている）。

決定変数は **割ったあとの `kind`** である。

| 文書 | 粒度 | Atom | R1 質問 | R2 質問 | R2 引用本文 | R2 定型文 |
| --- | --- | ---: | ---: | ---: | ---: | ---: |
| `CLAUDE.md` | 粗い（現状） | 218 | 21 | 87 | 40,694 | 10,089 |
| 〃 | 細かく割るが `kind` は `list_item` のまま | 404 | 24 | 93 | 41,072 | 10,782 |
| 〃 | 細かく割って `kind` を `sentence` にする | 404 | **278** | **677** | 41,656 | **78,234** |

**引用する本文の総量は粒度でほとんど変わらない**（40,694 → 41,656 文字）。
変わるのは question の個数と、それに比例する定型文である。

- `kind` が `list_item` のままなら、構造ルール 4（`list_item` どうしは
  SAME_UNIT）が効くので **question はほぼ増えない**（21 → 24、87 → 93）
- `kind` が `sentence` になると規則 5 で Jev に聞く境界が激増し、`CLAUDE.md`
  では R1・R2 とも **`max_tokens_exceeded` で失敗した**

時間の方は、粒度が実際に変わって**かつ収まる**文書（`design/jev.md`、Atom
149 → 154）で R1 1.05 → 1.01 秒・R2 1.54 → 1.41 秒と、**横ばい**だった。
「Atom を細かくすると並列が増えて速くなる」は観測されていない。速くも遅くも
ならず、**天井に当たるかどうかだけが変わる**。

表示は、`## 結論` の下の 1 行で**行の途中が切り替わった**。

| READ | 「採用する方式は差分配信である。」 | 「詳細は付録にまとめた。」 |
| ---- | ---------------------------------- | -------------------------- |
| 100% | MARKED | NORMAL |
| 70%  | MARKED | NORMAL |
| 60%  | MARKED | **DIM** |

`demo.json`（人の注釈）では 75 % で切り替わる（このページ上部の表）。Jev の
判定では 60 % だった。一方 `## 補足` の行は、Jev が `つまり、…` と
`念のため繰り返しておく。` を**どちらも DETAIL** と見たため 90 % で両側とも
同時に DIM になり、行の途中では切り替わらなかった。

### MARKED を Unit の核だけに絞る（2026-09-21 の実測）

45.6 KB の実業務文書（`CLAUDE.md`）を開くと、**画面の半分近くが MARKED**
だった。原因は Atom の粒度ではなく **Unit** である。境界の構造ルール 4
（`list_item` どうしは SAME_UNIT）が箇条書き 1 つを丸ごと 1 Unit にまとめ、
`policy::decorate` が Unit の Tier を構成 Atom **全部へ一律に**投影していた。
だから ESSENTIAL な箇条書きは段落ごと光る。直前の改修で Atom を 218 → 372 へ
細かくしても、**比率は 1 % も動かなかった**（判断も表示も Unit のままだったため）。

そこでラウンド 3 を足し、MARKED になる Unit にだけ

> このまとまりから **1 か所だけ**読むとしたら、どこを読めば要点が取れるか

を Choice で聞いて、**その Atom だけを MARKED、同じ Unit の残りを NORMAL** に
した。選択肢は Unit を構成する Atom の本文そのもの（キーは `atom:<index>`）。

**この文面はこの日のうちに損失ベースへ差し替えた**（次の節）。この節の数字は
差し替え**前**の文面で取ったものである。

**DIM は一律のままである。** Unit が落ちたなら丸ごと沈む — ここを選択的に
すると「なぜこの行の一部だけが沈むのか」を読者に説明できない。

比率（`decorate-report`。分母は Atom のバイト長の合計）:

| 文書 | Budget | MARKED 前 | MARKED 後 | NORMAL 前 → 後 | DIM 前 → 後 |
| --- | ---: | ---: | ---: | --- | --- |
| `CLAUDE.md` (45.6 KB) | 100 % | 46.7 % | **5.0 %** | 53.3 → 95.0 | 0.0 → 0.0 |
| 〃 | 80 % | 46.7 % | **5.0 %** | 22.2 → 63.1 | 31.1 → 31.9 |
| 〃 | 60 % | 46.7 % | **5.0 %** | 8.2 → 49.1 | 45.1 → 45.9 |
| 〃 | 40 % | 22.2 % | **2.9 %** | 0.0 → 19.8 | 77.8 → 77.3 |

### 箇条書きを項目ごとに割る（規則 4 の変更・2026-09-21 の実測）

**結論から: 実装はしたが、置いた合格条件は満たさなかった。** MARKED 比率が
揺れの床を超えて増える。採否は下の「定性的な証拠」と合わせて人が決めること。

#### 何を変えたか

境界の構造ルール 4 は「`list_item` どうしは SAME_UNIT」だった。これだと
箇条書きが丸ごと 1 Unit になり、**10 個の決定事項が全部同じ Tier**になる。
ユーザーの言葉:

> 決定事項は一緒に沈むので正しい。が、しょうもない決定事項があれば個別に
> 沈んで欲しいという気持ちもある。

そこで規則 4 を「**別項目どうしは NEW / 同じ項目の中は SAME**」に変えた。
判別は構造だけで、Jev には聞かない（設計書「Jev に判断させないもの:
syntax parsing」）。手がかりは `atomize` が項目の Atom を**マーカーから**
始めることで、継続文にはマーカーが無い。

**割るのはトップレベルの項目の切れ目だけである。** 子項目は親に SAME のまま
残す。ユーザーの言う「決定事項」は親項目＋その詳細の束なので、そこで割ると
`policy::decorate` の docstring が警告する「半分だけ DIM のリスト」が親子の
あいだで起きる。深さは要求 JSON から取れる — `range.start` から直前の改行まで
戻れば行頭のインデントが読める（[`list_marker_indent`]）。

境界の内訳（構造だけで決まるので、Jev を呼ばずに数えられる）:

| 文書 | 規則 4 が当たる境界 | → NEW（別項目） | SAME（子項目） | SAME（継続文） |
| --- | ---: | ---: | ---: | ---: |
| `demo.md` | 1 | 1 | 0 | 0 |
| `design/semantic-reading-layer.md` | 21 | 21 | 0 | 0 |
| この `README.md` | 6 | 3 | 0 | 3 |
| 業務議事録 22.7 KB | 94 | 46 | 0 | 48 |
| 業務 `CLAUDE.md` 45.6 KB | 314 | **97** | **63** | 154 |

**ネストを持っていたのは `CLAUDE.md` だけ**である（インデント 2 が 55 件、
4 が 8 件）。子を割らない判断がここで 63 Unit を節約している。

#### Unit 数と context window

Unit 数は実際の Jev の答えから数えたもの（実行ごとに境界が揺れるので幅がある）。
R2 の input tokens は `usage` の実測で、括弧内は実測の天井 65,536 に対する割合。

| 文書 | Unit 前 | Unit 後 | R2 tokens 前 | R2 tokens 後 |
| --- | ---: | ---: | --- | --- |
| `demo.md` 1.6 KB | 16 | 17 | 4,329 (7 %) | 4,511 (7 %) |
| `design/…` 9.9 KB | 150〜152 | 172〜173 | 34,027〜34,389 (52 %) | 38,029〜38,211 (58 %) |
| この `README.md` 32.5 KB | 181〜183 | 185〜186 | 58,285〜58,651 (89 %) | 59,014〜59,197 (90 %) |
| 業務議事録 22.7 KB | 46〜48 | 92〜95 | 25,260〜25,620 (39 %) | 33,619〜34,160 (52 %) |
| 業務 `CLAUDE.md` 45.6 KB | 34〜35 | 130〜132 | 40,910〜41,092 (62 %) | 58,370〜58,733 (**89 %**) |

**`CLAUDE.md` は天井を超えなかった。** 事前の見積もりでは超える計算だったが、
その計算は 1 Unit あたりの固定費を **262 tokens**（Tier 181 + redundancy 81）と
置いていた。redundancy は既にラウンド 3 へ移してあって SUPPORTING 以上にしか
聞かないので、**ラウンド 2 に乗る固定費は Tier の 181 だけ**である。加えて
子を割らない判断が 63 Unit を節約した。実測は `40,911 + 97 × 181 ≒ 58,500` と

**ただし余裕は無い。** `README.md` は 90 %、`CLAUDE.md` は 89 % に載っている。
これは規則 4 の欠陥ではなく、規則 4 と無関係に今日もある既存の崖である
（`docs/gotchas.md` 未解決 5）。**R2 を分割する実装はここでしない。**

#### MARKED 比率 — ここで落ちた

**まず揺れの床を測った。** 変更前を同じ要求で複数回走らせ、MARKED 比率が
どれだけブレるかを見る。床を知らずに閾値を置くと「変更なし」すら棄却する
基準になる（`docs/gotchas.md` 5.1 と同じ作法）。

分母は Atom のバイト長の合計、Budget 100 %。括弧内はラン数。

| 文書 | 変更前＝揺れの床 | 変更後 | 判定 |
| --- | --- | --- | --- |
| `demo.md` | 12.8〜13.4 % (4) | 16.6 % (4) | **床を超えて増加** |
| `design/…` | 22.9〜26.0 % (4) | 23.1〜26.0 % (4) | 床の中 |
| この `README.md` | 2.9 % (2) | 1.4〜1.5 % (2) | 減少 |

**5 文書のうち 3 文書で、MARKED が揺れの床を超えて増えた。** 合格条件は
「床を超えて増えていないこと」だったので、**不合格**である。

理屈は素直で、これは**予見されていた本当のリスク**そのものだった。MARKED は
「ESSENTIAL かつ非 REDUNDANT な Unit」ごとに 1 つの核 Atom として付く
（[`wants_core`]）。Unit が割れれば ESSENTIAL な Unit が増え、MARKED は
比例して増えうる。ユーザーの要望は

> パーセントにかかわらず、これさえ見ればオッケー的なミニマルな提案

なので、MARKED が増えるのは要望に反する。

**Tier 一致率は測っていない。** その床は「同じ分割どうし」の比較で測った値で、
分割そのものを変える今回には使えない。

#### 定性的な証拠 — 要望そのものは叶っている

数字は落ちたが、**ユーザーが言った現象は実際に直っている。** 業務議事録の
`## 決定事項`（番号つき 8 項目）を Budget 60 % で見る。

変更前は 8 項目が**丸ごと 1 Unit** で、**8 項目すべてが一斉に DIM** になる。
これが「決定事項は一緒に沈む」である。

変更後は項目ごとに割れて、沈み方が分かれた:

| 決定事項 | 変更前 | 変更後 |
| --- | --- | --- |
| 決定 1 | DIM | DIM |
| 決定 2 | DIM | **MARKED** |
| 決定 3 | DIM | **MARKED** |
| 決定 4 | DIM | DIM |
| 決定 5 | DIM | NORMAL ＋ 核が MARKED |
| 決定 6 | DIM | **MARKED** |
| 決定 7 | DIM | DIM |
| 決定 8 | DIM | DIM |

**「しょうもない決定事項が個別に沈む」は起きている** — 1・4・7・8 が沈み、
2・3・5・6 が残る。変更前は全部まとめて沈むか、まとめて残るかしかなかった。

**同時に、MARKED が 0 個から 4 個へ増えている。** これが上の比率の正体である。
要望の 2 つの側面がここで正面から衝突する:

- 「しょうもない決定事項が個別に沈んで欲しい」 → **叶う**
- 「これさえ見ればオッケー的なミニマルな提案」 → **反する**

**採否はこの取引をどう見るかで決まる。** 測った側で決めていない。

#### 親と子はどう扱われたか

ネストがあるのは `CLAUDE.md` だけである。親項目・子項目・継続文が 1 つの Unit に
まとまり、核は 1 つだけ MARKED になる — 「半分だけ DIM のリスト」は起きていない。

本文は業務文書なので伏せる。**構造だけ**を書くと、1 つの Unit が

```text
Unit u41  tier=essential  core=[79]
  idx 73  項目(indent=0)   ← 親項目
  idx 74  継続文
  idx 75  継続文
  idx 76  継続文
  idx 77  項目(indent=2)   ← 子項目
  idx 78  継続文
★ idx 79  項目(indent=2)   ← 子項目（ここが核）
  idx 80  継続文
```

のようにまとまり、**核は 1 つだけ**である。

#### 増えたぶんは「1 Atom の Unit」だけに寄ってはいない

`assign_lone_cores` は散文の候補が 1 つしかない Unit の核を**聞かずに**決める
ので、項目ごとに割ると「1 Atom の Unit がそのまま光る」経路が増える。これは
上の「箇条書きのラベルが MARKED になる」（`docs/gotchas.md`）と同じ形なので、
**そこだけ直せば増加を消せるのではないか**を確かめた。

MARKED になる Unit（ESSENTIAL かつ非 REDUNDANT）の内訳:

| 文書 | | MARKED Unit | うち Jev が核を選択 | うち 1 散文 Atom（聞かず） |
| --- | --- | ---: | ---: | ---: |
| 業務 `CLAUDE.md` | 前 | 11〜12 | 7〜8 | 4 |
| | 後 | **25〜26** | **16〜17** | **9** |
| 業務議事録 | 前 | 10〜12 | 6〜8 | 4〜5 |
| | 後 | **16〜19** | **9〜11** | **7〜8** |

**どちらの経路も同じ比率で増えている。** 逃げ道は無い — 増加は 1 Atom の Unit の
扱いではなく、**分割そのもの**から来ている。「個別に沈む」と「MARKED を増やさない」
を別々に取ることは、この実装ではできない。

#### run キャップを入れたらどこまで戻るか（数えただけ・未実装）

衝突している 2 つの要望はメカニズムが別である。**沈む**のは Tier（Unit ごと）、
**光る**のは核（`wants_core` が Unit ごと）。そこで「Tier は項目ごとのまま、核は
**リスト 1 本につき 1 つ**」にしたらどうなるかを、既存の応答から数えた。

ここで **run** とは、規則 4 由来の境界（`rule:new_list_item`）でつながった Unit の
並び ＝ 1 本のリストである。上限は

    「MARKED になりうる Unit を 1 つ以上含む run」の数
      + どの run にも属さない単独の MARKED Unit の数

で、run キャップを入れたときの MARKED Unit 数の**上限**になる。

| 文書 | 変更前 | 変更後 | run キャップ上限 |
| --- | ---: | ---: | ---: |
| 業務 `CLAUDE.md` | 11〜12 | 25〜26 | **13〜14** |
| 業務議事録 | 10〜12 | 16〜19 | **13〜14** |
| `design/…` | 35〜38 | 37〜42 | **33〜38** |
| この `README.md` | 7 | 6 | **6** |
| `demo.md` | 3 | 4 | **3** |

**5 文書とも変更前の水準に戻る。** つまり増加の出どころは「**1 本のリストの中で
複数の項目が光る**」であって、「丸ごとだと CONTEXT だったリストが、割ると中に
ESSENTIAL が現れる」ではない。後者なら run キャップでは消えないはずだが、消える。

`design` は上限の下側が変更前の下限（35）より低い（33）。run キャップは
**変更前より MARKED を減らしうる** — 変更前から 1 本のリストが複数 Unit に
分かれていた箇所（散文の境界で割れたもの）にも効くためである。

**これは上限であって実測ではない。** 実装すれば核の question の出し方が変わるので、
Tier の揺れ次第で上下する。**まだ実装していない。**

分割すると redundancy の問いは増え、核の問いは（Unit が小さくなるので）1 つ

#### 確認したこと

要求 JSON は `cargo run -p semantic-reading --example dump-request` で akapen 本体と
同じ `atomize` 経路から作り、**変更前のスクリプトを退避して同じ要求を食わせた**
（`atomize` は一切変えていないので、Atom の range は前後で同一。表示状態の
突き合わせはこの range で行った）。5 文書 × 変更前後を、`README.md` だけ 2 回、
残り 4 文書は 3〜4 回ずつ、合計 38 ラン。比率は `decorate-report`、Atom ごとの
状態は `atom-states`（どちらも `policy::decorate` そのものを通す）。核の経路の
内訳は各応答の `units[].jev.core_by` から数えた。run キャップの上限と R3 の
天井比は、**Jev を呼び直さずに**この 38 ラン分の応答から数えたものである
（run は各応答の `jev.boundaries` の `rule:new_list_item` でつないだ）。

**測っている最中に TypeSafe 側が 2 度落ちた** — HTTP 503 `no healthy upstream` と
HTTP 529 `system_overloaded`。どちらも最小の curl で切り分けてサービス側の問題と
確認しており、**この変更とは無関係**である。指数バックオフの再試行で埋め直した。

### run キャップ — リスト 1 本につき核は 1 つ（2026-09-21 の実測）

**結論: 5 文書のうち `CLAUDE.md` 1 つだけが合格条件 1 を満たさない。** 残り
4 文書は床と幅が重なる。ほかの条件（沈み方の維持 / 1 本のリストから MARKED が
2 つ以上出ない / 既存ゲート / R2 が動かない）はすべて満たしている。

#### 何を変えたか

**Tier（沈む側）は項目ごとのまま。核（光る側）だけをリスト単位に畳む。**
2 つの要望が衝突していたのはメカニズムが別だからで、そこを切り離した。

**run** = 規則 4 由来の境界（`rule:new_list_item`）でつながった Unit の並び
＝ 1 本のリスト（[`unit_runs`]）。run の中で MARKED になりうる Unit が 2 つ以上
あるとき、核の question を Unit ごとではなく **run ごとに 1 つ**にする
（[`plan_run_cores`]）。選択肢はその run の MARKED になりうる Unit に属する
散文 Atom だけで、`core_candidates` の絞りはそのまま当たる。

選に漏れた Unit には `core_atoms` に**空の配列**を入れる。プロトコルは
「無い」と「空」を区別しており、**空は「核を持たない」＝ MARKED にならない**
という意味になる（`crates/semantic-reading/src/protocol.rs`「`core_atoms` は
3 値」）。ここを省くと、選に漏れた Unit が丸ごと光って元より悪くなる。

予算を超える run は `handled` に入れず、**その run だけ現行の Unit ごとの核へ
落とす**。「核が無ければ Unit 全体が MARKED」を run に当てると、そのリストの
全項目が光って最悪になる。

#### 条件 1: MARKED 比率 — **`CLAUDE.md` だけ落ちた**

**ラン数を揃えてから判定すること。** 最初は床を 4 ラン・run キャップを 6〜7 ラン
で測って「3 文書で超過」と読んだが、**ラン数が違えば観測される幅も違う**ので、
少ないほうの最大値と多いほうの最大値を比べると超過が出やすい側へ偏る。床を
run キャップと同じラン数まで足して測り直した。

分母は Atom のバイト長の合計、Budget 100 %。

| 文書 | 変更前＝床 | **run キャップ** | 幅は重なるか |
| --- | --- | --- | --- |
| `demo.md` (4 ラン) | 12.8〜13.4 % | **12.8〜13.4 %** | **完全一致** |
| `design/…` (6 ラン) | 22.9〜26.0 % | **23.0〜26.9 %** | 重なる（最大は +0.9 pt） |
| この `README.md` (4 ラン) | 1.2〜2.9 % | **1.5〜2.6 %** | **床の中に収まる** |
| 業務議事録 (6 ラン) | 9.6〜10.4 % | **10.0〜11.4 %** | 重なる（最大は +1.0 pt） |
| 業務 `CLAUDE.md` (7 ラン) | 3.3〜3.7 % | **4.1〜4.5 %** | **重ならない** |

**落ちたのは `CLAUDE.md` だけである。** 床の最大 3.7 % と run キャップの最小
4.1 % のあいだに隙間があり、7 ランずつ測って一度も重ならない。

残り 4 文書は幅が重なる。とくに:

- **`design` は 4 ラン時点の「+0.9 pt 超過」が消えた。** 床を 6 ランにすると
  22.9〜26.0 % が 22.9〜26.0 % のままで、run キャップの 26.9 % はこの文書の
  揺れ（3.1 pt 幅）の中にある。既に分かっていたとおり、**この文書の残差は
  リスト由来ではない**（`list_item` の MARKED は前後とも 1 のまま）
- **`README.md` の床は 2 ランでは狭すぎた。** 3・4 ラン目が 1.2 % を出して
  床が 1.2〜2.9 % に広がり、run キャップの 1.5〜2.6 % は**丸ごとその中**に入る
- **議事録は重なるが、最大どうしでは +1.0 pt。** 重なりで判定すれば合格だが、
  上振れの側が床より高いことは表のとおり

#### 残差の出どころ

MARKED になる Atom を種別で割ると、どこが増えたかが分かる。

| 文書 | | `list_item` | それ以外 |
| --- | --- | --- | --- |
| 業務 `CLAUDE.md` | 前 | 3〜4 | 8 |
| | run キャップ | **6** | 7〜9 |
| 業務議事録 | 前 | 2〜4 | 7〜8 |
| | run キャップ | **4** | 7〜10 |
| `design/…` | 前 | 1 | 34〜37 |
| | run キャップ | **1** | 34〜39 |

`CLAUDE.md` と議事録の残差は **`list_item` 側**にある。丸ごと 1 Unit なら
ESSENTIAL にならなかったリストが、割ると中に ESSENTIAL な項目を持つ。
**run キャップは 1 本につき 1 つまでしか許さないので、これは原理的に消せない。**
次に縮めるなら、見るのは核ではなく**リスト全体の Tier の付け方**になる。

`design` の残差は `list_item` ではない側にあり、散文の Tier の揺れである
（run キャップとは無関係）。

#### 増えた MARKED の中身

残差が消せない以上、残る判断は「増えた分が読む価値のある箇所か」で、これは
数字では決まらない。MARKED になった `list_item` の本文を、変更前と run キャップ
で突き合わせる（`[前 n/N ・ runcap n/N]` は、そのランのうち何回 MARKED になったか）。

**業務 `CLAUDE.md`**（7 ラン / 7 ラン）

業務 `CLAUDE.md`（7 ラン / 7 ラン）は、**変更前から光っていた 4 件が全ランで
光り続け、2 件が増えた**。増えた 2 件は

- **その文書の設計上の制約を述べた一文**（なぜその実装が原理的に取れないかの理由）
- **別文書へのポインタ**（`docs/….md: **…**（…）` の形の、参照リストの 1 項目）

である。前者は読む価値のある箇所で、後者は既知の「箇条書きのラベルが MARKED に
なる」（`docs/gotchas.md`）がこの run で表に出たもの。**本文は引用しない**
（`docs/gotchas.md`「業務文書の本文はこのリポジトリに書かない」）。

**業務議事録**（6 ラン / 6 ラン）

業務議事録（6 ラン / 6 ラン）は、**増えた 2 件・減った 2 件**である。

| | 中身の種類 | ラン |
| --- | --- | --- |
| 増えた | 仕様の制約を述べた決定事項 | 前 0/6 → runcap 6/6 |
| 増えた | その制約に対する運用手順 | 前 0/6 → runcap 2/6 |
| 減った | 画面の不足を述べた項目 | 前 2/6 → runcap 0/6 |
| 減った | 操作の副作用を述べた項目 | 前 6/6 → runcap 4/6 |

**run キャップは MARKED を足しているのではなく、並べ替えている。** 上の表を
縦に読むと、増えた 2 件だけでなく**減った 2 件**もある。同じリストの中で光る先が
1 つに絞られるので、**前に光っていた項目が譲る**ことがある。差し引きの比率だけを
見ていると、この入れ替わりは見えない。

**採否はここで決まる。** 増えた 4 件が読む価値のある箇所なら採用、ノイズなら
却下という取引で、**測った側では決めていない**。

なお増えた 2 件のうち**別文書へのポインタ**が光るのは、既知の
**「箇条書きのラベルが MARKED になる」**（`docs/gotchas.md`）がこの run で
表に出たものである。**run キャップの欠陥ではない**し、ここで直そうとしないこと
— 同じ形の手がかりは 4 つ潰して地雷に残してある。

**変更前と run キャップはラン数を揃えてある**（demo と README は 4、design と

突き合わせること（`docs/gotchas.md`）。

### `--dry-run`

API を叩かず、送る 3 ラウンドのリクエスト（`state` / `model` / `questions`）を
そのまま出す。後のラウンドは前のラウンドの答えに依存するので仮定を置く
（`assumptions` にも載る）。

- ラウンド 2: **Jev に聞く境界はすべて `new_unit` だった**と仮定する
- ラウンド 3: **すべての Unit が `essential` かつ非 REDUNDANT だった**と仮定
  する。本番ではここが絞られるので、実際に送る question はこれより少ない

akapen から使うものではなく、要求の JSON を自分で流し込んで見る。

```sh
python3 examples/semantic/jev-annotate.py --dry-run < request.json | jq '.rounds[].questions | length'
```

鍵は要らない。テストもこの経路でリクエストの形を検証している。

### テスト

`cargo test` には載せられないので Python の `unittest` で、スクリプトの隣に置く
（`plugins/akp/scripts/test_akp.py` と同じ置き方）。**API は叩かない。**

```sh
python3 -m unittest discover -s examples/semantic -p 'test_*.py'
```

見ているのは構造ルール / フィクスチャからの Unit 組み立て / `--dry-run` が送る
リクエストの形 / `TYPESAFE_API_KEY` 未設定時のエラー経路 / HTTP エラーの文面の
5 つで、判定の質は上の実測の表で見る。

### 自分で測る

上の表を測り直すには、akapen を起動せずにアダプタだけを走らせる。要求 JSON は
**akapen 本体と同じ `atomize` 経路**から作る（別実装で真似すると、測っている
ものが本番とずれる）。

```sh
cargo run -p semantic-reading --example dump-request -- doc.md > request.json
TYPESAFE_API_KEY=... python3 examples/semantic/jev-annotate.py --timeout 120 \
  < request.json > answer.json
jq '.jev.rounds' answer.json
cargo run -p semantic-reading --example decorate-report -- doc.md answer.json
```

`jev.rounds` に 1 ラウンドずつの `questions` / `elapsed_s` / `usage` が載る。
`--timeout` を既定の 20 秒より伸ばしておくのは、測っている最中に切られないため。

`decorate-report` は `policy::decorate` そのものを通して、Budget ごとの
MARKED / NORMAL / DIM の比率を出す（**分母は Atom のバイト長の合計**であって
source 全体ではない — Markdown の記号や空行は Atom に入らない）。
