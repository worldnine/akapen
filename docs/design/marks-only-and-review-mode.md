### 定型プロンプトは綺麗なセットが欲しい

問いが外に出ると、**定型の質がそのまま道具の質**になる。ここに今日までの知見が
生きる:

- **損失の言い方で聞く**（「落とすと〜を取り違える」）。核の選択の問いと同じ軸
  （`core-selection.md`。核の選択は 2026-09-24 にやめた）。「重要か」と直接聞かない
- **例示でクラスの形を伝える**。System One は例から読む。ESSENTIAL の criteria が
  「決まったもの」の名詞ばかりだったせいで未決の節が全部 DETAIL になった
  （`essential-unsettled.md`）。例示は決定・未決・制約・宿題の**両側**を置く
- **方向が要る問いには方向を入れる**（「これより前で」）。対称に聞くと結論が
  重複に見える（`redundancy.md`）
- **1 つの問いに 1 つの軸**。理解と行動を 1 問に混ぜない。赤入れは別の定型にする
- **「無い」を Choice で聞かない**。Jev は「該当なし」を選ばない
  （`gotchas/semantic-reading.md`）。有無は Noul で

**最初のセットを測った**（2026-09-22。5 文書 × 8 問 × 2 ラン。
`examples/semantic/measurements/marks-presets.md`）。**文面そのものを下に置く** —
文面が道具の一部なので、ここに無いと次に触る人が同じものを測れない。

**2026-09-24 から、定型と自由入力は英語の短い文面である（形 E1）。** 正本は
`assets/marks-questions.json`、測ったのは
[`question-form.md`](../../examples/semantic/measurements/question-form.md) の追記
（正解ラベルで下の旧い形と並び、費用は約半分）。instructions をオブジェクトにして、
その文を別の欄に置く:

```json
{"question": "`passage` states something that has been decided.", "passage": "〈その文〉"}
```

| 定型 | 文面（`text`） |
| --- | --- |
| essential（要点） | `` Missing `passage` would make a reader misunderstand the document's main point, conclusion, constraints, or open issues. `` |
| settled（決まったこと） | `` `passage` states something that has been decided. `` |
| unsettled（決まっていないこと） | `` `passage` states something that is still undecided. `` |
| decide（判断が要る） | `` `passage` asks the reader to make a decision, confirm something, or choose. `` |
| numbers（数字と日付） | `` `passage` contains a deadline, an amount of money, or a quantity. `` |
| 自由入力の型 | `` `passage` addresses or answers "{q}". `` |

判定器は**文面に `` `passage` `` があるときだけ**この形で聞き、無ければ下の旧い形
（枠で本文を埋め込む）で聞く（`examples/semantic/jev-annotate.py` の
`marks_instructions`）。Review のルール（3 節）と、前の版のまま置いた読み手の
`marks-questions.json` は旧い形のまま聞かれる。criteria は付けない（付けても
ラベルの成績は変わらず、揺れと費用が増えた）。

**以下は 2026-09-24 までの文面**（段 1 で測った日本語）。

すべて **Noul**、Unit ごとに 1 問、`state` は文書全文。`{body}` に Unit の本文を
埋める — 2026-09-24 からは Unit が散文の Atom 1 つなのでその文そのもの（それまでは
Jev が束ねた Unit の Atom を空白で連結していた）。枠は全問共通:

```text
\n\n――― 対象 ―――\n{body}\n―――――――――
```

**定型 1「要点」** — `TIER_CRITERIA["essential"]` の**逐語**を含む。

```text
下の「対象」は、この文書の中で次に当てはまる箇所である。落とすと文書の要点、
結論、制約、未決の論点や宿題などを取り違える可能性が高い。
```

**定型 2「判断が要る」**

```text
下の「対象」は、読み手に判断・確認・選択を求めている箇所である。ここを落とすと、
読み手は自分が下すべき判断・確認・選択を見落とす。書き手が答えを待っている問い、
並べられた選択肢、「これでよいか」「どちらにするか」という求め、書き手自身が
迷っていて読み手に委ねている書き方が当てはまる。既に決まったことを述べている
だけの箇所、実行する人が決まっている作業を挙げただけの箇所は当てはまらない。
```

**定型 3「決まったこと」**

```text
下の「対象」は、決定・合意・確定した事柄を述べている箇所である。ここを落とすと、
読み手は何が決まったのかを取り違える。決めた内容、合意した方針、確定した結論、
採用すると述べた案が当てはまる。まだ決まっていない事柄、検討中・保留中の事柄、
これから決める予定を述べただけの箇所は当てはまらない。
```

**定型 4「決まっていないこと」**

```text
下の「対象」は、まだ決まっていない事柄を述べている箇所である。ここを落とすと、
読み手は決まっていないものを決まったと取り違える。未決の論点、保留された事柄、
確認待ちの事柄、結論が出ないまま次へ持ち越された事柄が当てはまる。既に決定・
合意した事柄、確定した結論を述べただけの箇所は当てはまらない。
```

**定型 5「数字と日付」**

```text
下の「対象」は、期限・金額・数量のいずれかを含んでいる箇所である。ここを落とすと、
読み手はいつまでに・いくらで・どれだけ、を取り違える。日付や期日・締切、金額や
単価、件数・人数・回数・割合といった具体的な数量が当てはまる。数字を含まない箇所、
版番号や見出しの番号のように量も時点も表さない数字だけの箇所は当てはまらない。
```

**自由入力**は**そのまま埋めない**（「日程」は主張ではないので Noul が評価
できない）。`{q}` に入力を差し込む型に入れる:

```text
下の「対象」は、「{q}」について述べている箇所である。ここを落とすと、読み手は
「{q}」について知りたいことを取りこぼす。「{q}」という語が出てこなくても、述べて
いる内容が「{q}」のことであれば当てはまる。同じ話題に関連するだけで「{q}」その
ものを述べていない箇所は当てはまらない。
```

### UI — 問いを選び、1 行で聞き、線が引かれる

**2026-09-22 に実機で議事録を読んだ評価は「かなりいい。特に自由入力は
えぐい。ただ TUI 的には相当ダサい」だった。** 直したのは 3 つで、いま
動いているのはこの形である。

**言葉は全部英語。** `label` は `Essential` / `Settled` / `Unsettled` /
`Your call` / `Numbers`、自由入力が `Ask`。**Jev へ送る `text` は日本語の
まま 1 字も変えていない** — 判定品質は文面で決まるので、ここが動けば上の
実測は根拠でなくなる。label は id を大文字で始めたものにしてある —
**`decide` だけは例外で `Your call`**（2026-09-23。`Settled` の hint の
`decided`・`Unsettled` の hint の `undecided`・名前の `Decide` と、同じ語根が
3 か所でかぶっていた）。fixture 経路（`--semantic <file>`）は label を持たず
id をそのまま出すので、`decide` の fixture だけは両経路で字面が違う。
要求に載るのは `id` と `text` だけで、キャッシュの鍵も `text` の sha なので、
表示の語を変えても判定もキャッシュも動かない
（`marks_questions::tests::relabelling_leaves_the_asked_ids_and_texts_untouched`）。

**読み出しはフッタの右端にある**（2026-09-22。1 日のうちにフッタ →
タイトル行の右 → **フッタの右下**と 2 度動いた。下の「なぜ戻したか」）:

```text
 BASELINE  examples/semantic/showcase.md

  VIEW  L1/170 · j/k scroll · v select · c comment · f focus · ? help   Essential · 15% ▐13▌
                                                                        │           │    └ 光っている Unit の数（座布団つき）
                                                                        │           └ つまみ（上から何 %）
                                                                        └ いま聞いている問い
```

タイトル行は**path とファイル位置だけ**に戻っている。**なぜ戻したか**:
ファイル名が長いと、読み出しが丸ごと引き下がって「あるはずの値が消える」
形になっていた。path は文書の身元なので譲れない — 譲れるのはフッタ左の
キー案内の方で、こちらは項目を落としても残りが読める。

**本数だけがマーカーと同じ琥珀の座布団に乗る**（黒字、前後 1 桁の余白
込み）。問いの名前と `15%` は薄いまま（`1/3 files` や `y copy` と同じ
薄さ）。**0 本は座布団を敷かない** — 光っているものが無いのに琥珀の四角が
出ると「何かある」と言ってしまう。幅は同じ形のままなので、つまみが 0 を
跨いでも行は揺れない。

**変化の瞬間だけ 300 ms 明るくなる** — 問いを変えた・つまみを回した・
答えが届いた、の 3 つで、どれも読み出しの字が変わる瞬間である
（`--no-fx` で止まる）。光るのは座布団の上だけで、色はマーカーの fade と
同じ。toast は出さない。

**幅が足りないときの縮む順**（`src/chrome.rs` の `footer_layout`）:

1. 左のキー案内を右から落とす。**`? help` と位置 `L12/80` は最後まで残る**
2. 読み出しは `15%` → 問いの名前 の順に落ち、**座布団の本数が最後まで
   残る**（いちばん小さくて意味がある値。% は問いを覚えていれば足りるし、
   名前は popup でも `?` でも確かめられる）
3. それでも足りなければ読み出しごと引き下がる

解析中は本数がまだ無いので、問いの名前から落として `analyzing…` を残す
（「なぜ」より「待っている」のほうが要る）。**タイムマシン中は出ない** —
過去の世代ではフッタを timeline bar が覆っている（マーカーは引かれたまま）。

自由入力のときだけ `Ask: 費用の話` になる。そこに入るのは読み手が
打った文字そのもの（たいてい日本語）で、ラベルではない —`Ask` の引数と
して読ませる枠に入れて、英語の並びに生で混ざらないようにしている
（鉤括弧で括っていたが、UI の言葉は英語なので 2026-09-22 に外した）。

| キー | 何をするか |
| --- | --- |
| `m` | 問いの選択（popup）を開く |
| `M` | 1 つ前の定型へ戻る（popup を開かない速い道） |
| `/` | 自由入力の 1 行プロンプト |
| `-` `+` / `<` `>` | つまみ ±1 / ±10 |
| `f` | **フォーカス** — マーカーの無いところを沈める |
| `]m` / `[m` | 次・前のマーク行へ飛ぶ |

### `Esc` — 一番手前の層から 1 枚ずつはがす（2026-09-23）

`Esc` には先客が何人もいる。**順番は 1 本の表**（`src/esc.rs` の `ORDER`）で、
view・source・Review の据え付けの一覧の 3 か所の `Esc` がみなそこを通る。
**次の `Esc` で何が起きるかは、タイトル行の右上のバッジ 1 か所が言う**
（2026-09-23 の改訂。下の「右上のバッジ」）。バッジも同じ表を読むので、
言ったことと実際に消えるものはずれない:

| 順 | 層 | 右上のバッジ | フラッシュ |
| ---: | --- | --- | --- |
| 1 | 終了の確認（`q`、未送信のコメントあり） | `esc cancel quit`（`--esc-quit` なら `esc close`） | `quit cancelled` |
| 2 | 選択（`v`・一覧の Enter） | `esc cancel selection` | `selection cancelled` |
| 3 | 削除のフォーカス（source の `n` / `N`） | `esc deselect deletion` | `deletion deselected` |
| 4 | Review の据え付けの一覧 | `esc close list` | `list closed` |
| 5 | フォーカス（`f`） | `esc focus off` | `focus off` |
| 6 | Review の下線とガターの印（候補） | `esc clear review` | `review cleared` |
| 7 | marks（問い・マーカー・読み出し） | `esc clear marks` | `marks cleared` |
| 8 | 終了（`--esc-quit` のときだけ） | `esc close` | — |
| — | はがす層が無く、`--esc-quit` でもない | （出さない） | — |

- **手前ほど軽い。** 上ほど一時的で、消しても何も失わない。Review と marks は
  消すと次に出すとき解析をやり直す（キャッシュに当たれば 0 円・一瞬だが、
  当たらなければお金と数秒）。**Review が marks より手前**なのは、Review が
  一時的な作業（直す候補を巡る）で、marks は読むための下敷きだからである
- **Review を消すのは画面の候補だけ。** dismiss の記録・accept で作った
  コメント・キャッシュは消さない。`R` を押せば同じ候補がまた出て、accept 済みは
  コメントから、捨てた候補は記録から、前と同じ印で戻る。起点（`review_armed`）も
  戻すので、次の reload が頼んでいない候補を描き直すことは無い
- **右上のバッジ**（2026-09-23 の改訂）。以前は `--esc-quit` のとき右上に
  固定の `esc close` が出て、フッタの右端に `Esc: clear marks` のような予告が
  出ていた。marks が出ているあいだ右上は「閉じる」と言うのに実際の `Esc` は
  marks を消すだけ — **右上が嘘をつき、しかも同じことを 2 か所で言っていた**。
  いまは右上の 1 か所だけで、語は**次の `Esc` で起きることそのもの**。フッタの
  予告はやめた（左の案内の作法は変えない）
  - 見た目は以前のバッジのまま（濃い灰色の地に黒字、右端、`▌ N` の右）。語は
    全段で小文字の `esc` ＋ 動作。動作の語はフラッシュと対（`clear marks` ↔
    `marks cleared`）で、語は `Layer::preview` の 1 か所にある。終了だけは
    `close` と言う — `--esc-quit` は akapen を popup として開く呼び手の設定で、
    呼び手から見た出来事は「閉じる」である
  - **削除の段は `focus` と言わない**（2026-09-23）。以前の
    `esc cancel deletion focus`（余白込み 27 桁）は一番長く、しかも `f` の
    フォーカス（`esc focus off`）と同じ語を使っていた。source の `n` / `N` が
    選んだ削除の塊を選び外す動作なので `esc deselect deletion`（23 桁）と言い、
    フラッシュも `deletion deselected` と対にした。ほかの段は 11〜22 桁で、
    どれも `focus` とは紛れないので変えていない。狭い幅では、身元の印も
    `▌ N` も無いとき端末 40 桁までこの段のバッジが残る（以前は 44 桁）
  - **`?` のヘルプに `esc` の行がある**（quit の行のすぐ上）:
    `top-right badge = what the next Esc does (or click)`。段ごとの語は
    並べない — それはバッジが言う。この 1 行のぶん、素のセッションのヘルプは
    24 行の端末で 1 行だけスクロールするようになった
  - **何も起きないときは出さない。** popup・composer・問いのプロンプトの間も
    出さない（そちらは `Esc` を自分で取る。出口はそれぞれの案内が言う）。
    以前の固定の `esc close` は popup の上でも出ていて、閉じるのは popup の
    方だった
  - **押せる。** 押す = `Esc` を 1 回（`TitleHit::Esc` → `esc::peel`）。
    塗った地のバッジはボタンに見えるし、タイトル行の他の要素（path・
    `1/3 files`・`▌ N`）も押せる。何が起きるかはバッジの字そのものなので、
    押して驚くことが無い
  - **狭いときは y/s の作法の延長で譲る**: y/s の説明が退く → path が 16 桁まで
    縮む → バッジが丸ごと退く。状態の印・`1/3 files`・`▌ N` は落とさない。
    短縮形（`esc` だけ）は作らない — 何が起きるかを言えない字は出さない方が
    よい。バッジが退いた幅で y/s が戻ることも無い（狭めるほど字が入れ替わって
    見えるので）
- バッジが出口を言うので、選択中の `Esc cancel` と一覧の `Esc close` は案内から
  外したまま（同じ状態を 2 か所で言わない）
- fixture 経路（`--semantic <file>`）では marks の段が立たない — そこは問いを
  選び直す道が無い。`0 Off` も出ない

### フォーカス（`f`）— 他を沈めて、マーカーだけ残す

「蛍光ラインがあまり目立たない」（読み手、2026-09-22 のドッグフーディング）
への答え。マーカーを濃くするのではなく、**周りを沈める**。

**沈むもの・沈まないものの線引き**（読み手の決定）:

| | どうなるか | なぜ |
| --- | --- | --- |
| 光った Unit の核 | 琥珀のまま | マーカーそのもの |
| **光った Unit の、核でない文** | **沈めない** | 核だけ浮くと段落が割れて読めない |
| **見出し** | **沈めない** | 沈んだ本文の中で現在地を読むのに要る |
| それ以外 | 沈む | フォーカスの本体 |

**2026-09-24 から 2 行目が働いていない（既知の劣化・後回し）。** Unit が散文の
Atom 1 つになったので、「光った Unit の核でない文」が無い — 光った文と見出しの
ほかは全部沈み、光った文の前後の文も沈む。表の「核だけ浮くと段落が割れて読めない」
がそのまま起きる。直すなら沈めない範囲を Unit ではなく**段落**で取る作り
（光った文を含む段落の Atom。見積りは
[`unit-granularity.md`](../../examples/semantic/measurements/unit-granularity.md)
6 節）で、marks の精度を優先して今回は入れていない。

**DIM 版の描画をそのまま使う**（`DecorationKind::Dim`）。判決
（`--semantic-mode budget`）ではなく読み手が自分で押した結果なので、
外れても誰も傷つかない — 沈める機構を 2 つ目作る理由が無い（1 節「判決」）。
投影は akapen 側（`src/semantic.rs` の `focus_decorations_for`）にあり、
**`marks.rs` にも `policy.rs` にも 1 行も入れていない**。

**`f` はトグルである。** 押すたびに沈む / 戻るが入れ替わり、端末で
振る舞いが変わるところは 1 つも無い（`src/focus.rs`）。

「押している間だけ沈む」形は 2026-09-22 に入れて、同じ日に捨てた。
離したことを知るには kitty keyboard protocol（`REPORT_EVENT_TYPES`）が
要るが、**その旗は端末の auto-repeat を `KeyEventKind::Repeat` に変える** —
`Press` だけを渡していた既存のキー経路が崩れて、矢印を押しっぱなしにしても
スクロールが 1 回で止まった。沈める / 戻すの 1 往復のために全部のキーの
押しっぱなしを賭けるのは釣り合わない（`docs/gotchas/terminal-keys.md`）。

`f` を押しっぱなしにすると auto-repeat が押下の連打として届くので、
**直前の押下から 120 ms 以内は捨てる**（沈む / 戻るの点滅よけ）。

沈んだまま**つまみも問いも動く** — 沈んだ状態で問いを変えられるのが
いちばんの使い道である。Esc の順は上の「`Esc` — 一番手前の層から 1 枚ずつ
はがす」の表。バッジ `FOCUS` はフッタのモードバッジのスロットで、
**`SELECT` が優先する**（transient な方を先に名乗る。Esc の順と同じ並び）。

### スクロールバーの目盛りと `]m`

右端スクロールバーの**溝**に、マークのある行を琥珀の点（`·`）で打つ
（VS Code の overview ruler）。**溝が無い（本文が収まっている）ときは
出さない。** ガターには何も足していない — 既に `>` / 黄 `▌` / 赤 `▌` /
`│` で混んでいる。

- **つまみが勝つ。** 点と重なる行では形は `▐` のままで、**色だけ琥珀に
  なる**。溝は 1 桁しかないので、点でつまみを切るとスクロール位置の
  ほうが読めなくなる
- **対応づけは溝の全長である**（つまみの座標ではない）。つまみは
  `pos * thumb_max / max_pos` で溝より短い範囲に写すので、同じ式で点を
  打つと「同じマークが、上へスクロールするとつまみの中、下へスクロール
  すると外」になる。目盛りは**文書の地図**である
- 色は `DecorationStyles::mark_tick()` — マークと同じ紙・同じ amber から
  作るので、`--light` でも `--theme` でも同じ系統で動く。**焼き込まない**

**`]m` / `[m`** で次・前のマーク行へ飛ぶ（`]c` と同じ chord の体系）。
環である。飛び先の台帳は溝の目盛りと**同じ 1 本**（`App::marks_lines`）—
2 か所で数えると「点の無いところへ飛ぶ」が起きる。marks モードでだけ
chord になり、それ以外では `]` の既定（ファイル切替）に落ちる。代償は
marks モードにあって、`]` のあとの `m` は popup を開かない（popup は
`]` を挟まずに `m` を打てば開く）。

**`m` は popup であって、巡るのではない。** 巡る形は 1 打ごとに Jev を
呼ぶので、4 本めを見るのに 4 回呼んでいた（議事録で 0.2 円 × 3 の無駄）。
popup は選んだ 1 本しか呼ばない。**開くだけでは 1 円もかからない。**

```text
┌────────────────────────────────────────────────────────────┐
│ mark for ──────────────────────────────────────────────────│
│  0 Off         clear the marks                             │  ← マークが出ているときだけ
│▸ 1 Essential   what you would misread if it were dropped   │
│  2 Settled     agreed, fixed, final                        │
│  3 Unsettled   open, pending, waiting to be confirmed      │
│  4 Your call   asks you to judge, confirm or choose        │
│  5 Numbers     deadlines, amounts, quantities              │
│  / Ask...      type your own question                      │
│ j/k:move  Enter:ask  Esc:close                             │
└────────────────────────────────────────────────────────────┘
```

**`questions` ではなく `mark for` と名乗る。** marks モードでは
「question」が**文書の中にある問い**とも読める（`Unsettled` と `Your call` が
まさにそれを光らせる）ので、こちらが持っている問いと同じ語になってしまう。
最下段の `/ Ask...` は、自由入力があること自体を見せるために行として
置いてある（以前は `?` ヘルプにしか書いていなかった）。

**問いの入力は 1 行プロンプト。** 以前はコメントの composer を借りて
いたが、吹き出しが `comment · 1` と名乗り、1 行の問いのために 3 行を
文書へ割り込ませていた。いまはメッセージ行（フッタのすぐ上）を使う:

```text
 ASK ▸ 費用の話█ ──────────────────────────────────────────────
  ASK   Enter ask · ←→ move · Esc cancel
```

キャレットと IME のアンカーは composer と同じ関数を通す（全角の扱いを
2 つ目実装しない）。**問いは 1 行**なので `^j`（改行）は断る。

**マーカーは引かれる。** 答えが届いた瞬間に全部が半分まで一斉に上がり
（250 ms）、そこへ**濃い琥珀の線が左→右に引かれ**（450 ms）、通った後ろが
**確定色へ乾く**（250 ms）。合計 950 ms — **判定の到着（数秒）と演出は
別物**で、待たせるためのものではない。
掴むセルは**琥珀の背景色そのもの**で選ぶので、「今回どこが光ったか」の
台帳が要らない。副作用としてカーソル行は演出に入らない（帯が優先して
琥珀ではない。`docs/gotchas/rendering.md`）。view と source の両方で走り、
`--no-fx` で止まる。**つまみには付けない** — 頻繁に打つ操作で邪魔になる
のと、「今回新しく光った箇所」を出すには装飾集合の差分が要って、つまみ
1 打の費用（いまは `marks::mark` 1 回）が上がるため。

**線だけ濃く、確定は読みやすい濃さのまま**である。2026-09-23 の読み手の
判断で、確定色は 0.27（ダークで琥珀 `rgb(90,69,33)`）のまま、引かれる線に
**`MARK_FLASH_BLEND`（0.65、ダークで `rgb(176,124,16)`）** を借りる形に
なった。前の版は線も確定色で、濃さを変える案（最初から濃い色で出る）も
実機で見たが、**「左から右にシュッと線が引かれる」動きは残す**方が良いと
選ばれた。

**天井（0.40）は確定色の話である。** 線は一瞬で通り過ぎて後ろも 250 ms で
乾くので、そこだけは超えてよい — 0.40 / 0.65 / 0.90 を実機に並べて 0.65 が
選ばれた（その上の字は 2.83:1。確定色では 7.03:1）。

## 1. マーカーのみの層 — DIM を廃止し、注目すべき箇所だけに線を引く

### 動機 — 費用と、判決の据わりの悪さ

**費用。** 1 文書 1 回の解析費用を実測した（`examples/semantic/measurements/redundancy.md`
のコストの節。単価は入力 $42 / 10⁹ tokens）:

| 文書 | サイズ | tokens（1 回） | 費用（1 回） |
| --- | ---: | ---: | ---: |
| `examples/semantic/demo.md` | 1.6 KB | 25〜27k | 0.1 ¢ |
| web 記事 | 18 KB | 170〜233k | 0.7〜1.0 ¢ |
| `docs/design/semantic-reading-layer.md` | 9.8 KB | 345〜372k | 1.5 ¢ |
| 業務議事録 | 22.7 KB | 707〜781k | 3.0〜3.3 ¢（≈ 5 円） |
| `docs/gotchas/semantic-reading.md` | 最大級 | 1.26〜1.33M | 5.3〜5.6 ¢（≈ 8 円） |

**費用の 9 割は問いの中身ではなく、文書全文（`state`）を何十回も送っている
ことにある。** 議事録は 8k tokens の文書に 740k tokens — 全文を 30 回近く送って
いる計算になる。ラウンドが 5 本以上（境界 → Tier → 冗長＋核 → 前提の波 ×N）、
各ラウンドが 32k 枠で数リクエストに割れるため。同じ 22 KB を汎用 LLM に 1 回
渡す入力費用（3〜4 円）と同じ桁になってしまっており、「速くて安い System One」
の売りが送り方で相殺されている。

**判決。** 読み手が READ 30 % で実文書を読んだときの感想は「DIM って概念が
そもそもそぐうのか。読み飛ばしていい、って気もしない」だった。
`reading-research.md` の言い方では、**MARKED は offer（外れても読み手は損を
しない）、DIM は verdict（外れると信頼を払う）**。そして同じ日に 5 回出た穴は
「読み手のモデルが無い」— 何が重要かは読み手の目的で逆転する（Pichert &
Anderson 1977）のに、Reading Tier は 1 軸で、読み手を知らない。**逆転するものに
判決を下すのが DIM の無理**である。

### 何が消えるか

DIM は「全 Unit に判決を下す」ので、全 Unit の Tier（一番重いラウンド）が要り、
判決を間違えないための部品が積み上がった。**2026-09-22 に作った部品の大半は、
DIM を正しくするためのものである。** マーカーだけなら:

| | いま（DIM あり） | マーカーのみ |
| --- | --- | --- |
| Jev のラウンド | 境界 / Tier / 冗長＋核 / 前提の波 ×N | 境界 / 「ここが要点か、どの一文か」 |
| 全文の送信回数 | 30 回前後 | 数回 |
| 費用（議事録 1 回） | ≈ 5 円 | ≈ 1 円の見立て（未測） |
| Reading Budget（`READ n%`） | 要る | **要らない** |
| Budget の下限（`policy::floor`） | 要る | 要らない |
| 二段台帳（`decorate` の一段目・二段目） | 要る | 要らない |
| `Presupposes` と閉包（context preservation） | 要る（沈んだ前提を戻す） | 要らない（何も沈まない） |
| 冗長の負け（`losers`） | 1 段沈める | 両方光るか片方だけ光るか、だけ |
| 見出しの復帰（`restore_section_heads`） | 要る | 要らない |

正直に書く: **`core-first-ledger` / `read-floor` / `redundancy-loser` / 
`heading-follows-content` / `context-preservation` は、この形では丸ごと不要に
なる。** それでも置いておくのは、Jev 的なものが安くなれば DIM は戻せるから。

### 何が消えないか

- ~~**箇条書きの run キャップ**（`lists-and-run-cap.md`）— しょうもない項目が
  個別に光らないための規則。マーカーの問題なので残る~~ → **外れた**
  （2026-09-22 の実機。0 節の「marks では run キャップを掛けない」）。
  あれは「問いを持たない判決」の側の規則で、問いが選ぶなら要らない
- **ESSENTIAL の criteria** と **核の一文を選ぶ問い**（`core-selection.md`）—
  これがマーカーの中身そのもの。criteria は 2026-09-22 に「未決の論点や宿題」
  まで広げてある（`essential-unsettled.md`）
- **密度と分布**（`mark-distribution.md`）— Scim の「diverse, evenly-distributed,
  important」。読み手が 100 % で言った「マーカーが少なくて物足りない」がそのまま
  主戦場になる。**いまの 4.5 % では少ない**
- **冗長の相手を Jev に選ばせる**（`redundancy.md`）— 対の両方を光らせるか
  片方だけかを決めるのに要る。相手が語彙の argmax だと、無関係な箇所が巻き添えに
  なる

### 新しく要るもの — 「量のつまみ」の置き換え

Reading Budget が消えると `<` `>` のつまみも消える。代わりに **マーカーの濃さ
（本数）のつまみ**が自然である: 少なめ（核だけ）↔ 多め（SUPPORTING の要点まで）。
判決ではなく**提案の量**を変えるので、外れても読み手は損をしない。

**強・弱の 2 段のマーカー**（琥珀の濃淡）で ESSENTIAL と SUPPORTING を分けるのも、
DIM 無しで階層を出す手。`decoration.rs` の `MARK_BG_BLEND` は既に連続量で、
天井 0.40 までの幅がある（`gotchas/rendering.md`「MARKED の天井の理由が変わった」）。

### 文献の支持

`reading-research.md` に既にある形で言えば:

- Lorch の signaling は**足す**合図であって、消す合図ではない
- Scim は光らせるだけで沈めない。冗長対の処理も無く、分布の後処理は「両方に
  光る可能性を残す」
- Pichert & Anderson 1977 — 何が重要かは読み手の視点で逆転する。逆転するものに
  判決を下すのが DIM の無理
- Duggan & Payne の satisficing は「読み手が自分で飛ばす」モデルで、道具が
  飛ばす先を決めるモデルではない

### 未測のこと

- マーカーのみのラウンド構成で費用が本当に 1/4〜1/5 になるか（見立てであって
  測っていない）
- 密度のつまみの上限で、run キャップと分布規則がどこまで持つか
- DIM が無いとき、長い文書で読み手が「どこを飛ばすか」を自分で決められるか
  （読み手の体験の測定）

## 2. 赤入れモード — 読み手の判断を求めている箇所を光らせる

### 動機

AI が Markdown を書くとき、**人に判断を仰ぐために下書きをする**場面がある。
議事録を一旦書いて「これでよいですか」と渡す、文書の中に「要確認」の項目を
残す、選択肢を並べて「どちらにしますか」と聞く。読み手（人）の仕事は全文を
理解することではなく、**判断が求められている箇所を見つけて、赤を入れる**こと
である。

いまの Reading Tier はこの場面に半分だけ合っている。2026-09-22 に ESSENTIAL の
例示を「未決の論点や宿題」まで広げた結果、業務議事録の「要確認」節は DETAIL
一色を脱した（`essential-unsettled.md`）。しかし ESSENTIAL は「落とすと取り違える」
という**理解の軸**であって、「読み手の判断が要る」という**行動の軸**ではない。
決定事項（決まったこと）と要確認（決めてほしいこと）は、理解の軸では同じ
ESSENTIAL に並ぶ。

### 形 — criteria を入れ替えるだけで、機構は同じ

`essential-unsettled.md` で「理解の軸と行動の軸を 2 軸にする」案は却下した
（ジャンル分けが原理のふりをする。汎用性は問いを減らすことで守る）。赤入れ
モードはその却下と矛盾しない — **軸を増やすのではなく、モードで criteria を
入れ替える**。

- 問いは 1 つ: 「この部分は、読み手に**判断・確認・選択**を求めているか」
  （Noul、Unit ごと）。System One の範囲に収まる形
- 光らせるのはその Unit の核の一文（run キャップも同じ）
- Tier も DIM も要らない。**1 節の「マーカーのみ」の形と同じ機構**で、費用も同じ桁
- 何も求めていない文書（完成した記事）では 0 本になる。それが正しい

### 何が難しいか

- **「判断を求めている」と「未決である」は違う。** 議事録の「要確認」は
  書き手が読み手に投げたもの、「宿題」は誰かがやること、「継続議題」は次回に
  持ち越すもの。赤入れが要るのは 1 つ目だけで、System One がこの 3 つを分ける
  かは測っていない
- **書き手の合図との重なり。** AI の下書きは「**要確認**」「TODO」「?」のような
  明示の合図を持つことが多い。合図があるなら Jev は要らない（構文で拾える）。
  合図の無い箇所 — 「〜と思われるが、〜の可能性もある」のような**書き手の
  迷い**を拾えるかが、このモードが Jev を使う理由になる。それも測っていない
- **モードの切り替えを誰が決めるか。** 起動フラグか、文書の種類の推定か。
  推定は「読み手のモデル」の問題を「書き手のモデル」に置き換えるだけで、
  同じ穴に落ちる。**フラグで始める**のが安全

### 未測のこと

- 判断を求める文と、未決を述べる文を、Noul 1 つで分けられるか（議事録の
  3 節で測れる）
- 書き手の明示の合図が無い箇所を拾えるか（下書きの実物が要る）
- 赤入れモードで光った箇所に、読み手が実際にコメント（akapen の本業）を
  付けるか — 光った箇所とコメントの位置の一致率が、このモードの唯一の
  成果指標になる

## 3. 意味の検索 — 自然語で聞いて、意味の合う箇所を光らせる

### 動機

文字列検索（`/`）は語が一致した箇所しか見つけない。「費用の話はどこ」「決まって
いないことは何」「この人が反対した箇所」のように、**読み手が知りたいことを
そのまま入力して、意味の合う箇所が光る**検索。

これは Jev の primitive にいちばん素直に乗る使い方である（`jev.md`）。
2026-09-22 に読み手自身が Jev をこう言っている:「かなりの確度で意味的な検索を
素早くできるのが売りなんじゃないの」。

### 形

- `state` = 文書全文、question = Unit ごとの Noul「この部分は『<入力>』に
  ついて述べている／答えている」。**1 ラウンド、1〜数リクエスト**
- 光らせるのは合った Unit の核（run キャップも同じ）。合う度合いで濃淡を付ける
  なら Score
- 境界（Unit の切り方）は 1 節・2 節と共有できる。**境界だけを先に 1 回取って
  おけば、検索 1 回の費用は `state` 1 回分の桁**（議事録で 0.1〜0.2 円）
- 入力は自然語。語の一致は要らないので、「決まっていないこと」で「要確認」節が
  光ってよい

### 1・2 節との関係

1 節（マーカーのみ）は「書き手が重要と言っていること」を光らせ、2 節（赤入れ）
は「読み手の判断が要ること」を光らせ、3 節は「**読み手がいま知りたいこと**」を
光らせる。**3 節だけが読み手のモデルを持つ** — 読み手が入力するから。
「読み手のモデルが無い」という穴は、モデルを推定するのではなく、**読み手に
聞く**ことで埋まる。Pichert & Anderson の視点効果を、視点を読み手に選ばせる形で
使うことになる。

### 何が難しいか

- **粒度。** Unit（段落）で聞くか Atom（文）で聞くか。文で聞くと question が
  増えるが `state` の送信回数は変わらないので、費用はあまり変わらない。表示の
  粒度は核の一文で揃えるのが自然
- **「述べている」と「答えている」は違う。** 「費用はいくら」に、費用の説明の
  段落（述べている）と金額の一文（答えている）のどちらを光らせるか。Noul の
  文面で分かれるはずだが、測っていない
- **話題と性質も違う。ここは測った**（2026-09-22、第 2 版の 6 節）。いまの型
  「『{q}』について述べている」は**話題**用で、**性質**には効かない —
  「AI slop」と打つと、slop **である**箇所ではなく slop という**語が書いてある**
  箇所が上位に出て、足切りを越えるのが 4 本しかない。**性質の型**
  「下の「対象」は、{q} に当てはまる箇所である。」に替えると AUC 0.87 → 0.99、
  つまみ 20 % の再現率 0.00 → 0.92 になった。**どちらの型を使うかを入力から
  自動で決めるのは難しい**（「費用の話」は話題、「AI slop」は性質、「曖昧な文」は
  どちらでも通る）ので、**型を 2 つ見せて読み手に選ばせる**のがいちばん安い。
  **実装していない**
- **速さ。** 検索は打つたびに走る。1 ラウンドでも往復 1〜3 秒。文書が 80 KB
  天井の近くだと `state` の分割でリクエストが増える。**境界の事前取得と
  キャッシュ**（費用の節の 1・2）がこの機能の前提になる
- **文字列検索との共存。** `/` は残す。意味の検索は別のキー。両方の結果が
  同じ画面に出るとき、色を分けるか

### 未測のこと

- Noul 1 つで「述べている」箇所がどれだけ拾えるか（議事録で「決まっていない
  こと」「費用」「日程」の 3 問を 4 ラン測れば分かる）
- 話題の型と性質の型を**両方聞いて高い方を採る**案の費用（問いが 2 倍になる）
- 文書 1 本の検索 1 回の実費と往復時間（marks の 1 問は 0.06〜0.12 円・1 秒前後。
  第 2 版の 9 節）

## 4. 直すためのマーク — slop の除去（段階 2 実装済み、2026-09-23）

**段階 2 まで実装した。** 候補を拾って一覧に出し、accept でコメントにし（段階 1）、
送る文面の先頭に書き換えの契約を載せる（段階 2）。流れの 2 → 6 を 1 周して測った
（下の「段階 1 で作ったもの」「段階 2 で作ったもの」）。LLM に送らず一覧の `e` で
人が直す道も足した（「直接編集」）。**判定の出どころは既定で linter に移した**
（末尾の「判定の出どころとしての linter」。Jev のルールは既定では 1 本も有効でない）。
節の残りは 2026-09-22 に読み手と設計したときのままである。

### ラインマーカーとの違い — 光ったあとの行き先

1〜3 節は読み手のためで、光った箇所は「そこを読め」。この節は書き手（校閲者）の
ためで、光った箇所は「そこを直せ」。機構は同じ（問い → Unit ごとに Noul → 琥珀）で、
**光ったあとの行き先**だけが違う。読むなら目で終わる。直すなら LLM へ渡す。

読み手の言葉: 「出来上がった文章の構成を大きく変えるのは難しいから、せめて AI slop
的な文章は阻止しよう」「検知器ではないから、そんなに厳しく取る必要はない」
「ユーザーが介在する形で。LLM だけに任せるとめっちゃ時間がかかる領域。ただ、
判定は素早く。書き換えは LLM に（Jev は文章を書かない）」。

### 配管はほぼ既にある — コメントが「人の承認」

akapen の本業は赤入れで、**コメントを外部エージェントへ送る口（`--send-cmd`）**、
**ファイルが書き換わったら差分を `! N` で見せる口**、**履歴を戻す口**が既にある。
この流れはそれを繋ぎ直すだけである。

```text
1. 問い「Slop」を選ぶ         → Jev が Unit ごとに判定（数秒、1 問 0.3 円前後）
2. 琥珀が乗る                  → 読み手が ]m で巡り、1 キーで「直す」/「これはいい」
3. 「直す」に入れた Unit に akapen が自動でコメントを付ける
     （"slop: filler" のような短い理由。コメント ＝ 人が承認した印）
4. 一括送信（既存の send）     → LLM に「この箇所だけ、意味を変えず短く」
5. LLM がファイルを書き換える → akapen が変更を検知し、差分が ! N で光る
6. 人が差分を 1 つずつ見て、採る / 戻す（履歴の機構）
```

人が介在するのは **2（選別）と 6（採否）**の 2 か所で、どちらも既存のキーの範囲。
LLM は 4 だけ。LLM に任せると時間がかかるのは**どこを直すか探すのに全文を読む**
からで、そこを Jev が数秒で肩代わりする。

### 汎用ルール — 「AI っぽさ」ではなく「バイトあたりの損失」

「AI が書いたか」は**出自**の問いで、専用の検出器でも当たらず、光った箇所が告発
として読まれる（判決の形）。聞くのは読み手が一目で感じる**症状**で、ジャンルを
またいで成り立つのは「**落としても読み手が何も失わない**」という言い方 — 要点の
裏返し — だけである。

| 定型 | 問い（損失の言い方） | 汎用か | 初回の実測（2026-09-22、`showcase-slop.md`） |
| --- | --- | --- | --- |
| **Filler** | ここを落としても、読み手が失う事実・数字・判断・理由は無い | ◎ どの文書でも成り立つ | **混ぜた 12 文に AUC 0.98。つまみ 20 %（15 本）で再現率 0.92・精度 0.73。** 叩き台のまま効く |
| **Echo** | ここは前で述べたことの言い直しで、新しい情報を加えない | ◎ **既にある**（冗長の対 Noul、`redundancy.md`）。slop の主症状 | **届いたのは 2 文のうち 1 本**（対 Noul 0.96）。もう 1 本は Tier が `context` で**聞かれもしない**。しかも ≥0.5 の 11 本中 10 本は`決定事項`の一覧＝**消してはいけない側** |
| **Preamble** | 「以下に説明する」「まとめると」のような、内容の前置き・締めで中身が無い | ○ | **`Filler` と相関 0.98。** 単独のラベルでは AUC 0.88 と 3 本で最低。**同じところが光る**（畳むかどうかは測っていない） |
| **Hedge** | 断定を避け、責任の所在をぼかす（〜と思われる、適切に対応する） | △ **ジャンル依存**（契約・医療では正しい書き方）。既定に入れず、選べる定型に | 自分のラベルには AUC 1.00（相関 0.67 で他の 2 本とは別のものを見ている）。12 文全体では **AUC 0.82** と低く、**既定に入れない判断と整合する** |

**数字は初回・1 文書・2 ランで、人の書いた文書での対照が無い。** 生値は
[`../../examples/semantic/measurements/marks-presets.md`](../../examples/semantic/measurements/marks-presets.md)
第 2 版の 3〜5 節。**文面は 1 字も変えずに測った** — 直すならここからである。

4 本目を既定から外すのが汎用の担保。**Jev の汎用性は、問いが文書の側ではなく
読み手の損失の側を向いているときに出る** — Tier が議事録で未決を落としたのは、
例示が文書の側（決まったものの名詞）に寄っていたからだった（`essential-unsettled.md`）。

文面の叩き台（5 則: 損失の言い方 / 例示は両側 / 方向 / 1 問 1 軸 / 無いは Noul）:

```text
Filler
  下の「対象」は、具体的なことを何も述べていない箇所である。ここを落としても、
  読み手が失う事実・数字・判断・理由は無い。一般論、決まり文句、それらしい
  前置きや締め、直前の言い換えが当てはまる。固有の事実・数字・判断・その理由を
  含む箇所は当てはまらない。

Preamble
  下の「対象」は、これから述べること・述べたことの案内だけで、内容そのものを
  持たない箇所である。ここを落としても読み手は内容を 1 つも失わない。
  「以下に説明する」「まとめると」「重要なのは」のような導入・締めが当てはまる。
  結論や判断を実際に述べている箇所は、締めの形でも当てはまらない。

Hedge（選べる定型。既定には入れない）
  下の「対象」は、断定を避けて責任の所在をぼかしている箇所である。ここを
  落とすと、読み手は誰が何を引き受けるのかを取り違える。「〜と思われる」
  「〜の可能性がある」「適切に対応する」「検討する」のように、主体・期限・
  内容のどれかが欠けた言い方が当てはまる。不確かさそのものを事実として
  述べている箇所（「未定」「確認待ち」）は当てはまらない。
```

Echo は新しい定型ではなく、冗長の対 Noul（相手は Jev の Choice）がそのまま
「直す側」の入力になる。

### 「検知器ではない」をどう活かすか

人が選別するので、**取り逃がしより拾いすぎの側に倒せる**。足切りを低めにし、
外れは 1 キーで捨てる。誤検知の代償は 1 キー、検知漏れの代償は slop が残ること。
前者を選ぶ。**offer であって verdict でない**理由はここにあり、フォーカスと同じ側に
いる。

### 一番怖いところ — LLM が「具体化」で捏造する

「空疎だから具体的に」と頼むと、LLM は数字や固有名詞を**作る**。書き換えの契約は:

- **削る・縮める・統合する**だけ。事実を足さない
- 具体性が足りないなら書き換えず、**`[要: 具体例]` のような印を残して人に返す**
- 意味の変化は差分で人が見る（流れの 6）

「書き換えは LLM、事実は人」。これがあれば 4 を外部エージェントに投げても
安全側に落ちる。

### フィードバックループ — 何が学ぶのか

Jev は学ばない。学ぶのは**定型の文面**（データ）と**送る指示**である。
「これはいい」と捨てられた Unit を集めれば、Filler の例示の「当てはまらない側」が
実データで増える — 段 1 でやった「例示はクラスの両側」の右側を、使うほど埋めて
いく形。捨てた Unit を LLM に「ここは触るな」として渡すのは、その場で効く。

### 測った（2026-09-22）／まだ測っていない

**測った 2 つ。**

- **`showcase.md` の素の `Filler` は 61 Unit 中 10 本**（足切り 0.20 超、16 %）。
  10 本を全部目で見ると、**3 本は fixture 自身の前書き**（議事録の本文ではない）、
  3 本は見出しと名札、1 本はリストの導入で、**議事録の散文で本当に空疎なのは
  1〜2 本**だった。AI が書いた文書でも、密に書かれていれば光らない —
  **測っているのは出自ではなく空疎さ**、の半分が出たことになる。
  残る半分（人の書いた文書でも空疎なら光るか）は未測
- **Echo は slop の文書で 11〜13 件出た**（人の文書の 0〜1 件に対して）。
  **ただし増えたぶんは slop ではない** — 10 本は`決定事項`と`要確認`の一覧が
  本文を言い直したもので、議事録では**言い直しが仕事**である。混ぜた Echo
  2 文のうち 1 本は Tier が `context` に落ちて聞かれもしなかった。
  **Echo をそのまま「直す側」の入力にはできない**（Tier の間引きを外す、
  一覧として意図された言い直しを除く、の 2 つが要る）。費用も marks の 10 倍で、
  1 ラン 1.2 円

**まだ測っていない。**

- 流れの 2 → 6 を 1 周して、人の手数（キー数）と LLM の往復時間
  — **測った（2026-09-23、段階 2）。** `showcase-slop.md` で **32 キー**
  （選別 19・差分の確認 13）、`s` から書き換わるまで **34 秒**。
  判定はキャッシュに当たったので、Jev の往復は入っていない。下の「段階 2 の実測」
- 書き換え後に事実が増えていないこと（LLM の契約が守られたか）を、差分の中の
  数字・固有名詞の出入りで数える — **測った（同）。** 11 か所がすべて削除で、
  **足された数字・語は 0**、`[要: …]` 印も 0。範囲の外で変わったのは空行 9 行だけ。
  **ただし 11 本とも「削れば済む」指示だった**ので、印を残す道（`rewrite`）は
  まだ通っていない
  — **通した（2026-09-23、2 周目）。** `Hedge` 3 本のうち 1 本に
  `[要: …]` 印が付き、2 本は削られた。**縮めて応えた箇所は 0**。足された
  数字・語は 0 のまま。下の「2 周目の実測」
- 本物の Jev の往復と、書き換え後の再解析 — **測った（同）。** `R` から
  候補まで **1.29 秒**（2 ルール並列、各 1 秒前後）、書き換え後の `r` から
  再解析が出揃うまで **1.15 秒**。往復の重さは LLM 側（39 秒）にある
- `Hedge` が「未定」「確認待ち」のような事実としての不確かさを誤って直すか
  — **測った（同）。** 「未定」2 行・「見込み」4 行は候補に出ず、1 字も
  変わらなかった。ただし fixture の 1 文書でしかない
- 人の書いた文書（web 記事）での `Filler`。**出自ではなく空疎さを測っている**
  ことの残り半分
- `Filler` / `Preamble` を 1 本に畳んだときに何を失うか（相関 0.98）

### 段階 1 で作ったもの（2026-09-23）

**marks の定型の環には入れていない。** 共有するのは判定器の一段の問い（Noul）・
Unit・境界・sha キャッシュだけで、UI・読み出し・色は別に持つ。判定器
`jev-annotate.py` は 1 行も変えていない — ルールの `text` を問いとして渡すだけ
である。`R` を押しても marks の問い・注釈・世代・装飾は 1 バイトも動かない
（テストがそれを押さえている）。

| どこ | 何 |
| --- | --- |
| `assets/review-rules.json` | ルール。`$XDG_CONFIG_HOME/akapen/review-rules.json` で上書き。`text` は上の叩き台の**逐語**で、既定で有効なのは `Filler` 1 本（**2026-09-23 に 0 本へ**。末尾の「判定の出どころとしての linter」） |
| `src/review_rules.rs` | ルールの読み込み（`marks_questions.rs` と同じ作法、別のファイル） |
| `src/review.rs` | 候補（diagnostics の形）・捨てた記録・`--review-json` |

**上位 N % ではなく閾値。** 文書によって slop の量は違うので、割合で切ると
きれいな文書からも 20 % 拾ってしまう。候補は score 降順ではなく**文書順**に
並ぶ（直すのは上から読みながらの作業である）。`has_core()` は見ない —
marks の投影は核を持たない Unit を落とすが、あれは「どこを読むか」を絞る

**UI。** `R` で一覧。**窓ではなく本文の下に据え付ける**（末尾の「一覧を本文の

`$EDITOR` で直す（末尾の「直接編集」）、`Esc` 閉じる。
accept / dismiss で行は消えず印が変わる（`✓` / `–`）。本文は Pending の Unit に
**細い下線**（紙から青緑へ寄せた色。琥珀と同じ式・違う色相なので `--light` でも
`--theme` を変えても距離が保たれる）、ガターに `!`（いまはどちらもパレットの色と

**accept = コメント。** 本文は `review: filler (0.87)`（形は
`crate::review::comment_text` の 1 か所。段階 2 の送り先がこれを読む）。以降は

**dismiss は記録する。** `~/.local/share/akapen/review/dismissed.jsonl` に
`{source_sha, range, rule, at}` を追記し、同じ文書を開いても一覧に薄く `–` で
出す（本文には出さない。2026-09-23 までは一覧からも消していた — 末尾の
「取り消しと状態」）。
**本文は書かない**（0600 / 0700。`~/.cache/akapen/semantic/` と同じ機密度）。
文書が 1 バイトでも変われば sha が変わって記録は当たらなくなる — 直したあとの
文書で同じ箇所がまた候補になるのは正しい（直っていないかもしれない）。

### 直接編集 — 一覧から `e` で人が直す（2026-09-23）

候補を LLM に送らず、**人が `$EDITOR` で直す**道。直すのが 1 文なら、送って
39 秒待つより自分で消す方が早い。LLM が書き換えた場合（`s` のあと、開いたまま
自動 / 手動で reload）も、下の 1・3 は同じ扱いになる。

```text
1. R で一覧 → j/k で候補へ → e
2. その候補の先頭行で $EDITOR が開く（本文の e と同じ作法・同じ行ジャンプの一覧）
3. 直して閉じる → 見届けた reload
     - 範囲が変わっていない dismiss を、新しい位置・新しい sha へ写す
     - 範囲の中が変わった accept 済みの review コメントを外す（フラッシュで 1 行）
     - 変わっていない review コメントは、新しい行へ付け直して NOW に残す
4. 一覧は開いたまま `review · analyzing…` → 答えが揃うと、カーソルは直した箇所へ
     （直した候補が残っていればそれ自身、消えていればその位置の次。文書順）
```

**「見届けた」とは、akapen が開いたまま起きた reload である**
（`crate::reload::reload_source` — `e` の戻り、`r`、`--reply` でない自動
reload）。閉じている間に変わったファイルは、起動時に前の版が手元に無いので
何もしない。`--reply` は文書を丸ごと差し替え、コメントも落とすので写さない。

**差分は既存の `similar` で、行 → 文字の 2 段**（`src/edit_map.rs`）。行で
比べて変わった塊の中だけを文字で比べ直すので、同じ行の別の文を直しても
隣の文の dismiss は写る。**範囲の中に 1 バイトでも挿入・削除・置換があれば
写さない** — 直された文は判定し直す。

| 対象 | 範囲の中が変わっていない | 変わった |
| --- | --- | --- |
| dismiss（`dismissed.jsonl`） | 新しい位置で新しい sha の記録を追記（形式は同じ、本文なし）。**捨てて戻した記録は写さない** | 写さない（判定し直す） |
| accept 済みの review コメント | 新しい行へ付け直し、NOW のコメントのまま残す。その候補は届いても `✓` のまま（`a` で 2 本目を作らせない） | **外す**（`s` で直した箇所への指示を送らない） |
| 人の赤入れ | **触らない**（今までどおり古い版へ留め置く） | 同左 |

review コメントの範囲は、accept した候補がまだ手元にあればその Unit のバイト
範囲、無ければコメントの行そのものである。見分けは
`crate::review::parse_comment_text` の形で、人が書いた「review: …」は形に
合わなければ赤入れとして扱う。

**限界。** 判定器の切り方（Unit の境界）が動くと、写した範囲が新しい Unit と
一致せず、捨てた候補が戻る。3 往復の実測では **0 / 18** だった。

| 数えたもの（3 往復、`Filler` 0.5、本物の Jev） | 値 |
| --- | ---: |
| dismiss の引き継ぎ | **18 / 18**（3・6・9 本） |
| 範囲が変わって写さなかった | 0 |
| 切り方が動いて一致しなかった | **0** |
| カーソルが直した位置の次の候補に着いた | **3 / 3** |
| 戻ってから候補が出揃うまで | **0.94〜0.98 秒** |

3 往復目にカーソルが着いたのは**旧の一覧に無かった候補**で、同じ Unit の
score が版ごとに 0.23 → 0.50 と上がって足切りを越えたものだった — 周りの
空疎な文を削るほど、残った文の `Filler` が上がる（1 ランの観察）。生値は
[`review-roundtrip.md`](../../examples/semantic/measurements/review-roundtrip.md)

### 判定の出どころとしての linter（2026-09-23）

**判定は linter に任せ、akapen はその後ろの流れを受け持つ。** 一覧・`x` で捨てる・
`a` でコメントにする・`s` で送る・一覧から `e` で直す・見届けた reload での引き継ぎ
— ここまでに作った流れはそのままで、候補の出どころに `--lint-cmd`（環境変数
`AKAPEN_LINT_CMD`）を足した。ルールは読み手が自分の linter の設定
（`~/.textlintrc` など）で決め、akapen はその存在を知らない。

**なぜ Jev を既定から外したか。** 読み手の指摘は「`Filler` などで拾える空疎さは、
実際に気になる箇所と合わない」だった。気になるのは**語の選び方の違和感とぼかし**で、
文単位の「落としても失うものが無いか」ではない。同じ fixture で数えると、軸が違う
ことがそのまま出る（生値は
[`review-roundtrip.md`](../../examples/semantic/measurements/review-roundtrip.md)
「linter を候補に」）:

| 出どころ | 候補 | 混ぜた slop 12 文に当たった | 12 文の外 | `R` → 出揃うまで |
| --- | ---: | ---: | ---: | ---: |
| `Filler`（Jev、段階 1） | 17 | 11 | 6 | 1.29 秒（2 周目、2 ルール） |
| textlint | 13 | 3 | 8 / 12（総評 1 本を除く） | 1.45〜1.99 秒 |
| natural-japanese | 6 | 3 | 2 / 6 | 0.33〜0.83 秒 |

linter は空疎な文をほとんど拾わず、72 行目の「かも」のような**2 字の範囲**で語を
指す。fixture のラベルは空疎さの正解なので、linter の良し悪しはこの表では測れない
— 判断の根拠は読み手の指摘であって、数字は「別の軸を見ている」ことの確認である。
Jev のルールは消していない。`review-rules.json` か `--review-rules` で
`enabled: true` にすれば走り、lint の候補と同じ一覧に文書順で並ぶ。

| どこ | 何 |
| --- | --- |
| `src/lint.rs` | コマンドを走らせ、Diagnostic の JSON を読み、UTF-16 の桁をバイトへ直す |
| `src/review.rs` | `Finding`（Jev のルール / lint）。lint のコメントの形 `lint: <source>/<code> — <message>` |
| `assets/review-contract-lint.md` | lint のコメントがあるときに送る文面の先頭へ足す段落（`$XDG_CONFIG_HOME/akapen/review-contract-lint.md` で上書き） |
| `examples/lint/` | textlint と natural-japanese の出力を Diagnostic に直すスクリプト（標準ライブラリだけ）。textlint 側は micro エディタ用の `--unix-oneline` も出す |

**受け付ける形は 1 つ: LSP の `Diagnostic`**（`{"diagnostics":[{range, message,
source, code, severity}]}`、`line` は 0 始まり、`character` は UTF-16 のコード単位）。
linter ごとの形を akapen に持ち込まない — 変換はスクリプトの側で、akapen が覚える
のはこの 1 つだけである。

- **走らせ方。** `sh -c '<cmd> "$@"'` で、作業ディレクトリは文書のあるディレクトリ、
  最後の引数は文書の絶対パス。stdin は空。見切りは `--semantic-cmd` と同じ（無音
  30 秒・天井 10 分）。linter はディスクを読むので、画面の本文と食い違えば走らせない

### 一覧を本文の下に据え付ける（2026-09-23）

読み手の指摘は 2 つだった。**一覧の窓が指摘箇所を覆って読めない**、そして
**一覧の行からは、その文の何が問題なのかが読めない**（linter の理由の文は長く、
複数行のものもある）。合意した形は「一覧を本文の下に据え付ける」:

```text
 BASELINE  showcase-slop.md                  esc close list   ← 次の Esc で起きること
 ┌──────────────────────────────────────────────┐
 │ …                                            │  ← 選んだ候補が中ほどに来るよう送る
 > …通知の出し方を変える方が効くかもしれない」   │
 └ review (1/13) ────────────────────────────────┘  ← 題は本文の枠の下辺に乗る
     L40 · ja-no-redundant-expression · …           ← 一覧
 ▸ ✓ L72 · ja-no-weak-phrase · 弱い表現: …           ← 選んだ行は本文のカーソル帯と同じ色
 ─ textlint/ja-no-weak-phrase · L72 ─────────────  ← 一覧で落とした <source>/ と範囲
   弱い表現: "かも" が使われています。                ← 理由の全文（折り返す）
 REVIEW L72/192 · j/k move · a accept · x dismiss · e edit · A accept all
```

| どこ | 何 |
| --- | --- |
| `src/review_dock.rs` | 配分（`dock_rows`）・割り付け（`split`）・送り（`follow`）・描画・一覧の行の当たり判定 |
| `src/app.rs` | `view_viewport_rows` / `source_viewport_rows` が据え付けのぶんを引く。`terminal_size`（テストで大きさを固定する口） |
| `src/chrome.rs` | `message_row`（toast は据え付けの題の行へ）・フッタのキーの案内・`REVIEW` のバッジ |
| `src/main.rs` | マウス（一覧の上は一覧、本文の上は本文へ）・Resize で送り直す |

**配分の式は 1 か所**（`review_dock::dock_rows`）。据え付けは端末の高さの
**4 割**までで、本文の領域に最低 6 行（枠込み）を残す。一覧は候補の数だけ
（**10 行で頭打ち**、それより多ければ一覧の中でスクロール）、理由の欄は
いちばん長い理由の行数（**6 行で頭打ち**、溢れたら `…`）。**理由の欄の高さは
選んだ候補ではなく全候補で決める** — j/k のたびに本文の高さが変わると本文が
上下に揺れる。代わりに短い理由の候補では欄に空行が残る。描画・本文の高さ・
マウスがこの式を通るので、「カーソルが一覧の下に潜る」「クリックが 1 行ずれる」
はテストが押さえている（`src/review_dock_tests.rs`）。

幅 80、`showcase-slop.md` を textlint で開いた 13 候補（いちばん長い理由は 5〜6 行）:

| ---: | --- | ---: | ---: |
| 20 | 8 = 1 + 3 + 1 + 3 | 9 行 | 10 行 |
| 24 | 9 = 1 + 4 + 1 + 3 | 12 行 | 13 行 |
| 40 | 16 = 1 + 8 + 1 + 6 | 21 行 | 22 行 |
| 60 | 18 = 1 + 10 + 1 + 6 | 39 行 | 40 行 |

高さ 11 以下では理由の欄を落とし（題 + 一覧だけ）、9 以下では据え付けそのものを
出さない（キーは効くが一覧は見えない）。

**実測**（2026-09-23、実機を tmux で 80 桁に固定し、`R` → `j` を 10 回、各回で
カーソル帯の行が本文の領域にあるかを ANSI で数えた）:

**判断したこと。**

- **Jev のルールの理由は、定義（`text`）の最初の 1 文を出す。** `review-rules.json` に
  短い説明の欄は足していない。段階 2 が LLM 向けの言い換えを持たなかったのと同じ
  理由で、足せば Jev に聞いた文面と人に見せる文面が 2 か所になる。定義は
  「下の「対象」は、〜な箇所である。」で始まり、その 1 文が要点になっている
- **本文を押しても一覧は閉じない。** 外を押して閉じるのは被さる窓の作法で、
  据え付けでは本文は「外」ではない。本文のクリックはカーソルを動かすだけ、
  一覧の行のクリックはその候補を選んで本文を送る（2 度押しが `Enter`）
- **キーの案内はフッタへ。** 一覧を開いている間はキーが一覧に届くので、フッタの
  本文のキーの案内は打っても効かない。一覧のキーに差し替え、バッジも `REVIEW`
  （色は候補の下線と同じ青緑）にした。窓が無いぶん「どこにキーが届くか」を示す
  ものがバッジしか無い
- **`j/k` は前の選択を落とす。** `Enter` で作った選択は別の候補の行を指したまま
  残り、フッタが `SELECT` を名乗り続けるため
- **文書全体を範囲にする指摘**（textlint の総評）を選んでも本文は動かさない（いまの
  形。下の「指摘の描き方」）。以前は先頭の行を中ほどに置いていた — 真ん中に寄せると
  本文のカーソルの行が画面の外に出たため
- toast は据え付けの題の行に出る（view では本文の枠の下辺のまま）。フッタのすぐ
  上は理由の欄の最後の行で、そこに乗ると読んでいる理由が消える
- 据え付けは Review だけ。`l` / `?` / `m` / Ctrl+p / `t` は今の窓のまま

### 指摘の描き方 — 範囲の字だけ・重さの色・波線（2026-09-23）

読み手の指摘は 3 つだった。**下線が広すぎる**（72 行目の「かも」に引用の塊全体の線が
乗る）、**下線しか無い**（nvim の LSP のような波線と重さの色が欲しい）、**総評が一覧の
先頭に来て全行に線と `!` が出る**。

**広すぎた原因は総評だった。** `decorate_row` は exact の span を装飾の境目で既に
切っていて、1 字の指摘には 1 字だけ線を引いていた。塊に見えたのは、同じ行に
**文書全体を範囲にする指摘**（L1–192）の線が重なっていたためである。実機
（tmux、幅 80、textlint、`showcase-slop.md` のコピー）で L72 を選んだ画面の下線の字数:

| | view | source |
| --- | ---: | ---: |
| 修正前 | 37（行頭の余白込み） | 32（`> ` 込み） |
| 修正前、総評を `x` で捨てたあと | 1（「か」） | — |
| 修正後 | 1（「か」） | 1（「か」） |

| どこ | 何 |
| --- | --- |
| `src/decoration.rs` | `ReviewSeverity`・重さごとの色と白抜き（`color` / `badge`）・行ごとの問い（`review_severity_on_row`）・波線の印 `CURL_CARRIER`・上位集合の span での Review の例外 |
| `src/undercurl.rs` | `--undercurl` の判定（`resolve`）と描画の出口（`draw`） |
| `src/review.rs` | `Candidate::severity` / `is_whole_document`（閾値） |
| `src/app.rs` | 総評を一覧の末尾へ、下線とガターの印から外す。`review_lines` が重さを運ぶ |
| `src/review_dock.rs` | 一覧の行で「文書全体」と名乗る。選んでも本文を送らない |
| `src/review_render_tests.rs` | `TestBackend` に描いてセルで固定するテスト |

- **範囲の字だけ。** exact の span は今までどおり範囲の境目で切る。linter が 1 字しか
  返さなくても**語の終わりまで伸ばさない** — 日本語は語の境目が字面に無く、伸ばす
  には形態素の判断が要る。外れれば線が別の語を指し、linter の範囲という契約も崩れる。
  何を言われたかは一覧の理由の文が語る
- **上位集合の span（表のセル・タブのある行）だけは断片ごと。** marks の交差ルール
  （覆うときだけ）をそのまま当てると、セルの中の指摘が本文に何も出ず、ガターの印
  だけが立つ。字の位置は source の添字で切れないので、触れた断片（折返しの 1 行ぶんの
  セル）を丸ごと引く。**空白だけの断片（hanging pad）には引かない** — 段落をまたぐ
  指摘が行頭の余白から線を引いていた
- **重さの色はターミナルの 16 色パレット**（2026-09-23 に紙から寄せる式を
  やめた）。akapen の色の決まりは「本文 = コードのテーマ、枠まわりの合図 =
  ターミナルのパレット、本文に重ねる印 = 紙から作る」で、重さは合図の側である。
  コードのテーマ（tmTheme）には警告色の決まった枠が無く、端末のテーマを替えれば
  一緒に替わる。marks の琥珀は本文に重ねる印なので、紙から作るまま:

  | severity | 色 | 下線の色（SGR） | ガター |
  | --- | --- | --- | --- |
  | 1 error | `Color::Red` | `58;5;1` | 赤地に `E` |
  | 2 warning | `Color::Yellow` | `58;5;3` | 黄地に `W` |
  | 3 info / 4 hint・無し・Jev | `Color::Cyan` | `58;5;6` | 青緑地に `I` |

  明るい版（`Light*`）は使わない。ガターの他の印（コメントの黄 `▌`・削除の赤 `▌`・
  選択の青緑 `▌`）と同じ色で揃え、`Light*` は強調（カーソルの `>`・選んだ変更）に
  取ってある。明るいテーマで `LightYellow` の地に白い紙の字を抜くと読めない、
  という理由もある。以前 warning を黄にしなかった理由（明るい紙で 1 ピクセルの
  線が消える）は、端末のパレットの黄に委ねた — 線が薄くても、重さは白抜きの字で
  読める
- **ガターの印は白抜きの 1 マス**（`ReviewSeverity::badge`）: 重さの色の地に、
  紙の色で `E` / `W` / `I` を抜く（`REVERSED` ではなく字の色を明示 — 反転だと字が
  端末の地色になり、テーマの紙と食い違う）。herdr は下線の色を落とすが、字と地の
  色は通すので herdr の中でも重さが読める。色だけで言わず字でも言う。`!` は
  使わない — `!` は「まだ見ていない変更」（左上の `! N`）だけの印である。
  行に複数の候補があればいちばん重いもの。優先順は今までどおり（カーソルの `>`・
  選択の `▌`・コメントの `▌` が上、削除・変更の `▌` が下）で、地の色は帯で
  塗り替えない
- **範囲の行だけに立てる。** view で複数のソース行が 1 段落に畳まれると、ソース
  行の旗（`review_lines`）では段落の全部の描画行に印が立っていた（2 行の引用で
  「か」の無い 1 行目にも）。いまは描画行ごとに、下線を引くのと同じ規則で問い
  直す（`decoration::review_severity_on_row`）。群のどの行にも下線が乗らない
  候補は、見失わないよう群の先頭の行に立てる
- **一覧の行頭にも同じ白抜き**を出す。残っている候補の `✓` / `–` の桁（今まで
  空白だった 1 マス）に入れるので桁は増えない。見た候補は `✓` / `–` のまま
- **波線。** ratatui 0.30 のセルには下線の形を書く場所が無い（`Modifier` に undercurl が
  無い）。装飾の層は下線に**印**（`CURL_CARRIER` = akapen が使っていない
  `RAPID_BLINK`）を立てるだけにし、描画の出口 `NoBlinkBackend::draw` →
  `undercurl::draw`（`CrosstermBackend::draw` の写し）が、印の立った下線を
  `CSI 4:3 m` か普通の下線に読み替える。印は点滅として決して出さない。見出しの
  下線（印が無い）は波線にならない
- **対応の判定**: `--undercurl <auto|on|off>`（既定 auto）、無ければ `AKAPEN_UNDERCURL`。
  auto は `TERM` が dumb / linux → 1 本線、terminfo に `Smulx` → 波線、`TMUX` → 波線
  （tmux は `4:3` を解釈し、外側に `Smulx` が無ければ 1 本線に落として出す）、
  `TERM_PROGRAM` / `TERM` が Ghostty・kitty・WezTerm・iTerm2・VS Code・Alacritty・
  foot・Rio・Contour → 波線、それ以外（Terminal.app を含む）→ 1 本線
- **herdr** は `4:3` をそのまま外側へ出す（herdr 0.9.1、外側の `TERM` を
  `tmux-256color` / `xterm-ghostty` にしても同じ）ので専用の枝は持たない — auto は
  herdr を立てた端末の `TERM_PROGRAM` で決まる。ただし **herdr は下線の色（`CSI 58`）を
  外側へ出さない**。herdr の中では重さの色は下線に乗らず、ガターの白抜きにだけ出る

- **文書全体を範囲にする指摘**は、範囲が文書の行の **9 割以上**（かつ 3 行以上）を
  覆うもの。9 割は、front matter や末尾の空行を外して返す linter の総評も拾うため

  `文書全体 · ai-tech-writing-guideline · …`、出どころの行は `文書全体 L1–192`。
  本文には下線もガターの印も出さず、選んでも本文を送らない（指す場所が無い — 一覧の

### 取り消しと状態 — `a` / `x` は切り替え（2026-09-23）

読み手の指摘は「捨てた・accept したが取り消せない」だった。`a` / `x` は
Pending にしか効かず、捨てた候補は次に開くと一覧から消えて戻す道が無く、
accept で作ったコメントを本文の `d` や `l` の一覧の `d` で消しても候補は `✓` の
ままだった（状態が候補とコメントの 2 か所にあり、片方だけが変わっていた）。

**状態は候補が持たない。** 毎回ほかの持ち物から導く
（`App::candidate_states`）。どの経路でコメントが消えても（本文の `d`・`l` の
一覧の `d`・`s`・見届けた reload の片付け）、候補は何もしなくても戻る:

| 状態 | 何から決まるか | 一覧 | 本文 |
| --- | --- | --- | --- |
| Dismissed | 捨てた記録（`dismissed.jsonl`、同じ鍵の最後の行）に載っている | 薄く `–` | 何も出さない |
| Accepted | この候補に結ばれた review / lint コメントが今ある（下の「結び目」） | 薄く `✓` | コメントの印 |
| Sent | そのコメントを `s` で送った（この版のうち。`sent.jsonl` で開き直しても残る） | 薄く `✓`（新しい印は作らない） | 何も出さない |
| Pending | どれでもない | 白抜きの重さ | 下線とガターの白抜き |

**遷移表**（正本は `src/review_undo_tests.rs` の
`every_state_goes_straight_to_the_state_of_the_key_pressed`）。どの状態からも
**押したキーの状態へ直接行く**:

| 状態 \ キー | `a` | `x` |
| --- | --- | --- |
| Pending | Accepted（コメントを作る） | Dismissed（記録を追記） |
| Accepted | **Pending**（コメントを消す。`review comment removed`） | Dismissed（コメントを消してから記録） |
| Dismissed | Accepted（取り消しを追記してからコメント） | **Pending**（取り消しを追記） |
| Sent | 何もしない（`already sent — decided again when the file changes`） | 同左 |

- `A` は今までどおり Pending だけを accept する。**直後にもう一度 `A`** を押すと、
  その `A` で accept したものだけをまとめて Pending に戻す（`a` / `x` の「同じキーを
  もう一度押せば戻る」と揃えてある。`App::undo_accept_all`）。`A` より前に `a` で
  作ったコメントと人の赤入れは触らない。**間にほかの操作を挟んだら戻せない** —
  一覧のどのキー（`j` / `k` の移動も含む）・一覧の外のキー・マウス・reload・一覧の
  `e` で閉じる。移動を含めたのは、「直後」を目で確かめられる形にするためである
  （移動して別の行を見たあとの `A` が「戻す」だと、押す前にフッタを読み直す必要が
  出る）。戻せるあいだだけフッタの `A` が `A undo all` になる。1 本も作らなかった
  `A` は戻す相手を持たない
- **送った候補には `a` も `x` も効かない。** `a` は同じ指示を二度送らせないため、
  `x` は捨てても指示はもう相手に届いているため。送った印は `sent.jsonl` にも
  追記し（下の「記録の形式」）、**同じ文書（sha が同じ）なら閉じて開き直しても
  `✓` のまま**である。**いまのファイルの NOW が書き換わった reload で忘れる**
  （`App::forget_review_sent` — 見届けた reload でも写さない。ディスクの記録は
  sha で鍵をかけてあるので、書き換わった版には効かない）。送った相手が直して
  いれば候補は出ず、直していなければ Pending で出る。`Esc` → `R` では同じ版なので
  `✓` のまま戻る
- `Esc` の「review を消す」は画面の候補を下げるだけで、状態には触らない（今のまま）

**案内の出し分け**（`chrome::review_toggle_hints`）。フッタの `a` / `x` は、
カーソル下の行でそのキーを押すと何が起きるかを言う:

| カーソル下 | フッタ |
| --- | --- |
| Pending（と一覧が空のとき） | `a accept · x dismiss` |
| Accepted | `a undo · x dismiss` |
| Dismissed | `a accept · x restore` |
| Sent | `a/x sent` |

`A` の案内は `A accept all`、`A` の直後だけ `A undo all`（`App::accept_all_hint`）。

**件数**（`Review · 3/9`、一覧の題の `review (3/9)`）。分母は一覧の行の全部 —
捨てた候補も一覧に残るので数える。分子は Pending でない行（`✓` と `–`）で、
**`9/9` は「残っている候補が無い」**。以前の分子は accept 済みだけで、捨てた候補は
開き直すと分母からも消えていた。

**記録の形式**（`dismissed.jsonl`、追記のみのまま）:

```json
{"source_sha":"…","range":[120,168],"rule":"filler","at":1790000000}
{"source_sha":"…","range":[120,168],"rule":"filler","at":1790000042,"undo":true}
```

- 捨てる行は今までと 1 バイトも同じ形（`undo` を書かない）。古い行はそのまま
  「捨てた」と読む
- **同じ鍵（sha, ルール, 範囲）は最後の行が勝つ。** 捨てて戻して捨てれば捨てている
- 本文は書かない。0600 / 0700 も今のまま
- 見届けた reload の引き継ぎ（`DismissedStore::carry`）は、旧版で**いま**捨てている
  ものだけを写す。戻した記録は写さない。加えて、旧版で戻した鍵が新版で捨てられて
  いれば（元に戻した版に昔の記録が残っている）、新版にも取り消しの行を足す —
  足さないと、戻した候補が元の版へ戻ったとたんに消える
- 送った記録は隣の `sent.jsonl` に、`{"source_sha":"…","range":[120,168],
  "rule":"filler","at":1790000000}` の形で追記する（本文は書かない。0600 / 0700。
  取り消しの行は無い — 送った指示は取り消せない）。書くのは `s` で送った
  コメントのうち、**いまのファイルの NOW に結び目で結ばれたもの**だけ（ほかの
  ファイル・過去の版は鍵にする文書の sha が手元に無い。結び目の無いコメントは
  範囲が無い）。読むのは捨てた記録と同じ時（`App::load_dismissed`）
- `--review-dismissed-clear` がファイルごと消す（`--semantic-cache-clear` と同じ
  作り。消す前に捨てていた本数を `cleared N dismissed review candidates (<path>)` と
  出す。戻したものは数えない）。**送った記録も一緒に消す**（件数は `cleared N sent
  review candidates (<path>)` と別の行で出す）。どちらも同じ置き場にある「この文書に
  ついて読み手が決めたこと」なので、フラグを分けるより 1 本で消せる方を取った。
  送った記録は文書が書き換われば効かなくなるので、消したくなるのは「同じ版を
  もう一度送り直したい」ときだけである
- `--review-json` は今までどおり捨てた候補を出さない（直す候補の列だからである）

**限界（済、2026-09-23）。** 以前のコメントは候補のバイト範囲を持たず、行とルール
だけで候補と結んでいた。同じ行に同じルールの候補が 2 本あれば、1 本を accept すると
2 本とも `✓` になり、`a` で戻すと 2 本とも戻った。送る文面も行番号と行の全文しか
持たず、受け手はどちらの指摘か分からなかった。下の「結び目」で解いた。

### コメントと候補の結び目（2026-09-23）

AI の書いた日本語の Markdown は 1 段落を 1 行で書くことが多く、段落の中に「かも」が
2 回あるだけで同じ行・同じルールの候補が 2 本になる。**コメントに候補との結び目を
持たせる**（`Comment::anchor: Option<ReviewAnchor>`）:

```rust
pub struct ReviewAnchor {
    pub rule: String,              // 候補のルール（lint なら <source>/<code>）
    pub range: Range<usize>,       // 候補のバイト範囲（文書の頭から。Candidate::range と同じ）
    pub column: usize,             // 範囲の始まりが行の何「文字」目か（1 始まり）
    pub excerpt: String,           // 同じ行の前後を少し含む抜粋。範囲は【】で括る
}
```

- **埋めるのは `a` / `A` で accept したときだけ。** 人が書いたコメントは `None`
- `column` と `excerpt` は `range` と本文から作る写しで（`Comment::lines` と同じ
  扱い）、作り直すのは accept したときと見届けた reload で付け直したときだけ
  （`ReviewAnchor::new`）
- **照合の鍵**（`app::CandidateSpot`）: 結び目のあるコメントは (ルール, バイト範囲)、
  結び目の無いコメントは今までどおり (ルール, 行)。候補の側は両方の鍵を持つので、
  どちらの形のコメントとも照合できる。ルールはコメントの本文から読む — 人が本文を
  書き換えて review の形でなくなったら、結び目が残っていても候補とは結ばない
- 送った印（`App::review_sent` と `sent.jsonl`）も同じ鍵で持つ。2 本のうち送った
  方だけが Sent になる
- **見届けた reload**（`App::settle_review_comments`）: 結び目の範囲を `edit_map` で
  写し、桁と抜粋を新しい版で作り直す。範囲の中が 1 バイトでも変わったコメントを
  外す規則はそのまま — 同じ行の 1 本目の「かも」を直せば、1 本目のコメントだけが
  外れて 2 本目は残る

**送る文面。** 結び目のあるコメントは、本文（`review: …` / `lint: …`）の後ろに
1 行足す:

```text
/path/to/doc.md:3
3: これは効くかもしれないし、効かないかもしれない。
lint: textlint/ja-no-weak-phrase — 弱い表現
箇所: 3 行目の 18 文字目から「…かもしれないし、効かない【かも】しれない。」
```

- 桁は**文字**（Unicode のスカラー値）で数え、文面にも「文字目」と書く — バイトや
  UTF-16 と取り違えられないように。行番号は位置の見出しと同じ 1 始まり
- 抜粋は**範囲の行の中だけ**から前後 12 文字まで（段落の境目を跨いで見出しを拾わ
  ない）。切ったところに `…`。範囲が 24 文字より長ければ頭と尻の 10 文字ずつを
  残して中を `…` で詰め、範囲が行を跨げば改行を空白 1 つに畳む
- 足す行を本文の**後ろ**に置いたのは、契約（`assets/review-contract.md`）が
  「`review:` で始まる指摘」と本文の頭で見分けているのと、`scripts/akapen2hunk`
  などの受け手が抜粋の行数を位置の見出し（`start-end`）から数えているためである。
  見出しにも抜粋にも手を入れていない
- `--reply` の形は行番号を持たない（指す先のファイルが無い）ので `箇所: 「…」` と
  抜粋だけを書く。まとめて送るときは本文と同じく字下げの中に入る
- **結び目の無いコメント（人の赤入れ・古い経路）の文面は 1 バイトも変えない**
  （`review_anchor_tests::a_comment_without_an_anchor_is_sent_byte_for_byte_as_before`
  と、`export.rs` の既存のテスト）

テストは `src/review_anchor_tests.rs`（同じ行・同じルールの 2 本を別々に accept /
取り消し・捨てる、見届けた reload で結び目が写る、送る文面の位置と抜粋、結び目の
無いコメントの文面）。
