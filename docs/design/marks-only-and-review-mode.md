## 0. 3 つは 1 つだった — 問いを当てて、答えている箇所を光らせる

下の 1〜3 節は別々に書いたが、並べて読むと**同じ機構**である（読み手の指摘、
2026-09-22）。違いは問いの文面だけ。

**機構の説明は正典へ移した** —
[`semantic-reading-layer.md`](semantic-reading-layer.md) の「問いとスコア」
「つまみ」「マーカーの決め方」。ここに残すのは実測である。

- **Reading Tier は「要点」という定型プロンプト 1 つに縮む。** ESSENTIAL の
  criteria（2026-09-22 に「未決の論点や宿題」まで広げたもの）がそのまま文面になる
- **赤入れモード（2 節）は定型プロンプトがもう 1 つ増えるだけ**
- **意味の検索（3 節）は自由入力欄**
- **費用は問い 1 つで 0.03〜0.4 円**（実測。議事録の 1 問は 0.2 円で、当初の
  見立てのとおり）。境界はキャッシュ。**外れていたのは仕組みの方** — `state`
  1 回分ではなく **2.5〜8.0 回分**で、効くのは定型の文面 × Unit 数である
  （下の「定型プロンプトは綺麗なセットが欲しい」の末尾）
- 残ったもの: 境界、核の一文、琥珀の描画。消えたもの: Tier の 4 段、Budget、
  下限、二段台帳、冗長、前提、見出し復帰
- **run キャップは掛けない**（問いが選ぶ。量はつまみ）。1 本のリストの項目が
  全部光るのは「答えが全部光る」で正しい（実測は
  [`marks-mode.md`](../../examples/semantic/measurements/marks-mode.md) 6 節）

### 定型プロンプトは綺麗なセットが欲しい

問いが外に出ると、**定型の質がそのまま道具の質**になる。ここに今日までの知見が
生きる:

- **損失の言い方で聞く**（「落とすと〜を取り違える」）。核の選択の問いと同じ軸
  （`core-selection.md`）。「重要か」と直接聞かない
- **例示でクラスの形を伝える**。System One は例から読む。ESSENTIAL の criteria が
  「決まったもの」の名詞ばかりだったせいで未決の節が全部 DETAIL になった
  （`essential-unsettled.md`）。例示は決定・未決・制約・宿題の**両側**を置く
- **方向が要る問いには方向を入れる**（「これより前で」）。対称に聞くと結論が
  重複に見える（`redundancy.md`）
- **1 つの問いに 1 つの軸**。理解と行動を 1 問に混ぜない。赤入れは別の定型にする
- **「無い」を Choice で聞かない**。Jev は「該当なし」を選ばない
  （`gotchas/semantic-reading.md`）。有無は Noul で

**最初のセットを測った**（2026-09-22。5 文書 × 8 問 × 2 ラン。
`examples/semantic/measurements/marks-presets.md`）。**文面そのものを下に置く** —
文面が道具の一部なので、ここに無いと次に触る人が同じものを測れない。

すべて **Noul**、Unit ごとに 1 問、`state` は文書全文。`{body}` に Unit の本文
（Atom を空白で連結）を埋める。枠は全問共通:

```text
\n\n――― 対象 ―――\n{body}\n―――――――――
```

**定型 1「要点」** — `TIER_CRITERIA["essential"]` の**逐語**を含む。

```text
下の「対象」は、この文書の中で次に当てはまる箇所である。落とすと文書の要点、
結論、制約、未決の論点や宿題などを取り違える可能性が高い。
```

**定型 2「判断が要る」**

```text
下の「対象」は、読み手に判断・確認・選択を求めている箇所である。ここを落とすと、
読み手は自分が下すべき判断・確認・選択を見落とす。書き手が答えを待っている問い、
並べられた選択肢、「これでよいか」「どちらにするか」という求め、書き手自身が
迷っていて読み手に委ねている書き方が当てはまる。既に決まったことを述べている
だけの箇所、実行する人が決まっている作業を挙げただけの箇所は当てはまらない。
```

**定型 3「決まったこと」**

```text
下の「対象」は、決定・合意・確定した事柄を述べている箇所である。ここを落とすと、
読み手は何が決まったのかを取り違える。決めた内容、合意した方針、確定した結論、
採用すると述べた案が当てはまる。まだ決まっていない事柄、検討中・保留中の事柄、
これから決める予定を述べただけの箇所は当てはまらない。
```

**定型 4「決まっていないこと」**

```text
下の「対象」は、まだ決まっていない事柄を述べている箇所である。ここを落とすと、
読み手は決まっていないものを決まったと取り違える。未決の論点、保留された事柄、
確認待ちの事柄、結論が出ないまま次へ持ち越された事柄が当てはまる。既に決定・
合意した事柄、確定した結論を述べただけの箇所は当てはまらない。
```

**定型 5「数字と日付」**

```text
下の「対象」は、期限・金額・数量のいずれかを含んでいる箇所である。ここを落とすと、
読み手はいつまでに・いくらで・どれだけ、を取り違える。日付や期日・締切、金額や
単価、件数・人数・回数・割合といった具体的な数量が当てはまる。数字を含まない箇所、
版番号や見出しの番号のように量も時点も表さない数字だけの箇所は当てはまらない。
```

**自由入力**は**そのまま埋めない**（「日程」は主張ではないので Noul が評価
できない）。`{q}` に入力を差し込む型に入れる:

```text
下の「対象」は、「{q}」について述べている箇所である。ここを落とすと、読み手は
「{q}」について知りたいことを取りこぼす。「{q}」という語が出てこなくても、述べて
いる内容が「{q}」のことであれば当てはまる。同じ話題に関連するだけで「{q}」その
ものを述べていない箇所は当てはまらない。
```

正解つきの列は
[`../../examples/semantic/measurements/marks-presets.md`](../../examples/semantic/measurements/marks-presets.md)
の第 2 版。`showcase.md`（AI が書いた架空の議事録）に、書いた本人が付けた
正解ラベル `showcase.labels.json` に対する再現率・精度・AUC である。
つまみは `marks::take_count` と同じ数え方（足切り 0.20 込み）。
**精度の分母は「光った Unit のうちラベルが付いているもの」**である（ラベルは
最小限で網羅的ではないので、分母を光った全部にすると、ラベルが黙っている
正しい箇所を誤りに数えてしまう）。
**ラベルの誤り 3 件も同じ節にある**（どれも「Atom では正しいが Unit では
負にできない」形で、直していない）。

**「判断が要る」は 2026-09-22 に `Decide` として入れた**（読み手の判断）。
上の表のとおり**独立は測れていない**（`決まっていないこと` と相関 0.88、
正解つきの 2 文書目でも 0.90）。
それでも入れたのは、他の 4 本がどれも文書の側の性質を聞いているのに対し、
**読み手に向けられているか**を聞く軸がこれしか無いからである。文面は上の
定型 2 の逐語なので測り直しは要らない — 測れていないのは集合が分かれるか
だけで、同じ場所が光ったらそれは相関 0.88 がそのまま出ている。

**良い定型のセット ＋ 自由入力**、が形。定型はデータ（ユーザーが自分の問いを
保存できる）にする。**文面を変えたら測り直すこと** — 実測の正本は証拠側の
`tools/presets.py`。

**費用の見立ては直した。** 「1 問 = `state` 1 回分」は**外れている** — 実測で
2.5〜8.0 回分だった。定型の文面が Unit ごとに丸ごと繰り返されるので、
**費用 ≒ `state` + 定型の長さ × Unit 数**である。8 問 × 5 文書 × 2 ランの実費は
16.3 円（1 文書 1 問あたり 0.03〜0.4 円）、1 問は 0.6〜2.5 秒。

### UI — 問いを選び、1 行で聞き、線が引かれる

**2026-09-22 に実機で議事録を読んだ評価は「かなりいい。特に自由入力は
えぐい。ただ TUI 的には相当ダサい」だった。** 直したのは 3 つで、いま
動いているのはこの形である。

**言葉は全部英語。** `label` は `Essential` / `Settled` / `Unsettled` /
`Decide` / `Numbers`、自由入力が `Ask`。**Jev へ送る `text` は日本語の
まま 1 字も変えていない** — 判定品質は文面で決まるので、ここが動けば上の
実測は根拠でなくなる。label は id を大文字で始めたものにしてある。
fixture 経路（`--semantic <file>`）は label を持たず id をそのまま出すので、
両方の経路で同じ字面になる。

**読み出しはフッタの右端にある**（2026-09-22。1 日のうちにフッタ →
タイトル行の右 → **フッタの右下**と 2 度動いた。下の「なぜ戻したか」）:

```text
 BASELINE  examples/semantic/showcase.md

  VIEW  L1/170 · j/k scroll · v select · c comment · f focus · ? help   Essential · 20% ▐13▌
                                                                        │           │    └ 光っている Unit の数（座布団つき）
                                                                        │           └ つまみ（上から何 %）
                                                                        └ いま聞いている問い
```

タイトル行は**path とファイル位置だけ**に戻っている。**なぜ戻したか**:
ファイル名が長いと、読み出しが丸ごと引き下がって「あるはずの値が消える」
形になっていた。path は文書の身元なので譲れない — 譲れるのはフッタ左の
キー案内の方で、こちらは項目を落としても残りが読める。

**本数だけがマーカーと同じ琥珀の座布団に乗る**（黒字、前後 1 桁の余白
込み）。問いの名前と `20%` は薄いまま（`1/3 files` や `y copy` と同じ
薄さ）。**0 本は座布団を敷かない** — 光っているものが無いのに琥珀の四角が
出ると「何かある」と言ってしまう。幅は同じ形のままなので、つまみが 0 を
跨いでも行は揺れない。

**変化の瞬間だけ 300 ms 明るくなる** — 問いを変えた・つまみを回した・
答えが届いた、の 3 つで、どれも読み出しの字が変わる瞬間である
（`--no-fx` で止まる）。光るのは座布団の上だけで、色はマーカーの fade と
同じ。toast は出さない。

**幅が足りないときの縮む順**（`src/chrome.rs` の `footer_layout`）:

1. 左のキー案内を右から落とす。**`? help` と位置 `L12/80` は最後まで残る**
2. 読み出しは `20%` → 問いの名前 の順に落ち、**座布団の本数が最後まで
   残る**（いちばん小さくて意味がある値。% は問いを覚えていれば足りるし、
   名前は popup でも `?` でも確かめられる）
3. それでも足りなければ読み出しごと引き下がる

解析中は本数がまだ無いので、問いの名前から落として `analyzing…` を残す
（「なぜ」より「待っている」のほうが要る）。**タイムマシン中は出ない** —
過去の世代ではフッタを timeline bar が覆っている（マーカーは引かれたまま）。

自由入力のときだけ `Ask: 費用の話` になる。そこに入るのは読み手が
打った文字そのもの（たいてい日本語）で、ラベルではない —`Ask` の引数と
して読ませる枠に入れて、英語の並びに生で混ざらないようにしている
（鉤括弧で括っていたが、UI の言葉は英語なので 2026-09-22 に外した）。

**キー**（正本は `src/keys.rs`）:

| キー | 何をするか |
| --- | --- |
| `m` | 問いの選択（popup）を開く |
| `M` | 1 つ前の定型へ戻る（popup を開かない速い道） |
| `/` | 自由入力の 1 行プロンプト |
| `-` `+` / `<` `>` | つまみ ±1 / ±10 |
| `f` | **フォーカス** — マーカーの無いところを沈める |
| `]m` / `[m` | 次・前のマーク行へ飛ぶ |
| `Esc` | **問いを消す** — マーカーも読み出しも消える |

`Esc` には先客がいる（終了確認・選択解除・popup を閉じる・composer の
取り消し・フォーカスを解く）。問いを消すのはその全部より後で、消すと
次に問うときに解析をやり直す（＝お金がかかる）からである。fixture 経路
（`--semantic <file>`）では断る — そこは問いを選び直す道が無い。

### フォーカス（`f`）— 他を沈めて、マーカーだけ残す

「蛍光ラインがあまり目立たない」（読み手、2026-09-22 のドッグフーディング）
への答え。マーカーを濃くするのではなく、**周りを沈める**。

**沈むもの・沈まないものの線引き**（読み手の決定）:

| | どうなるか | なぜ |
| --- | --- | --- |
| 光った Unit の核 | 琥珀のまま | マーカーそのもの |
| **光った Unit の、核でない文** | **沈めない** | 核だけ浮くと段落が割れて読めない |
| **見出し** | **沈めない** | 沈んだ本文の中で現在地を読むのに要る |
| それ以外 | 沈む | フォーカスの本体 |

**DIM 版の描画をそのまま使う**（`DecorationKind::Dim`）。判決
（`--semantic-mode budget`）ではなく読み手が自分で押した結果なので、
外れても誰も傷つかない — 沈める機構を 2 つ目作る理由が無い（1 節「判決」）。
投影は akapen 側（`src/semantic.rs` の `focus_decorations_for`）にあり、
**`marks.rs` にも `policy.rs` にも 1 行も入れていない**。

**`f` はトグルである。** 押すたびに沈む / 戻るが入れ替わり、端末で
振る舞いが変わるところは 1 つも無い（`src/focus.rs`）。

「押している間だけ沈む」形は 2026-09-22 に入れて、同じ日に捨てた。
離したことを知るには kitty keyboard protocol（`REPORT_EVENT_TYPES`）が
要るが、**その旗は端末の auto-repeat を `KeyEventKind::Repeat` に変える** —
`Press` だけを渡していた既存のキー経路が崩れて、矢印を押しっぱなしにしても
スクロールが 1 回で止まった。沈める / 戻すの 1 往復のために全部のキーの
押しっぱなしを賭けるのは釣り合わない（`docs/gotchas/terminal-keys.md`）。

`f` を押しっぱなしにすると auto-repeat が押下の連打として届くので、
**直前の押下から 120 ms 以内は捨てる**（沈む / 戻るの点滅よけ）。

沈んだまま**つまみも問いも動く** — 沈んだ状態で問いを変えられるのが
いちばんの使い道である。Esc の順は 終了確認 → 選択解除 → フォーカス
解除 → 終了。バッジ `FOCUS` はフッタのモードバッジのスロットで、
**`SELECT` が優先する**（transient な方を先に名乗る。Esc の順と同じ並び）。

### スクロールバーの目盛りと `]m`

右端スクロールバーの**溝**に、マークのある行を琥珀の点（`·`）で打つ
（VS Code の overview ruler）。**溝が無い（本文が収まっている）ときは
出さない。** ガターには何も足していない — 既に `>` / 黄 `▌` / 赤 `▌` /
`│` で混んでいる。

- **つまみが勝つ。** 点と重なる行では形は `▐` のままで、**色だけ琥珀に
  なる**。溝は 1 桁しかないので、点でつまみを切るとスクロール位置の
  ほうが読めなくなる
- **対応づけは溝の全長である**（つまみの座標ではない）。つまみは
  `pos * thumb_max / max_pos` で溝より短い範囲に写すので、同じ式で点を
  打つと「同じマークが、上へスクロールするとつまみの中、下へスクロール
  すると外」になる。目盛りは**文書の地図**である
- 色は `DecorationStyles::mark_tick()` — マークと同じ紙・同じ amber から
  作るので、`--light` でも `--theme` でも同じ系統で動く。**焼き込まない**

**`]m` / `[m`** で次・前のマーク行へ飛ぶ（`]c` と同じ chord の体系）。
環である。飛び先の台帳は溝の目盛りと**同じ 1 本**（`App::marks_lines`）—
2 か所で数えると「点の無いところへ飛ぶ」が起きる。marks モードでだけ
chord になり、それ以外では `]` の既定（ファイル切替）に落ちる。代償は
marks モードにあって、`]` のあとの `m` は popup を開かない（popup は
`]` を挟まずに `m` を打てば開く）。

**`m` は popup であって、巡るのではない。** 巡る形は 1 打ごとに Jev を
呼ぶので、4 本めを見るのに 4 回呼んでいた（議事録で 0.2 円 × 3 の無駄）。
popup は選んだ 1 本しか呼ばない。**開くだけでは 1 円もかからない。**

```text
┌────────────────────────────────────────────────────────────┐
│ mark for ──────────────────────────────────────────────────│
│▸ 1 Essential   what you would misread if it were dropped   │
│  2 Settled     decided, agreed, fixed                      │
│  3 Unsettled   undecided, pending, waiting to be confirmed │
│  4 Decide      asks you to judge, confirm or choose        │
│  5 Numbers     deadlines, amounts, quantities              │
│  / Ask...      type your own question                      │
│ j/k:move  Enter:ask  Esc:close                             │
└────────────────────────────────────────────────────────────┘
```

**`questions` ではなく `mark for` と名乗る。** marks モードでは
「question」が**文書の中にある問い**とも読める（`Unsettled` と `Decide` が
まさにそれを光らせる）ので、こちらが持っている問いと同じ語になってしまう。
最下段の `/ Ask...` は、自由入力があること自体を見せるために行として
置いてある（以前は `?` ヘルプにしか書いていなかった）。

**問いの入力は 1 行プロンプト。** 以前はコメントの composer を借りて
いたが、吹き出しが `comment · 1` と名乗り、1 行の問いのために 3 行を
文書へ割り込ませていた。いまはメッセージ行（フッタのすぐ上）を使う:

```text
 ASK ▸ 費用の話█ ──────────────────────────────────────────────
  ASK   Enter ask · ←→ move · Esc cancel
```

キャレットと IME のアンカーは composer と同じ関数を通す（全角の扱いを
2 つ目実装しない）。**問いは 1 行**なので `^j`（改行）は断る。

**マーカーは引かれる。** 答えが届いた瞬間に薄く全箇所へ乗り（250 ms）、
少し遅れて左→右に線が引かれる（450 ms）。合計 700 ms —
**判定の到着（数秒）と演出は別物**で、待たせるためのものではない。
掴むセルは**琥珀の背景色そのもの**で選ぶので、「今回どこが光ったか」の
台帳が要らない。副作用としてカーソル行は演出に入らない（帯が優先して
琥珀ではない。`docs/gotchas/rendering.md`）。view と source の両方で走り、
`--no-fx` で止まる。**つまみには付けない** — 頻繁に打つ操作で邪魔になる
のと、「今回新しく光った箇所」を出すには装飾集合の差分が要って、つまみ
1 打の費用（いまは `marks::mark` 1 回）が上がるため。

### 1〜3 節の位置づけ

以下の 3 節は、この 0 節に畳まれる前の記録として残す。費用の実測、消える部品の
表、赤入れの難しさ、検索の粒度の話は、0 節の各部の根拠になる。

## 1. マーカーのみの層 — DIM を廃止し、注目すべき箇所だけに線を引く

### 動機 — 費用と、判決の据わりの悪さ

**費用。** 1 文書 1 回の解析費用を実測した（`examples/semantic/measurements/redundancy.md`
のコストの節。単価は入力 $42 / 10⁹ tokens）:

| 文書 | サイズ | tokens（1 回） | 費用（1 回） |
| --- | ---: | ---: | ---: |
| `examples/semantic/demo.md` | 1.6 KB | 25〜27k | 0.1 ¢ |
| web 記事 | 18 KB | 170〜233k | 0.7〜1.0 ¢ |
| `docs/design/semantic-reading-layer.md` | 9.8 KB | 345〜372k | 1.5 ¢ |
| 業務議事録 | 22.7 KB | 707〜781k | 3.0〜3.3 ¢（≈ 5 円） |
| `docs/gotchas/semantic-reading.md` | 最大級 | 1.26〜1.33M | 5.3〜5.6 ¢（≈ 8 円） |

**費用の 9 割は問いの中身ではなく、文書全文（`state`）を何十回も送っている
ことにある。** 議事録は 8k tokens の文書に 740k tokens — 全文を 30 回近く送って
いる計算になる。ラウンドが 5 本以上（境界 → Tier → 冗長＋核 → 前提の波 ×N）、
各ラウンドが 32k 枠で数リクエストに割れるため。同じ 22 KB を汎用 LLM に 1 回
渡す入力費用（3〜4 円）と同じ桁になってしまっており、「速くて安い System One」
の売りが送り方で相殺されている。

**判決。** 読み手が READ 30 % で実文書を読んだときの感想は「DIM って概念が
そもそもそぐうのか。読み飛ばしていい、って気もしない」だった。
`reading-research.md` の言い方では、**MARKED は offer（外れても読み手は損を
しない）、DIM は verdict（外れると信頼を払う）**。そして同じ日に 5 回出た穴は
「読み手のモデルが無い」— 何が重要かは読み手の目的で逆転する（Pichert &
Anderson 1977）のに、Reading Tier は 1 軸で、読み手を知らない。**逆転するものに
判決を下すのが DIM の無理**である。

### 何が消えるか

DIM は「全 Unit に判決を下す」ので、全 Unit の Tier（一番重いラウンド）が要り、
判決を間違えないための部品が積み上がった。**2026-09-22 に作った部品の大半は、
DIM を正しくするためのものである。** マーカーだけなら:

| | いま（DIM あり） | マーカーのみ |
| --- | --- | --- |
| Jev のラウンド | 境界 / Tier / 冗長＋核 / 前提の波 ×N | 境界 / 「ここが要点か、どの一文か」 |
| 全文の送信回数 | 30 回前後 | 数回 |
| 費用（議事録 1 回） | ≈ 5 円 | ≈ 1 円の見立て（未測） |
| Reading Budget（`READ n%`） | 要る | **要らない** |
| Budget の下限（`policy::floor`） | 要る | 要らない |
| 二段台帳（`decorate` の一段目・二段目） | 要る | 要らない |
| `Presupposes` と閉包（context preservation） | 要る（沈んだ前提を戻す） | 要らない（何も沈まない） |
| 冗長の負け（`losers`） | 1 段沈める | 両方光るか片方だけ光るか、だけ |
| 見出しの復帰（`restore_section_heads`） | 要る | 要らない |

正直に書く: **`core-first-ledger` / `read-floor` / `redundancy-loser` / 
`heading-follows-content` / `context-preservation` は、この形では丸ごと不要に
なる。** それでも置いておくのは、Jev 的なものが安くなれば DIM は戻せるから。

### 何が消えないか

- ~~**箇条書きの run キャップ**（`lists-and-run-cap.md`）— しょうもない項目が
  個別に光らないための規則。マーカーの問題なので残る~~ → **外れた**
  （2026-09-22 の実機。0 節の「marks では run キャップを掛けない」）。
  あれは「問いを持たない判決」の側の規則で、問いが選ぶなら要らない
- **ESSENTIAL の criteria** と **核の一文を選ぶ問い**（`core-selection.md`）—
  これがマーカーの中身そのもの。criteria は 2026-09-22 に「未決の論点や宿題」
  まで広げてある（`essential-unsettled.md`）
- **密度と分布**（`mark-distribution.md`）— Scim の「diverse, evenly-distributed,
  important」。読み手が 100 % で言った「マーカーが少なくて物足りない」がそのまま
  主戦場になる。**いまの 4.5 % では少ない**
- **冗長の相手を Jev に選ばせる**（`redundancy.md`）— 対の両方を光らせるか
  片方だけかを決めるのに要る。相手が語彙の argmax だと、無関係な箇所が巻き添えに
  なる

### 新しく要るもの — 「量のつまみ」の置き換え

Reading Budget が消えると `<` `>` のつまみも消える。代わりに **マーカーの濃さ
（本数）のつまみ**が自然である: 少なめ（核だけ）↔ 多め（SUPPORTING の要点まで）。
判決ではなく**提案の量**を変えるので、外れても読み手は損をしない。

**強・弱の 2 段のマーカー**（琥珀の濃淡）で ESSENTIAL と SUPPORTING を分けるのも、
DIM 無しで階層を出す手。`decoration.rs` の `MARK_BG_BLEND` は既に連続量で、
天井 0.40 までの幅がある（`gotchas/rendering.md`「MARKED の天井の理由が変わった」）。

### 文献の支持

`reading-research.md` に既にある形で言えば:

- Lorch の signaling は**足す**合図であって、消す合図ではない
- Scim は光らせるだけで沈めない。冗長対の処理も無く、分布の後処理は「両方に
  光る可能性を残す」
- Pichert & Anderson 1977 — 何が重要かは読み手の視点で逆転する。逆転するものに
  判決を下すのが DIM の無理
- Duggan & Payne の satisficing は「読み手が自分で飛ばす」モデルで、道具が
  飛ばす先を決めるモデルではない

### 未測のこと

- マーカーのみのラウンド構成で費用が本当に 1/4〜1/5 になるか（見立てであって
  測っていない）
- 密度のつまみの上限で、run キャップと分布規則がどこまで持つか
- DIM が無いとき、長い文書で読み手が「どこを飛ばすか」を自分で決められるか
  （読み手の体験の測定）

## 2. 赤入れモード — 読み手の判断を求めている箇所を光らせる

### 動機

AI が Markdown を書くとき、**人に判断を仰ぐために下書きをする**場面がある。
議事録を一旦書いて「これでよいですか」と渡す、文書の中に「要確認」の項目を
残す、選択肢を並べて「どちらにしますか」と聞く。読み手（人）の仕事は全文を
理解することではなく、**判断が求められている箇所を見つけて、赤を入れる**こと
である。

いまの Reading Tier はこの場面に半分だけ合っている。2026-09-22 に ESSENTIAL の
例示を「未決の論点や宿題」まで広げた結果、業務議事録の「要確認」節は DETAIL
一色を脱した（`essential-unsettled.md`）。しかし ESSENTIAL は「落とすと取り違える」
という**理解の軸**であって、「読み手の判断が要る」という**行動の軸**ではない。
決定事項（決まったこと）と要確認（決めてほしいこと）は、理解の軸では同じ
ESSENTIAL に並ぶ。

### 形 — criteria を入れ替えるだけで、機構は同じ

`essential-unsettled.md` で「理解の軸と行動の軸を 2 軸にする」案は却下した
（ジャンル分けが原理のふりをする。汎用性は問いを減らすことで守る）。赤入れ
モードはその却下と矛盾しない — **軸を増やすのではなく、モードで criteria を
入れ替える**。

- 問いは 1 つ: 「この部分は、読み手に**判断・確認・選択**を求めているか」
  （Noul、Unit ごと）。System One の範囲に収まる形
- 光らせるのはその Unit の核の一文（run キャップも同じ）
- Tier も DIM も要らない。**1 節の「マーカーのみ」の形と同じ機構**で、費用も同じ桁
- 何も求めていない文書（完成した記事）では 0 本になる。それが正しい

### 何が難しいか

- **「判断を求めている」と「未決である」は違う。** 議事録の「要確認」は
  書き手が読み手に投げたもの、「宿題」は誰かがやること、「継続議題」は次回に
  持ち越すもの。赤入れが要るのは 1 つ目だけで、System One がこの 3 つを分ける
  かは測っていない
- **書き手の合図との重なり。** AI の下書きは「**要確認**」「TODO」「?」のような
  明示の合図を持つことが多い。合図があるなら Jev は要らない（構文で拾える）。
  合図の無い箇所 — 「〜と思われるが、〜の可能性もある」のような**書き手の
  迷い**を拾えるかが、このモードが Jev を使う理由になる。それも測っていない
- **モードの切り替えを誰が決めるか。** 起動フラグか、文書の種類の推定か。
  推定は「読み手のモデル」の問題を「書き手のモデル」に置き換えるだけで、
  同じ穴に落ちる。**フラグで始める**のが安全

### 未測のこと

- 判断を求める文と、未決を述べる文を、Noul 1 つで分けられるか（議事録の
  3 節で測れる）
- 書き手の明示の合図が無い箇所を拾えるか（下書きの実物が要る）
- 赤入れモードで光った箇所に、読み手が実際にコメント（akapen の本業）を
  付けるか — 光った箇所とコメントの位置の一致率が、このモードの唯一の
  成果指標になる

## 3. 意味の検索 — 自然語で聞いて、意味の合う箇所を光らせる

### 動機

文字列検索（`/`）は語が一致した箇所しか見つけない。「費用の話はどこ」「決まって
いないことは何」「この人が反対した箇所」のように、**読み手が知りたいことを
そのまま入力して、意味の合う箇所が光る**検索。

これは Jev の primitive にいちばん素直に乗る使い方である（`jev.md`）。
2026-09-22 に読み手自身が Jev をこう言っている:「かなりの確度で意味的な検索を
素早くできるのが売りなんじゃないの」。

### 形

- `state` = 文書全文、question = Unit ごとの Noul「この部分は『<入力>』に
  ついて述べている／答えている」。**1 ラウンド、1〜数リクエスト**
- 光らせるのは合った Unit の核（run キャップも同じ）。合う度合いで濃淡を付ける
  なら Score
- 境界（Unit の切り方）は 1 節・2 節と共有できる。**境界だけを先に 1 回取って
  おけば、検索 1 回の費用は `state` 1 回分の桁**（議事録で 0.1〜0.2 円）
- 入力は自然語。語の一致は要らないので、「決まっていないこと」で「要確認」節が
  光ってよい

### 1・2 節との関係

1 節（マーカーのみ）は「書き手が重要と言っていること」を光らせ、2 節（赤入れ）
は「読み手の判断が要ること」を光らせ、3 節は「**読み手がいま知りたいこと**」を
光らせる。**3 節だけが読み手のモデルを持つ** — 読み手が入力するから。
「読み手のモデルが無い」という穴は、モデルを推定するのではなく、**読み手に
聞く**ことで埋まる。Pichert & Anderson の視点効果を、視点を読み手に選ばせる形で
使うことになる。

### 何が難しいか

- **粒度。** Unit（段落）で聞くか Atom（文）で聞くか。文で聞くと question が
  増えるが `state` の送信回数は変わらないので、費用はあまり変わらない。表示の
  粒度は核の一文で揃えるのが自然
- **「述べている」と「答えている」は違う。** 「費用はいくら」に、費用の説明の
  段落（述べている）と金額の一文（答えている）のどちらを光らせるか。Noul の
  文面で分かれるはずだが、測っていない
- **話題と性質も違う。ここは測った**（2026-09-22、第 2 版の 6 節）。いまの型
  「『{q}』について述べている」は**話題**用で、**性質**には効かない —
  「AI slop」と打つと、slop **である**箇所ではなく slop という**語が書いてある**
  箇所が上位に出て、足切りを越えるのが 4 本しかない。**性質の型**
  「下の「対象」は、{q} に当てはまる箇所である。」に替えると AUC 0.87 → 0.99、
  つまみ 20 % の再現率 0.00 → 0.92 になった。**どちらの型を使うかを入力から
  自動で決めるのは難しい**（「費用の話」は話題、「AI slop」は性質、「曖昧な文」は
  どちらでも通る）ので、**型を 2 つ見せて読み手に選ばせる**のがいちばん安い。
  **実装していない**
- **速さ。** 検索は打つたびに走る。1 ラウンドでも往復 1〜3 秒。文書が 80 KB
  天井の近くだと `state` の分割でリクエストが増える。**境界の事前取得と
  キャッシュ**（費用の節の 1・2）がこの機能の前提になる
- **文字列検索との共存。** `/` は残す。意味の検索は別のキー。両方の結果が
  同じ画面に出るとき、色を分けるか

### 未測のこと

- Noul 1 つで「述べている」箇所がどれだけ拾えるか（議事録で「決まっていない
  こと」「費用」「日程」の 3 問を 4 ラン測れば分かる）
- 話題の型と性質の型を**両方聞いて高い方を採る**案の費用（問いが 2 倍になる）
- 文書 1 本の検索 1 回の実費と往復時間（marks の 1 問は 0.06〜0.12 円・1 秒前後。
  第 2 版の 9 節）

## 4. 直すためのマーク — slop の除去（段階 2 実装済み、2026-09-23）

**段階 2 まで実装した。** 候補を拾って一覧に出し、accept でコメントにし（段階 1）、
送る文面の先頭に書き換えの契約を載せる（段階 2）。流れの 2 → 6 を 1 周して測った
（下の「段階 1 で作ったもの」「段階 2 で作ったもの」）。LLM に送らず一覧の `e` で
人が直す道も足した（「直接編集」）。**判定の出どころは既定で linter に移した**
（末尾の「判定の出どころとしての linter」。Jev のルールは既定では 1 本も有効でない）。
節の残りは 2026-09-22 に読み手と設計したときのままである。

### ラインマーカーとの違い — 光ったあとの行き先

1〜3 節は読み手のためで、光った箇所は「そこを読め」。この節は書き手（校閲者）の
ためで、光った箇所は「そこを直せ」。機構は同じ（問い → Unit ごとに Noul → 琥珀）で、
**光ったあとの行き先**だけが違う。読むなら目で終わる。直すなら LLM へ渡す。

読み手の言葉: 「出来上がった文章の構成を大きく変えるのは難しいから、せめて AI slop
的な文章は阻止しよう」「検知器ではないから、そんなに厳しく取る必要はない」
「ユーザーが介在する形で。LLM だけに任せるとめっちゃ時間がかかる領域。ただ、
判定は素早く。書き換えは LLM に（Jev は文章を書かない）」。

### 配管はほぼ既にある — コメントが「人の承認」

akapen の本業は赤入れで、**コメントを外部エージェントへ送る口（`--send-cmd`）**、
**ファイルが書き換わったら差分を `! N` で見せる口**、**履歴を戻す口**が既にある。
この流れはそれを繋ぎ直すだけである。

```text
1. 問い「Slop」を選ぶ         → Jev が Unit ごとに判定（数秒、1 問 0.3 円前後）
2. 琥珀が乗る                  → 読み手が ]m で巡り、1 キーで「直す」/「これはいい」
3. 「直す」に入れた Unit に akapen が自動でコメントを付ける
     （"slop: filler" のような短い理由。コメント ＝ 人が承認した印）
4. 一括送信（既存の send）     → LLM に「この箇所だけ、意味を変えず短く」
5. LLM がファイルを書き換える → akapen が変更を検知し、差分が ! N で光る
6. 人が差分を 1 つずつ見て、採る / 戻す（履歴の機構）
```

人が介在するのは **2（選別）と 6（採否）**の 2 か所で、どちらも既存のキーの範囲。
LLM は 4 だけ。LLM に任せると時間がかかるのは**どこを直すか探すのに全文を読む**
からで、そこを Jev が数秒で肩代わりする。

### 汎用ルール — 「AI っぽさ」ではなく「バイトあたりの損失」

「AI が書いたか」は**出自**の問いで、専用の検出器でも当たらず、光った箇所が告発
として読まれる（判決の形）。聞くのは読み手が一目で感じる**症状**で、ジャンルを
またいで成り立つのは「**落としても読み手が何も失わない**」という言い方 — 要点の
裏返し — だけである。

| 定型 | 問い（損失の言い方） | 汎用か | 初回の実測（2026-09-22、`showcase-slop.md`） |
| --- | --- | --- | --- |
| **Filler** | ここを落としても、読み手が失う事実・数字・判断・理由は無い | ◎ どの文書でも成り立つ | **混ぜた 12 文に AUC 0.98。つまみ 20 %（15 本）で再現率 0.92・精度 0.73。** 叩き台のまま効く |
| **Echo** | ここは前で述べたことの言い直しで、新しい情報を加えない | ◎ **既にある**（冗長の対 Noul、`redundancy.md`）。slop の主症状 | **届いたのは 2 文のうち 1 本**（対 Noul 0.96）。もう 1 本は Tier が `context` で**聞かれもしない**。しかも ≥0.5 の 11 本中 10 本は`決定事項`の一覧＝**消してはいけない側** |
| **Preamble** | 「以下に説明する」「まとめると」のような、内容の前置き・締めで中身が無い | ○ | **`Filler` と相関 0.98。** 単独のラベルでは AUC 0.88 と 3 本で最低。**同じところが光る**（畳むかどうかは測っていない） |
| **Hedge** | 断定を避け、責任の所在をぼかす（〜と思われる、適切に対応する） | △ **ジャンル依存**（契約・医療では正しい書き方）。既定に入れず、選べる定型に | 自分のラベルには AUC 1.00（相関 0.67 で他の 2 本とは別のものを見ている）。12 文全体では **AUC 0.82** と低く、**既定に入れない判断と整合する** |

**数字は初回・1 文書・2 ランで、人の書いた文書での対照が無い。** 生値は
[`../../examples/semantic/measurements/marks-presets.md`](../../examples/semantic/measurements/marks-presets.md)
第 2 版の 3〜5 節。**文面は 1 字も変えずに測った** — 直すならここからである。

4 本目を既定から外すのが汎用の担保。**Jev の汎用性は、問いが文書の側ではなく
読み手の損失の側を向いているときに出る** — Tier が議事録で未決を落としたのは、
例示が文書の側（決まったものの名詞）に寄っていたからだった（`essential-unsettled.md`）。

文面の叩き台（5 則: 損失の言い方 / 例示は両側 / 方向 / 1 問 1 軸 / 無いは Noul）:

```text
Filler
  下の「対象」は、具体的なことを何も述べていない箇所である。ここを落としても、
  読み手が失う事実・数字・判断・理由は無い。一般論、決まり文句、それらしい
  前置きや締め、直前の言い換えが当てはまる。固有の事実・数字・判断・その理由を
  含む箇所は当てはまらない。

Preamble
  下の「対象」は、これから述べること・述べたことの案内だけで、内容そのものを
  持たない箇所である。ここを落としても読み手は内容を 1 つも失わない。
  「以下に説明する」「まとめると」「重要なのは」のような導入・締めが当てはまる。
  結論や判断を実際に述べている箇所は、締めの形でも当てはまらない。

Hedge（選べる定型。既定には入れない）
  下の「対象」は、断定を避けて責任の所在をぼかしている箇所である。ここを
  落とすと、読み手は誰が何を引き受けるのかを取り違える。「〜と思われる」
  「〜の可能性がある」「適切に対応する」「検討する」のように、主体・期限・
  内容のどれかが欠けた言い方が当てはまる。不確かさそのものを事実として
  述べている箇所（「未定」「確認待ち」）は当てはまらない。
```

Echo は新しい定型ではなく、冗長の対 Noul（相手は Jev の Choice）がそのまま
「直す側」の入力になる。

### 「検知器ではない」をどう活かすか

人が選別するので、**取り逃がしより拾いすぎの側に倒せる**。足切りを低めにし、
外れは 1 キーで捨てる。誤検知の代償は 1 キー、検知漏れの代償は slop が残ること。
前者を選ぶ。**offer であって verdict でない**理由はここにあり、フォーカスと同じ側に
いる。

### 一番怖いところ — LLM が「具体化」で捏造する

「空疎だから具体的に」と頼むと、LLM は数字や固有名詞を**作る**。書き換えの契約は:

- **削る・縮める・統合する**だけ。事実を足さない
- 具体性が足りないなら書き換えず、**`[要: 具体例]` のような印を残して人に返す**
- 意味の変化は差分で人が見る（流れの 6）

「書き換えは LLM、事実は人」。これがあれば 4 を外部エージェントに投げても
安全側に落ちる。

### フィードバックループ — 何が学ぶのか

Jev は学ばない。学ぶのは**定型の文面**（データ）と**送る指示**である。
「これはいい」と捨てられた Unit を集めれば、Filler の例示の「当てはまらない側」が
実データで増える — 段 1 でやった「例示はクラスの両側」の右側を、使うほど埋めて
いく形。捨てた Unit を LLM に「ここは触るな」として渡すのは、その場で効く。

| --- | --- |

**上位 N % ではなく閾値。** 文書によって slop の量は違うので、割合で切ると
きれいな文書からも 20 % 拾ってしまう。候補は score 降順ではなく**文書順**に
並ぶ（直すのは上から読みながらの作業である）。`has_core()` は見ない —
marks の投影は核を持たない Unit を落とすが、あれは「どこを読むか」を絞る
仕掛けで、「ここを直せ」には関係が無い。

**UI。** `R` で一覧（`Overlay::Comments` と同じ体裁）。1 行 =
`L42 · Filler 0.87 · <Unit の先頭 40 桁>`。`j/k` 移動、`Enter` で本文へ飛ぶが
**一覧は閉じない**、`a` accept、`x` dismiss、`A` で Pending 全部、`e` でその候補を
`$EDITOR` で直す（末尾の「直接編集」）、`Esc` 閉じる。
accept / dismiss で行は消えず印が変わる（`✓` / `–`）。本文は Pending の Unit に
**細い下線**（紙から青緑へ寄せた色。琥珀と同じ式・違う色相なので `--light` でも
`--theme` を変えても距離が保たれる）、ガターに `!`。フッタ右は marks の読み出しの

**accept = コメント。** 本文は `review: filler (0.87)`（形は
`crate::review::comment_text` の 1 か所。段階 2 の送り先がこれを読む）。以降は
既存の `l` / `y copy` / `s send` にそのまま乗る。

**dismiss は記録する。** `~/.local/share/akapen/review/dismissed.jsonl` に
`{source_sha, range, rule, at}` を追記し、同じ文書を開いたら出さない。
**本文は書かない**（0600 / 0700。`~/.cache/akapen/semantic/` と同じ機密度）。
文書が 1 バイトでも変われば sha が変わって記録は当たらなくなる — 直したあとの
文書で同じ箇所がまた候補になるのは正しい（直っていないかもしれない）。
**ただし akapen が前後の版を見届けた reload では、中身が 1 バイトも変わって

`--semantic-cache-clear` のあとは捨てた候補が戻りうる。

**`--review-json`。** TUI を立てず候補を stdout へ出して終わる
（`{version, source_sha, candidates:[{lines, rule, action, score}]}`）。
**本文は 1 バイトも出ない。** 段階 2 と LSP の入口である。

### 段階 2 で作ったもの（2026-09-23）

**送る文面の先頭に、書き換えの契約を載せる。** 載せるのは、送るコメントに
`review:` の形（`crate::review::comment_text`）が 1 本でもあるときだけで、
**赤入れだけの送信は段階 1 までと 1 バイトも変わらない**（テストが押さえている）。
形に合わない「review: …」は人の赤入れとして扱う（逆向きの
`parse_comment_text` が形を決める）。

| どこ | 何 |
| --- | --- |
| `assets/review-contract.md` | 契約の文面。`$XDG_CONFIG_HOME/akapen/review-contract.md` で上書き。中身は上の「一番怖いところ」の 4 つ（指示した箇所だけを削る・縮める・統合する／事実・数字・固有名詞を足さない／足りなければ `[要: 具体例]` を残す／範囲の外は触らない） |
| `src/review_contract.rs` | 組み立ての 1 か所（`compose`）。`s` も一覧の `y` も `--reply` も同じ文面を通る |
| `src/main.rs` | `export_text` — `export_all` が送る・写す文面 |

**ルールの定義は `review-rules.json` の `text` を逐語で渡す。** コメントは
`review: filler (0.87)` でルール名しか持たないので、契約の後ろに**使われた
ルールだけ**を `- filler（削る）: <text>` の形で並べる。問いの文面は
「下の「対象」は…」で始まるので、その「対象」が指示した箇所だという一言を
添える。**LLM 向けに言い換えた説明を別に持たない** — 持てば Jev に聞いたことと
LLM に伝えたことが 2 か所になり、片方だけ直す日が来る。直し方（`action`）も
契約の 3 つの動詞の内側で言う（`rewrite` は「縮める・統合する。足りなければ印を
残す」）。

**`y` も同じ文面である。** コピーの貼り先も LLM なので、コピーと送信で中身が
違うと「コピーで試した」が試しにならない。本文の `y`（表示のコピー）は
コメントを写さないので関係しない。

**一覧のカーソルのずれを直した。** ルールが 2 本以上あると答えは 1 本ずつ届き、
届くたびに文書順へ並べ直す。一覧を開いたまま前に候補が差し込まれると、添字の
ままのカーソルが別の候補を指し、`a` / `x` が見ていない行に効いていた。並べ直す
前にカーソルの下の候補（rule と range）を覚えて付け直す。

### 直接編集 — 一覧から `e` で人が直す（2026-09-23）

候補を LLM に送らず、**人が `$EDITOR` で直す**道。直すのが 1 文なら、送って
39 秒待つより自分で消す方が早い。LLM が書き換えた場合（`s` のあと、開いたまま
自動 / 手動で reload）も、下の 1・3 は同じ扱いになる。

```text
1. R で一覧 → j/k で候補へ → e
2. その候補の先頭行で $EDITOR が開く（本文の e と同じ作法・同じ行ジャンプの一覧）
3. 直して閉じる → 見届けた reload
     - 範囲が変わっていない dismiss を、新しい位置・新しい sha へ写す
     - 範囲の中が変わった accept 済みの review コメントを外す（フラッシュで 1 行）
     - 変わっていない review コメントは、新しい行へ付け直して NOW に残す
4. 一覧は開いたまま `review · analyzing…` → 答えが揃うと、カーソルは直した箇所へ
     （直した候補が残っていればそれ自身、消えていればその位置の次。文書順）
```

**「見届けた」とは、akapen が開いたまま起きた reload である**
（`crate::reload::reload_source` — `e` の戻り、`r`、`--reply` でない自動
reload）。閉じている間に変わったファイルは、起動時に前の版が手元に無いので
何もしない。`--reply` は文書を丸ごと差し替え、コメントも落とすので写さない。

**差分は既存の `similar` で、行 → 文字の 2 段**（`src/edit_map.rs`）。行で
比べて変わった塊の中だけを文字で比べ直すので、同じ行の別の文を直しても
隣の文の dismiss は写る。**範囲の中に 1 バイトでも挿入・削除・置換があれば
写さない** — 直された文は判定し直す。

| 対象 | 範囲の中が変わっていない | 変わった |
| --- | --- | --- |
| dismiss（`dismissed.jsonl`） | 新しい位置で新しい sha の記録を追記（形式は同じ、本文なし） | 写さない（判定し直す） |
| accept 済みの review コメント | 新しい行へ付け直し、NOW のコメントのまま残す。その候補は届いても `✓` のまま（`a` で 2 本目を作らせない） | **外す**（`s` で直した箇所への指示を送らない） |
| 人の赤入れ | **触らない**（今までどおり古い版へ留め置く） | 同左 |

review コメントの範囲は、accept した候補がまだ手元にあればその Unit のバイト
範囲、無ければコメントの行そのものである。見分けは
`crate::review::parse_comment_text` の形で、人が書いた「review: …」は形に
合わなければ赤入れとして扱う。

**限界。** 判定器の切り方（Unit の境界）が動くと、写した範囲が新しい Unit と
一致せず、捨てた候補が戻る。3 往復の実測では **0 / 18** だった。

| 数えたもの（3 往復、`Filler` 0.5、本物の Jev） | 値 |
| --- | ---: |
| dismiss の引き継ぎ | **18 / 18**（3・6・9 本） |
| 範囲が変わって写さなかった | 0 |
| 切り方が動いて一致しなかった | **0** |
| カーソルが直した位置の次の候補に着いた | **3 / 3** |
| 戻ってから候補が出揃うまで | **0.94〜0.98 秒** |

3 往復目にカーソルが着いたのは**旧の一覧に無かった候補**で、同じ Unit の
score が版ごとに 0.23 → 0.50 と上がって足切りを越えたものだった — 周りの
空疎な文を削るほど、残った文の `Filler` が上がる（1 ランの観察）。生値は
[`review-roundtrip.md`](../../examples/semantic/measurements/review-roundtrip.md)
「直接編集」。

### 判定の出どころとしての linter（2026-09-23）

**判定は linter に任せ、akapen はその後ろの流れを受け持つ。** 一覧・`x` で捨てる・
`a` でコメントにする・`s` で送る・一覧から `e` で直す・見届けた reload での引き継ぎ
— ここまでに作った流れはそのままで、候補の出どころに `--lint-cmd`（環境変数
`AKAPEN_LINT_CMD`）を足した。ルールは読み手が自分の linter の設定
（`~/.textlintrc` など）で決め、akapen はその存在を知らない。

**なぜ Jev を既定から外したか。** 読み手の指摘は「`Filler` などで拾える空疎さは、
実際に気になる箇所と合わない」だった。気になるのは**語の選び方の違和感とぼかし**で、
文単位の「落としても失うものが無いか」ではない。同じ fixture で数えると、軸が違う
ことがそのまま出る（生値は
[`review-roundtrip.md`](../../examples/semantic/measurements/review-roundtrip.md)
「linter を候補に」）:

| 出どころ | 候補 | 混ぜた slop 12 文に当たった | 12 文の外 | `R` → 出揃うまで |
| --- | ---: | ---: | ---: | ---: |
| `Filler`（Jev、段階 1） | 17 | 11 | 6 | 1.29 秒（2 周目、2 ルール） |
| textlint | 13 | 3 | 8 / 12（総評 1 本を除く） | 1.45〜1.99 秒 |
| natural-japanese | 6 | 3 | 2 / 6 | 0.33〜0.83 秒 |

linter は空疎な文をほとんど拾わず、72 行目の「かも」のような**2 字の範囲**で語を
指す。fixture のラベルは空疎さの正解なので、linter の良し悪しはこの表では測れない
— 判断の根拠は読み手の指摘であって、数字は「別の軸を見ている」ことの確認である。
Jev のルールは消していない。`review-rules.json` か `--review-rules` で
`enabled: true` にすれば走り、lint の候補と同じ一覧に文書順で並ぶ。

| どこ | 何 |
| --- | --- |
| `src/lint.rs` | コマンドを走らせ、Diagnostic の JSON を読み、UTF-16 の桁をバイトへ直す |
| `src/review.rs` | `Finding`（Jev のルール / lint）。lint のコメントの形 `lint: <source>/<code> — <message>` |
| `assets/review-contract-lint.md` | lint のコメントがあるときに送る文面の先頭へ足す段落（`$XDG_CONFIG_HOME/akapen/review-contract-lint.md` で上書き） |
| `examples/lint/` | textlint と natural-japanese の出力を Diagnostic に直すスクリプト（標準ライブラリだけ）。textlint 側は micro エディタ用の `--unix-oneline` も出す |

**受け付ける形は 1 つ: LSP の `Diagnostic`**（`{"diagnostics":[{range, message,
source, code, severity}]}`、`line` は 0 始まり、`character` は UTF-16 のコード単位）。
linter ごとの形を akapen に持ち込まない — 変換はスクリプトの側で、akapen が覚える
のはこの 1 つだけである。

- **走らせ方。** `sh -c '<cmd> "$@"'` で、作業ディレクトリは文書のあるディレクトリ、
  最後の引数は文書の絶対パス。stdin は空。見切りは `--semantic-cmd` と同じ（無音
  30 秒・天井 10 分）。linter はディスクを読むので、画面の本文と食い違えば走らせない
- **成否は終了コードではなく出力で決める。** textlint は指摘があると exit 1 で JSON を
  出す。形が違えば `lint: output is not diagnostics JSON`（抜粋は出さない — 本文が
  混じりうる）で、一覧も「0 件」とは言わない
- **範囲は指摘そのまま**（Unit に寄せない）。下線もそこに引く。壊れた範囲はその 1 件
  だけ捨て、幅 0 は行末まで広げる。`severity` は読むが、まだ色分けに使っていない
  （段階の意味が linter ごとに違う — textlint は error / warning / info、lint.py は
  critical / warn / info。色に割り当てる前に揃え方を決めたい）
- **一覧の 1 行は理由を見せる**: `L72 · ja-no-weak-phrase · 弱い表現: "かも" が…`。
  Jev の候補の行（`L42 · Filler 0.87 · <Unit の先頭>`）は変えていない
- **accept = `lint: <source>/<code> — <message>`**（複数行は 1 行に畳む）。送る文面には
  lint 用の短い段落（直し方は指摘に従う・事実を足さない・範囲の外は触らない）を
  足す。Jev ルール用の契約の文面は変えていない。両方あれば両方、Jev の段落が先
- **後ろの流れは既存のまま。** dismiss・差分越しの引き継ぎ・片付けは (rule, 範囲) を
  鍵にしていて、lint の rule（`textlint/ja-no-weak-phrase`）と範囲がそのまま乗る。
  コメントの見分けは `review:` と `lint:` の 2 つの形の和（`candidate_comment_rule`）
- **出どころが 1 本も無ければ** `R` は `no review source — set --lint-cmd or enable a
  rule` と言って断る。`R` のキーは意味層か `--lint-cmd` があれば生きている

**実測で見えたこと。** 1 周の数字は上の表と
[`review-roundtrip.md`](../../examples/semantic/measurements/review-roundtrip.md)。

- `e` で L72 を直して戻ると 1.42〜1.44 秒で出揃い、13 → 10 本（直した 1 本が消え、
  捨てた 2 本は 2 / 2 引き継ぎ、accept した 1 本は `✓` のまま）
- **文書全体を範囲にする指摘がある**（textlint の総評）。下線は全文に引かれ、直すたびに
  範囲の中が変わるので捨てても引き継がれない。`e` のあとのカーソルも一度はここに
  攫われた（直した位置を「覆う」最初の候補だったため）。直した行より上から始まる
  候補を後回しにして直した
