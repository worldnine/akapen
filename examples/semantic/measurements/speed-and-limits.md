# 速さと上限の実測

`examples/semantic/README.md` から分けた実測の記録です。索引は
[`../README.md`](../README.md)「実測の索引」。**文中に測定対象として出てくる
`examples/semantic/README.md` / `docs/gotchas.md` のバイト数・Unit 数は
分割前の値です**（この分割でどちらも小さくなっています）。

---

### demo.md での実測

| | ラウンド 1 | ラウンド 2 | ラウンド 3 |
| - | --------- | --------- | --------- |
| question 数 | 9（境界 26 件のうち散文どうしだけ） | 16（Unit 16 の Tier） | 6（redundancy 5 + 核 1） |
| 所要 | 0.71 秒 | 0.72 秒 | 0.51 秒 |
| input tokens | 3,197 | 4,329 | 1,642 |

合計 9,168 input tokens ＝ **約 $0.0004**（出力トークンは無料）。1 回の解析で
往復は 3 回。Budget の上げ下げでは Jev を呼ばない。

### 大きな文書での実測（2026-09-21）

demo.md は 1,664 バイトしかない。**日常的に開く大きさの文書で測り直した。**
どれも 2 回ずつ（45,650 バイトのものは 7 回）、`--timeout 120` で走らせている。

| 文書 | バイト | Atom | R1 質問 | R1 秒 | R1 tokens | R2 質問 | R2 秒 | R2 tokens | 全体 |
| --- | ---: | ---: | ---: | ---: | ---: | ---: | ---: | ---: | ---: |
| `demo.md` | 1,664 | 27 | 9 | 0.69 | 3,197 | 31 | 0.69 | 6,088 | 1.50〜1.55 秒 |
| `design/semantic-reading-layer.md` | 9,857 | 221 | 36 | 0.82 | 12,390 | 301〜305 | 1.45 | 49,609 | 2.33〜2.45 秒 |
| `design/jev.md` | 15,656 | 149 | 71 | 1.03 | 26,067 | 163〜169 | 1.23 | 38,139 | 2.30〜2.48 秒 |
| `gotchas.md` | 24,280 | 181 | 121 | 1.52 | 46,389 | 153〜159 | 1.42 | 46,107 | 2.88〜3.27 秒 |
| 実業務の `CLAUDE.md` | 45,650 | 218 | 21 | 1.00 | 23,935 | 67 | 1.36 | 60,518 | **2.42〜2.63 秒** |

**時間は問題ではない。** 45,650 バイトで 2.5 秒、akapen の `COMMAND_TIMEOUT`
（60 秒）には 18 倍の余裕がある。

> **この結論は第 2 版（2026-09-22）で覆っています。** ラウンドが 2 本から
> 9 種に増えてリクエストが 12〜41 本になり、同じ経路の壁時計が 47 秒まで
> 伸びました（余裕 1.27 倍）。`COMMAND_TIMEOUT` 自体もう存在せず、
> `COMMAND_IDLE_TIMEOUT`（無音 30 秒）と `COMMAND_BACKSTOP`（600 秒）に
> 分かれています。下の「第 2 版」を読んでください。

### 本当の上限は context window（≒ 65,536 input tokens）

大きな文書で先に当たるのは**時間ではなく大きさ**である。超えると 2 秒台で
HTTP 400 `max_tokens_exceeded` が返る（待っても変わらない）。

| 条件 | input tokens | 結果 |
| --- | ---: | --- |
| 実業務の `CLAUDE.md` そのまま（45,650 B） | 60,518〜63,152 | OK（**天井の 92〜96 %**） |
| 同じ文書を 1.04 倍（47,556 B） | 64,851 | OK |
| 同じ文書を 1.06 倍（48,470 B） | — | **失敗** |
| state 固定で question を増やす二分探索 | 65,033 | OK |
| 同上 | 約 65.5k | **失敗** |

天井は `65,536`（2^16）と読めるが、**TypeSafe の公式値は未確認**である。設計書
`docs/design/jev.md` も「context window は需要に応じて変わりうる」と書いている。
バイト数での上限（この日本語文書では約 2.6 バイト/token）は文書の言語に依存する
ので、**上限は tokens で言うこと**。

ラウンド 2 が重かったのは、`state`（文書全文）に加えて**各 Unit の本文を Tier と
redundancy で 2 回引用していた**ためである。redundancy を SUPPORTING 以上へ
絞ってからは引用が原則 1 回になり、この README で 62,523 → 50,895 tokens に
下がった。**この表の数字は絞り込み前のものである。**

### 何が時間を使っているかの切り分け

2 軸を独立に振って測った（どちらも同じ 1 リクエスト）。

| 条件 | question 数 | input tokens | 所要（中央値） |
| --- | ---: | ---: | ---: |
| 往復の床（極小 state・1 question） | 1 | 277 | 0.58 秒 |
| **state 固定**（45,650 B）・question を変える | 1 | 17,750 | 0.91 秒 |
| 〃 | 20 | 21,876 | 1.03 秒 |
| 〃 | 87 | 63,152 | 1.42 秒 |
| **question 固定**（同じ 20 個）・state を変える | 20 | 5,167 | 0.68 秒 |
| 〃 | 20 | 13,201 | 0.81 秒 |
| 〃 | 20 | 21,876 | 1.00 秒 |

question を 1 → 87（87 倍）にしても 0.91 → 1.42 秒にしかならない。**question の
個数そのものは、時間にはほぼ効かない** — 「全 question を並列・独立に評価する」
が実際にそう動いている。両軸を通すと `約 0.55 秒 + 1.3 マイクロ秒/token` で
説明がつき、question 数の単独の寄与は誤差に埋もれる。

ただし **tokens では question 数はタダではない**。question 1 つにつき定型文
（instructions の枕と `criteria`）が約 116 文字乗る。時間ではなく**天井**に
効くのはこちらである。

## 第 2 版: プロセス壁時計を測り直した（2026-09-22）

上の第 1 版は **2 ラウンドの頃の数字**です。ラウンドは 9 種になり
（probe / boundary / tier / core / redundancy_gate / context1 / pick /
context3 / pick2）、リクエストはチャンクに割られて 12〜41 本になりました。

測ったのは**アダプタのプロセス壁時計**です。当時の `COMMAND_TIMEOUT` が
縛っていたのは子プロセスの寿命そのものなので、`elapsed_s` の合計ではなく
`subprocess.run` を挟んだ壁時計を取っています。5 文書 × 2 ラン、
`dump-request` で本番と同じ要求 JSON を作ってアダプタへ流す経路です。

| 文書 | バイト | Atom | Unit | 壁時計 | リクエスト | 1 req 最遅 | input tokens | 費用 |
| --- | ---: | ---: | ---: | ---: | ---: | ---: | ---: | ---: |
| `demo.md` | 1,664 | 27 | 17 | 6.72 / 6.95 秒 | 12 / 12 | 0.76 秒 | 25.3k / 25.4k | 0.1 円 |
| `design/semantic-reading-layer.md` | 9,857 | 221 | 174 | 20.17 / 17.28 秒 | 23 / 19 | 1.48 秒 | 450k / 422k | 2.2〜2.4 円 |
| web 記事 | 18,250 | 70 | 60 | 13.06 / 11.83 秒 | 16 / 14 | 1.31 秒 | 234k / 210k | 1.1〜1.2 円 |
| 業務議事録 | 22,685 | 182 | 94 | 28.89 / 29.38 秒 | 27 / 28 | 1.56 秒 | 882k / 885k | 4.6 円 |
| `gotchas/semantic-reading.md` | 35,021 | 267 | 124 | **46.88 / 47.43 秒** | 40 / 41 | 1.64 秒 | 1.59M / 1.61M | 8.3〜8.4 円 |

10 ラン合計 6.33M input tokens ≈ 33 円。

### 「18 倍の余裕」は 1.27 倍だった

第 1 版の最大が 3.27 秒で、当時の `COMMAND_TIMEOUT`（60 秒）に 18 倍。
**第 2 版の最大は 47.4 秒で、余裕は 1.27 倍**です。時間が増えたのは
1 リクエストが遅くなったからではありません — 1 リクエストは
**0.76〜1.64 秒**のままで、増えたのは**本数**です。

### 本数は spawn 前に見積もれない

Atom あたりのリクエスト数は **0.095〜0.44** と 4.6 倍ぶれます。18 KB の
散文（web 記事）が 15 本、10 KB の設計書が 21 本で、**バイト数も Atom 数も
代理変数として足りません**。だから固定値も比例式も当たらず、
`COMMAND_TIMEOUT` は**無音時間**の判定に置き換えました
（`src/semantic.rs` の `COMMAND_IDLE_TIMEOUT` = 30 秒、
`COMMAND_BACKSTOP` = 600 秒）。アダプタは 1 リクエストごとに stderr へ
1 行出して生きていることを示します（`jev-annotate.py` の `progress`）。

### 測定対象が 1 日で 1.55 倍になった（**見積もりのまま**）

表の 35,021 B は `docs/gotchas/semantic-reading.md` の **2026-09-22 09:16
時点**です。同日のリポジトリの版は **54,435 B / 421 Atom**（1.55 倍 / 1.58 倍）。

見積もりを 2 通りで出し、どちらも 60 秒を超えました。

1. **Atom 比の素通し**: 40.5 × 1.58 ≈ 64 リクエスト
2. **`--dry-run` の較正**（`--state-tokens` に実測相当の 20,600 を渡して
   チャンクを数え、35,021 B 版の実測との比でラウンドごとに較正）:
   probe 1 / boundary 3 / tier 3 / round3 77×0.245=19 / round4 4×0.5=2 /
   round5 79×0.44=35 = **63 リクエスト**

63 × 1.17 秒/req ≈ **74 秒**。費用は約 15 円/ラン。**実測はしていません** —
5 文書 × 2 ランで予算（40 円）を 33 円使ったためで、この行は見積もりです。

### 副産物: 現在の版は候補の切り詰めが始まる大きさにいる

`redundancy_choice` / `context_choice` は question が `pair`（32k 側）に
収まるまで候補を遠い順に落とします。この切り詰めは**測定した 5 文書では
1 度も発火していません**（10 ラン全部で `redundancy.by_budget = 0`）が、
`--dry-run` を実測相当の state で回すと、ラウンド 3 の question のうち
`pair` の天井に張り付くものが 35,021 B 版で 21/229、**54,435 B 版で
247/370** になります（dry-run は全 Unit を ESSENTIAL と仮定するので上限側の
数字）。時間ではなく**判定品質**の話で、このタスクでは触っていません。

**証拠**: `~/.local/share/akapen/evidence/runs/2026-09-22-command-timeout/`
（README・10 本の応答・ランナー・測定に使ったアダプタ）。測定に使った
アダプタは `examples/semantic/jev-annotate.py` と diff 0 行で、
`2026-09-22-redundancy-choice/ans/*.gate.*.json` の 4 ラン × 5 文書も同じ
アダプタの測定として読めます（壁時計だけが無い）。1 リクエストの最遅
1.72 秒はその**合計 30 ラン / 680 リクエスト**からの数字です。
