> **DIM 版（Reading Budget）は 2026-09-22 に削除済み。当時の記録です。**

`examples/semantic/README.md` から分けた実測の記録です。索引は
[`../README.md`](../README.md)「実測の索引」。**文中に測定対象として出てくる
`examples/semantic/README.md` / `docs/gotchas.md` のバイト数・Unit 数は

### Atom を細かくするとどうなるか

`atomize` がリスト項目を文へ割るようになると Atom 数が増える。**同じ文書・同じ
state で、question の粒度だけを変えて測った**（`atomize.rs` は触らず、計測側で
割っている）。

決定変数は **割ったあとの `kind`** である。

| 文書 | 粒度 | Atom | R1 質問 | R2 質問 | R2 引用本文 | R2 定型文 |
| --- | --- | ---: | ---: | ---: | ---: | ---: |
| `CLAUDE.md` | 粗い（現状） | 218 | 21 | 87 | 40,694 | 10,089 |
| 〃 | 細かく割るが `kind` は `list_item` のまま | 404 | 24 | 93 | 41,072 | 10,782 |
| 〃 | 細かく割って `kind` を `sentence` にする | 404 | **278** | **677** | 41,656 | **78,234** |

**引用する本文の総量は粒度でほとんど変わらない**（40,694 → 41,656 文字）。
変わるのは question の個数と、それに比例する定型文である。

- `kind` が `list_item` のままなら、構造ルール 4（`list_item` どうしは
  SAME_UNIT）が効くので **question はほぼ増えない**（21 → 24、87 → 93）
- `kind` が `sentence` になると規則 5 で Jev に聞く境界が激増し、`CLAUDE.md`
  では R1・R2 とも **`max_tokens_exceeded` で失敗した**

時間の方は、粒度が実際に変わって**かつ収まる**文書（`design/jev.md`、Atom
149 → 154）で R1 1.05 → 1.01 秒・R2 1.54 → 1.41 秒と、**横ばい**だった。
「Atom を細かくすると並列が増えて速くなる」は観測されていない。速くも遅くも
ならず、**天井に当たるかどうかだけが変わる**。

表示は、`## 結論` の下の 1 行で**行の途中が切り替わった**。

| READ | 「採用する方式は差分配信である。」 | 「詳細は付録にまとめた。」 |
| ---- | ---------------------------------- | -------------------------- |
| 100% | MARKED | NORMAL |
| 70%  | MARKED | NORMAL |
| 60%  | MARKED | **DIM** |

`demo.json`（人の注釈）では 75 % で切り替わる（このページ上部の表）。Jev の
判定では 60 % だった。一方 `## 補足` の行は、Jev が `つまり、…` と
`念のため繰り返しておく。` を**どちらも DETAIL** と見たため 90 % で両側とも
同時に DIM になり、行の途中では切り替わらなかった。

### 第 2 版 — 表を行ごとの Atom に割る（2026-09-22）

上の実測は**リスト項目**を文へ割ったときの話である。同じ問い（Atom を細かく
すると何が動くか）を、**表**について測った。

生値は `~/.local/share/akapen/evidence/runs/2026-09-22-table-rows/`。

#### 何を変えたか

表 1 つ = Atom 1 つだったものを、**ヘッダ行（＋区切り行）＋ データ行**へ割った
（`table` / `table_row`）。境界は「次が `table_row` なら SAME」の 1 行で、
**表は 1 つの Unit のまま**である。核の候補（`PROSE_KINDS`）にデータ行を足し、
ヘッダ行は入れていない。

#### Atom 数は「表のデータ行の数」だけ増える

測定対象 5 文書と、表を含むリポジトリ内の 2 文書。**前は HEAD の `dump-request`、
後は同じ文書の新しい `dump-request`** で、本文は同じものを食わせている。

| 文書 | 前 | 後 | 差 | うち `table_row` |
| --- | ---: | ---: | ---: | ---: |
| `examples/semantic/demo.md` | 27 | 27 | 0 | 0 |
| `docs/design/semantic-reading-layer.md` | 243 | 243 | 0 | 0 |
| 業務議事録 | 182 | 182 | 0 | 0 |
| web 記事（第三者・公開） | 70 | 70 | 0 | 0 |
| `docs/gotchas/semantic-reading.md` | 428 | 454 | +26 | 26 |
| `docs/README.md` | 27 | 48 | +21 | 21 |
| `docs/quickstart.md` | 55 | 65 | +10 | 10 |

**差は `table_row` の数と 1 件残らず一致する。** そして表を含まない 4 文書では、
Atom 列が `(kind, range)` まで**バイト単位で同一**だった（JSON を `diff`）。
表を含む 3 文書でも、**表以外の Atom は 1 つも動いていない**。

> 測定対象 5 文書のうち表を含むのは `docs/gotchas/semantic-reading.md` だけ
> だった。DIM 版の実測に `docs/README.md` と `docs/quickstart.md` を足したのは
> そのためである（どちらも小さく、表の密度が高い）。

#### DIM 版 — Unit の切り方も Tier も動かない。動くのは MARKED の面積

`docs/README.md` を前後 2 ランずつ、`docs/quickstart.md` を前後 2 ランずつ。
数字は `decorate-report`（**分母は Atom のバイト長の合計**）。**8 ラン中、
同じ側の 2 ランは 1 つ残らず同じ値だった**（幅 0）ので、下の差は揺れではない。

| | Unit | ESSENTIAL | MARKED(100%) | DIM(80%) | DIM(下限) |
| --- | ---: | ---: | ---: | ---: | ---: |
| `README` 前 | 13 | 7 | 67.9 % | 21.7 % | 26.0 % |
| `README` 後 | 13 | 7 | **18.2 %** | 21.6 % | 26.0 % |
| `quickstart` 前 | 38 | 6 | 21.6 % | 19.8 % | 72.7 % |
| `quickstart` 後 | 38 | 5 | **9.7 %** | 19.9 % | 80.6 % |

- **Unit 数は前後で同じ**（13 / 38）。表が 1 Unit のままだからで、境界のラウンドに
  新しい質問は 1 つも増えていない
- **Tier はほぼ動かない。** `README` の表 3 つは前後とも
  `essential` / `detail` / `essential` で**完全に同じ**。動いたのは
  `quickstart` の表 1 つで、ESSENTIAL → SUPPORTING へ 1 段落ちた。前後とも
  2 ランが同じ値なので**揺れではない** — 行へ割ったことで Tier のラウンドが
  見る本文の形が変わった分である。表を含む 4 Unit のうち 1 つ、方向は
  「下がる」側（光らせすぎない側）で、**ESSENTIAL が増えた Unit は 1 つも無い**
- **下限の位置も動かない。** どちらも Budget 60 % 以下で値が止まる
- **MARKED の面積だけが大きく減る**（67.9 → 18.2 %、21.6 → 9.7 %）。MARKED の
  Atom 数は 6 で同じなので、これは**1 つの MARKED が指す面積**が変わったという
  こと ——「表が丸ごと光る」から「表の中の 1 行が光る」への変化がそのまま出た

**`jev.unsent` は 8 ラン全部で 0 件。**

#### marks モード — 表が「一度も光らない」が直った

`docs/README.md`（表 3 つ）に定型の問いを当てた。前後 1 ランずつ。

| 問い | 表の Unit | score（前 / 後） | 核（前 → 後） |
| --- | --- | --- | --- |
| 数字と日付 | 3 つ | 0.17 / 0.27、0.10 / 0.09、**0.64 / 0.61** | 空 → データ行 1 つ（足切りを越えた 2 つ） |
| 要点 | 3 つ | 0.73 / 0.78、0.79 / 0.79、0.82 / 0.82 | **空 → データ行 1 つ（3 つとも）** |

**スコアは前後でほとんど同じ**（表の中身は変わっていないので当然である）。
変わったのは核で、変更前は**足切り 0.20 を大きく超えていても核が空**だった
—— marks では核の無い Unit は光らないので、`要点` で 0.82 を取った表が
一度も光らなかった。変更後は 3 つとも 1 行だけが光る。

**費用**: 全 12 ラン（DIM 8 / marks 4）で入力 42.3 万・出力 2.2 万トークン、
`docs/design/marks-only-and-review-mode.md` の換算で **≈ 3 円**。
