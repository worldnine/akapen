# 核の選び方の実測

> **DIM 版（Reading Budget）は 2026-09-22 に削除済み。当時の記録です。**

`examples/semantic/README.md` から分けた実測の記録です。索引は
[`../README.md`](../README.md)「実測の索引」。**文中に測定対象として出てくる
`examples/semantic/README.md` / `docs/gotchas.md` のバイト数・Unit 数は
分割前の値です**（この分割でどちらも小さくなっています）。

### MARKED を Unit の核だけに絞る（2026-09-21 の実測）

45.6 KB の実業務文書（`CLAUDE.md`）を開くと、**画面の半分近くが MARKED**
だった。原因は Atom の粒度ではなく **Unit** である。境界の構造ルール 4
（`list_item` どうしは SAME_UNIT）が箇条書き 1 つを丸ごと 1 Unit にまとめ、
`policy::decorate` が Unit の Tier を構成 Atom **全部へ一律に**投影していた。
だから ESSENTIAL な箇条書きは段落ごと光る。直前の改修で Atom を 218 → 372 へ
細かくしても、**比率は 1 % も動かなかった**（判断も表示も Unit のままだったため）。

そこでラウンド 3 を足し、MARKED になる Unit にだけ

> このまとまりから **1 か所だけ**読むとしたら、どこを読めば要点が取れるか

を Choice で聞いて、**その Atom だけを MARKED、同じ Unit の残りを NORMAL** に
した。選択肢は Unit を構成する Atom の本文そのもの（キーは `atom:<index>`）。

**この文面はこの日のうちに損失ベースへ差し替えた**（次の節）。この節の数字は
差し替え**前**の文面で取ったものである。

**DIM は一律のままである。** Unit が落ちたなら丸ごと沈む — ここを選択的に
すると「なぜこの行の一部だけが沈むのか」を読者に説明できない。

**小さい文書で MARKED が消えはしない。** `demo.md` は 27 Atom のうち 6 →
**3** が MARKED として残った（Atom が 1 つしかない Unit には核を聞かないので、
短い文書ほど絞り込みが効かない）。

ラウンド 3 の値段:

| 文書 | 聞いた Unit | question | 所要 | input tokens |
| --- | ---: | ---: | ---: | ---: |
| `CLAUDE.md` | 34 Unit 中 8（ESSENTIAL 11 のうち Atom が 2 つ以上あるもの） | 8 | 0.99 秒 | 28,354 |
| `demo.md` | 16 Unit 中 2 | 2 | 0.49 秒 | 1,171 |

**context window には余裕が残る。** いちばん重いのは依然ラウンド 2 で、
`CLAUDE.md` の 60,772 tokens（天井 ≒65,536 の 93 %）。ラウンド 3 は state に
核を聞く Unit の本文だけを足すので 28,354 tokens（43 %）に収まった。
プロセス全体は 2.64 秒 → **3.54〜3.57 秒**（2 回）、`demo.md` は 1.33 → 1.88 秒。

**核の選択は 2 回の実行で揺れなかった。** `CLAUDE.md` を 2 回走らせると、
境界（Unit の組）は完全に一致し、両方で聞かれた 7 つの question は
**7 件とも同じ Atom** を核に選んだ。8 つ目の question は片方にしか無い —
ラウンド 2 の Tier がその Unit で揺れて ESSENTIAL から外れたためで、
ラウンド 3 が揺れたのではない。`demo.md` は 2 回とも完全一致。比率で見ても
MARKED は 5.0 % と 4.9 %（修正前も 46.7 % と 46.3 %）で、この差は実行ごとの
揺れの幅に収まっている。

**核に閾値は使っていない。** Choice が返す 1 つをそのまま採り、
`probabilities` を閾値で切って複数採ることはしない（`confidence` の閾値が
実測で不安定だった件は
`examples/semantic/README.md`「confidence は記録するだけ」）。選ばれた核の
`confidence` は 0.31〜0.96 と幅が広いが、**値で判定を倒していない**。

選ばれた核の `kind` の内訳（`CLAUDE.md` 8 件）は `list_item` 4 / `sentence` 3
/ `heading` 1 だった。見出しが核になった Unit が 1 つある（構造ルール 2 で
見出しは直後の内容と同じ Unit になる）。**これが読み物として良いかは
測っていない。**

### 核の問いを損失ベースにする（2026-09-21 の実測）

上の節の文面（「**1 か所だけ**読むとしたら、どこを読めば要点が取れるか」）
だと、後続をまとめている導入文や、その節の主題そのもののラベルが核に選ばれる。
**Jev は問いに正しく答えている** — 悪いのは問いの方である（理由は
`docs/design/jev.md`「Unit の核」）。文面を

> このまとまりの中で、**これを読み飛ばすと要点を失う**のはどれか。

へ差し替えて測った。**`atomize` は一切変えずに、文面だけを差し替えて測って
いる**（同じ日に測った擬似見出しの `atomize` 案は採らなかった。理由は
`docs/gotchas/semantic-reading.md`「箇条書きのラベルが MARKED になる」）。
各条件 2 回ずつ走らせている。

核の選び方が実際に変わり、**ラベルから中身へ倒れる**。

| Unit | 旧文面の核 | 損失ベースの核 |
| --- | --- | --- |
| 議事録の登録手順（19 Atom） | 項目の**ラベル**（`- **…**:` の部分） | その項目が述べている**制約そのもの** |
| 業務 `CLAUDE.md` の冒頭（3 Atom） | 太字リードの前半（閉じ記号が迷子の断片） | **着手できない理由そのもの** |

**demo.md の看板は残った。** 行の途中で表示が切り替わる「採用する方式は差分
配信である。」は 8 回の実行すべてで核のままで、「詳細は付録にまとめた。」は
NORMAL のままである（実機の ANSI でもセル単位で確認した）。制約 Unit の核
だけが「既存の API は変更しない」→「移行期間中も取りこぼしを出さない」へ
移った。

MARKED 比率（分母は Atom のバイト長の合計。budget 100 %・run1）:

| 文書 | 旧文面 | 損失ベース |
| --- | ---: | ---: |
| `demo.md` 1.6 KB | 12.8 % | 13.4 % |
| `design/semantic-reading-layer.md` 9.9 KB | 24.7 % | 26.7 % |
| この `README.md` 29 KB | 1.2 % | 1.0 % |
| 業務議事録 22.7 KB | 9.1 % | 11.3 % |
| 業務 `CLAUDE.md` 45.6 KB | 4.9 % | 3.3 % |

**context window の使い方は変わらない。** いちばん重いラウンドの input tokens
（÷ 実測の天井 ≒65,536）は、旧文面 → 損失ベースで `demo.md` 4,329 → 4,329
（7 %）、design 34,210 → 34,026（52 %）、この README 52,985 → 52,986
（**81 %**）、議事録 25,620 → 25,801（39 %）、`CLAUDE.md` 40,911 → 41,092
（63 %）。差はどれも 1 % 未満で、選択肢の本文は変えていないので当然である
（変わるのは instructions の数十 tokens だけ）。

**ラウンド 3 では検証できない Unit がある。** 業務議事録の `## 決定事項`
（文書の前半で述べた決定の再掲）は、**8 回の実行すべてでラウンド 2 に
REDUNDANT と判定され、ラウンド 3 に到達しない**。核を聞かれないので、この
Unit の核で文面の良し悪しを測ることはできない。redundancy の判定自体は妥当
である。**核の question の合格条件をここに置くと、文面をどう変えても満たせ
ない** — 前任者が詰まったのと同じ構造なので、次に測る人は先に
「その Unit が本当に R3 まで来るか」を確かめること。

### 引用（`block_quote`）を核の候補に入れる（2026-09-22 の実測）

引用だらけの web 記事を marks で読むと、**引用の中が一度も光らなかった**。
`PROSE_KINDS` に `block_quote` が無く、`core_candidates` が引用を核の候補から
外していたため、引用しか持たない Unit の `core_atoms` が空のまま残る。marks は
核を持たない Unit を光らせない（`marks::lights_up`）ので、何を聞いても光らない。

`PROSE_KINDS` に 1 語足した前後を、**核のラウンドだけ**測った。境界と Tier は
既存の応答から借りて API を叩かない（叩くのはラウンド 3 だけ）。5 文書 × 2 ラン
× 前後、DIM 版の掛かり方（Tier が ESSENTIAL）と marks の掛かり方（スコアが
足切り 0.20 以上）の両方。

**marks の掛かり方**（問い「要点」）:

| 文書 | ラン | Unit | 引用を含む Unit | 核を持つ Unit 前→後 | うち引用 Unit 前→後 | question 前→後 |
| --- | ---: | ---: | ---: | ---: | ---: | ---: |
| `demo.md` | 1 | 17 | 1 | 15 → 16 | 0 → 1 | 2 → 2 |
| 〃 | 2 | 17 | 1 | 15 → 16 | 0 → 1 | 2 → 2 |
| web 記事 | 1 | 58 | 17 | 38 → **55** | 0 → **17** | 10 → 10 |

| 文書 | ラン | 核を持つ Unit 前→後 | うち引用 Unit 前→後 | question 前→後 |

**web 記事は DIM 版では動かない。** 58 Unit のうち ESSENTIAL が 2 つしかなく、
引用 Unit は 1 つも ESSENTIAL にならないので、そもそも核を聞かれない。この
文書で効くのは marks だけである — 問いが引用を拾うから。

**question は 1 本も増えなかった**（合計 245 → 245、DIM 版 95 → 95）。
新たに核が付いた引用 Unit は marks で 47 件・DIM 版で 19 件だが、
**全件が `rule:only_prose_atom`**（Jev に聞かずに決まった）である。構造ルール 6
が `block_quote` の境界を常に NEW にするので引用 1 文が 1 Unit になり、候補が
1 つしか無いためで、[`assign_lone_cores`] がそのまま埋める。実費も
157,035 input tokens で前後同一だった。

**予算を超えて核を失った Unit は無い**（前→後で核を持つ Unit が減った文書は
無い）。引用は候補の本文を長くするので [`core_fits`] に当たりうるが、この
5 文書では起きていない。

**引用を含まない Unit の核は動いていない。** DIM 版は 10 ラン全部で 0 件。
marks では 1〜3 件動いた文書があるが、**同じ版の 2 ランを突き合わせた揺れの床**
（design 11 件、`gotchas` 3 件、業務議事録 2 件）の中に収まる — 前後は別の
リクエストなので、Choice の答えがもともとこれだけ揺れる。
