# 箇条書きと run キャップの実測

> **DIM 版（Reading Budget）は 2026-09-22 に削除済み。当時の記録です。**

`examples/semantic/README.md` から分けた実測の記録です。索引は
[`../README.md`](../README.md)「実測の索引」。**文中に測定対象として出てくる
`examples/semantic/README.md` / `docs/gotchas.md` のバイト数・Unit 数は
分割前の値です**（この分割でどちらも小さくなっています）。

---

### 箇条書きを項目ごとに割る（規則 4 の変更・2026-09-21 の実測）

**結論から: 実装はしたが、置いた合格条件は満たさなかった。** MARKED 比率が
揺れの床を超えて増える。採否は下の「定性的な証拠」と合わせて人が決めること。

#### 何を変えたか

境界の構造ルール 4 は「`list_item` どうしは SAME_UNIT」だった。これだと
箇条書きが丸ごと 1 Unit になり、**10 個の決定事項が全部同じ Tier**になる。
ユーザーの言葉:

> 決定事項は一緒に沈むので正しい。が、しょうもない決定事項があれば個別に
> 沈んで欲しいという気持ちもある。

そこで規則 4 を「**別項目どうしは NEW / 同じ項目の中は SAME**」に変えた。
判別は構造だけで、Jev には聞かない（設計書「Jev に判断させないもの:
syntax parsing」）。手がかりは `atomize` が項目の Atom を**マーカーから**
始めることで、継続文にはマーカーが無い。

**割るのはトップレベルの項目の切れ目だけである。** 子項目は親に SAME のまま
残す。ユーザーの言う「決定事項」は親項目＋その詳細の束なので、そこで割ると
`policy::decorate` の docstring が警告する「半分だけ DIM のリスト」が親子の
あいだで起きる。深さは要求 JSON から取れる — `range.start` から直前の改行まで
戻れば行頭のインデントが読める（[`list_marker_indent`]）。

境界の内訳（構造だけで決まるので、Jev を呼ばずに数えられる）:

| 文書 | 規則 4 が当たる境界 | → NEW（別項目） | SAME（子項目） | SAME（継続文） |
| --- | ---: | ---: | ---: | ---: |
| `demo.md` | 1 | 1 | 0 | 0 |
| `design/semantic-reading-layer.md` | 21 | 21 | 0 | 0 |
| この `README.md` | 6 | 3 | 0 | 3 |
| 業務議事録 22.7 KB | 94 | 46 | 0 | 48 |
| 業務 `CLAUDE.md` 45.6 KB | 314 | **97** | **63** | 154 |

**ネストを持っていたのは `CLAUDE.md` だけ**である（インデント 2 が 55 件、
4 が 8 件）。子を割らない判断がここで 63 Unit を節約している。

#### Unit 数と context window

Unit 数は実際の Jev の答えから数えたもの（実行ごとに境界が揺れるので幅がある）。
R2 の input tokens は `usage` の実測で、括弧内は実測の天井 65,536 に対する割合。

| 文書 | Unit 前 | Unit 後 | R2 tokens 前 | R2 tokens 後 |
| --- | ---: | ---: | --- | --- |
| `demo.md` 1.6 KB | 16 | 17 | 4,329 (7 %) | 4,511 (7 %) |
| `design/…` 9.9 KB | 150〜152 | 172〜173 | 34,027〜34,389 (52 %) | 38,029〜38,211 (58 %) |
| この `README.md` 32.5 KB | 181〜183 | 185〜186 | 58,285〜58,651 (89 %) | 59,014〜59,197 (90 %) |
| 業務議事録 22.7 KB | 46〜48 | 92〜95 | 25,260〜25,620 (39 %) | 33,619〜34,160 (52 %) |
| 業務 `CLAUDE.md` 45.6 KB | 34〜35 | 130〜132 | 40,910〜41,092 (62 %) | 58,370〜58,733 (**89 %**) |

**`CLAUDE.md` は天井を超えなかった。** 事前の見積もりでは超える計算だったが、
その計算は 1 Unit あたりの固定費を **262 tokens**（Tier 181 + redundancy 81）と
置いていた。redundancy は既にラウンド 3 へ移してあって SUPPORTING 以上にしか
聞かないので、**ラウンド 2 に乗る固定費は Tier の 181 だけ**である。加えて
子を割らない判断が 63 Unit を節約した。実測は `40,911 + 97 × 181 ≒ 58,500` と
ぴったり合う。**天井超えを不合格の理由にはしていない**（そもそも超えなかった）。

**ただし余裕は無い。** `README.md` は 90 %、`CLAUDE.md` は 89 % に載っている。
これは規則 4 の欠陥ではなく、規則 4 と無関係に今日もある既存の崖である
（`docs/gotchas/open-questions.md` 未解決 5）。**R2 を分割する実装は
ここでしない。**

#### MARKED 比率 — ここで落ちた

**まず揺れの床を測った。** 変更前を同じ要求で複数回走らせ、MARKED 比率が
どれだけブレるかを見る。床を知らずに閾値を置くと「変更なし」すら棄却する
基準になる（`docs/gotchas/open-questions.md` 5.1 と同じ作法）。

分母は Atom のバイト長の合計、Budget 100 %。括弧内はラン数。

| 文書 | 変更前＝揺れの床 | 変更後 | 判定 |
| --- | --- | --- | --- |
| `demo.md` | 12.8〜13.4 % (4) | 16.6 % (4) | **床を超えて増加** |
| `design/…` | 22.9〜26.0 % (4) | 23.1〜26.0 % (4) | 床の中 |
| この `README.md` | 2.9 % (2) | 1.4〜1.5 % (2) | 減少 |
| 業務議事録 | 9.6〜10.2 % (4) | 11.7〜13.1 % (3) | **床を超えて増加** |
| 業務 `CLAUDE.md` | 3.3〜3.7 % (4) | 10.8〜11.2 % (4) | **約 3 倍** |

**5 文書のうち 3 文書で、MARKED が揺れの床を超えて増えた。** 合格条件は
「床を超えて増えていないこと」だったので、**不合格**である。

理屈は素直で、これは**予見されていた本当のリスク**そのものだった。MARKED は
「ESSENTIAL かつ非 REDUNDANT な Unit」ごとに 1 つの核 Atom として付く
（[`wants_core`]）。Unit が割れれば ESSENTIAL な Unit が増え、MARKED は
比例して増えうる。ユーザーの要望は

> パーセントにかかわらず、これさえ見ればオッケー的なミニマルな提案

なので、MARKED が増えるのは要望に反する。

**Tier 一致率は測っていない。** その床は「同じ分割どうし」の比較で測った値で、
分割そのものを変える今回には使えない。

#### 定性的な証拠 — 要望そのものは叶っている

数字は落ちたが、**ユーザーが言った現象は実際に直っている。** 業務議事録の
`## 決定事項`（番号つき 8 項目）を Budget 60 % で見る。

変更前は 8 項目が**丸ごと 1 Unit** で、**8 項目すべてが一斉に DIM** になる。
これが「決定事項は一緒に沈む」である。

変更後は項目ごとに割れて、沈み方が分かれた:

| 決定事項 | 変更前 | 変更後 |
| --- | --- | --- |
| 決定 1 | DIM | DIM |
| 決定 2 | DIM | **MARKED** |
| 決定 3 | DIM | **MARKED** |
| 決定 4 | DIM | DIM |
| 決定 5 | DIM | NORMAL ＋ 核が MARKED |
| 決定 6 | DIM | **MARKED** |
| 決定 7 | DIM | DIM |
| 決定 8 | DIM | DIM |

**「しょうもない決定事項が個別に沈む」は起きている** — 1・4・7・8 が沈み、
2・3・5・6 が残る。変更前は全部まとめて沈むか、まとめて残るかしかなかった。

**同時に、MARKED が 0 個から 4 個へ増えている。** これが上の比率の正体である。
要望の 2 つの側面がここで正面から衝突する:

- 「しょうもない決定事項が個別に沈んで欲しい」 → **叶う**
- 「これさえ見ればオッケー的なミニマルな提案」 → **反する**

**採否はこの取引をどう見るかで決まる。** 測った側で決めていない。

#### 親と子はどう扱われたか

ネストがあるのは `CLAUDE.md` だけである。親項目・子項目・継続文が 1 つの Unit に
まとまり、核は 1 つだけ MARKED になる — 「半分だけ DIM のリスト」は起きていない。

本文は業務文書なので伏せる。**構造だけ**を書くと、1 つの Unit が

```text
Unit u41  tier=essential  core=[79]
  idx 73  項目(indent=0)   ← 親項目
  idx 74  継続文
  idx 75  継続文
  idx 76  継続文
  idx 77  項目(indent=2)   ← 子項目
  idx 78  継続文
★ idx 79  項目(indent=2)   ← 子項目（ここが核）
  idx 80  継続文
```

のようにまとまり、**核は 1 つだけ**である。

#### 増えたぶんは「1 Atom の Unit」だけに寄ってはいない

`assign_lone_cores` は散文の候補が 1 つしかない Unit の核を**聞かずに**決める
ので、項目ごとに割ると「1 Atom の Unit がそのまま光る」経路が増える。これは
`docs/gotchas/semantic-reading.md`「箇条書きのラベルが MARKED になる」と
同じ形なので、
**そこだけ直せば増加を消せるのではないか**を確かめた。

MARKED になる Unit（ESSENTIAL かつ非 REDUNDANT）の内訳:

| 文書 | | MARKED Unit | うち Jev が核を選択 | うち 1 散文 Atom（聞かず） |
| --- | --- | ---: | ---: | ---: |
| 業務 `CLAUDE.md` | 前 | 11〜12 | 7〜8 | 4 |
| | 後 | **25〜26** | **16〜17** | **9** |
| 業務議事録 | 前 | 10〜12 | 6〜8 | 4〜5 |
| | 後 | **16〜19** | **9〜11** | **7〜8** |

**どちらの経路も同じ比率で増えている。** 逃げ道は無い — 増加は 1 Atom の Unit の
扱いではなく、**分割そのもの**から来ている。「個別に沈む」と「MARKED を増やさない」
を別々に取ることは、この実装ではできない。

#### run キャップを入れたらどこまで戻るか（数えただけ・未実装）

衝突している 2 つの要望はメカニズムが別である。**沈む**のは Tier（Unit ごと）、
**光る**のは核（`wants_core` が Unit ごと）。そこで「Tier は項目ごとのまま、核は
**リスト 1 本につき 1 つ**」にしたらどうなるかを、既存の応答から数えた。

ここで **run** とは、規則 4 由来の境界（`rule:new_list_item`）でつながった Unit の
並び ＝ 1 本のリストである。上限は

    「MARKED になりうる Unit を 1 つ以上含む run」の数
      + どの run にも属さない単独の MARKED Unit の数

で、run キャップを入れたときの MARKED Unit 数の**上限**になる。

| 文書 | 変更前 | 変更後 | run キャップ上限 |
| --- | ---: | ---: | ---: |
| 業務 `CLAUDE.md` | 11〜12 | 25〜26 | **13〜14** |
| 業務議事録 | 10〜12 | 16〜19 | **13〜14** |
| `design/…` | 35〜38 | 37〜42 | **33〜38** |
| この `README.md` | 7 | 6 | **6** |
| `demo.md` | 3 | 4 | **3** |

**5 文書とも変更前の水準に戻る。** つまり増加の出どころは「**1 本のリストの中で
複数の項目が光る**」であって、「丸ごとだと CONTEXT だったリストが、割ると中に
ESSENTIAL が現れる」ではない。後者なら run キャップでは消えないはずだが、消える。

`design` は上限の下側が変更前の下限（35）より低い（33）。run キャップは
**変更前より MARKED を減らしうる** — 変更前から 1 本のリストが複数 Unit に
分かれていた箇所（散文の境界で割れたもの）にも効くためである。

**これは上限であって実測ではない。** 実装すれば核の question の出し方が変わるので、
Tier の揺れ次第で上下する。**まだ実装していない。**

分割すると redundancy の問いは増え、核の問いは（Unit が小さくなるので）1 つ

| | 後 | 59〜60 | 42〜44 | 16〜17 | 34,259〜34,796 | **52〜53 %** |

| | 後 | 65〜67 | 52〜53 | 13〜14 | 21,251〜21,515 | **32 %** |
| `design/…` | 前 | 50〜53 | 47〜50 | 3 | 8,948〜9,348 | 13〜14 % |

**質問数が 3 倍になっても tokens はほとんど動かない。** redundancy の固定費は
1 問 81 tokens しかないうえ、**核の question が軽くなるぶんで相殺される** — 巨大な
Unit を丸ごと選択肢に引用していた核 question（`CLAUDE.md` の 82 散文 Atom で

37,571 → 34,796 に**下がり**、実行ごとの幅も狭まった。

**R3 は制約になっていない。** 縛っているのは引き続きラウンド 2（89〜90 %）である。

#### 確認したこと

要求 JSON は `cargo run -p semantic-reading --example dump-request` で akapen 本体と
同じ `atomize` 経路から作り、**変更前のスクリプトを退避して同じ要求を食わせた**
（`atomize` は一切変えていないので、Atom の range は前後で同一。表示状態の
突き合わせはこの range で行った）。5 文書 × 変更前後を、`README.md` だけ 2 回、
残り 4 文書は 3〜4 回ずつ、合計 38 ラン。比率は `decorate-report`、Atom ごとの
状態は `atom-states`（どちらも `policy::decorate` そのものを通す）。核の経路の
内訳は各応答の `units[].jev.core_by` から数えた。run キャップの上限と R3 の
天井比は、**Jev を呼び直さずに**この 38 ラン分の応答から数えたものである
（run は各応答の `jev.boundaries` の `rule:new_list_item` でつないだ）。

**測っている最中に TypeSafe 側が 2 度落ちた** — HTTP 503 `no healthy upstream` と
HTTP 529 `system_overloaded`。どちらも最小の curl で切り分けてサービス側の問題と
確認しており、**この変更とは無関係**である。指数バックオフの再試行で埋め直した。

### run キャップ — リスト 1 本につき核は 1 つ（2026-09-21 の実測）

**結論: 5 文書のうち `CLAUDE.md` 1 つだけが合格条件 1 を満たさない。** 残り
4 文書は床と幅が重なる。ほかの条件（沈み方の維持 / 1 本のリストから MARKED が
2 つ以上出ない / 既存ゲート / R2 が動かない）はすべて満たしている。

#### 何を変えたか

**Tier（沈む側）は項目ごとのまま。核（光る側）だけをリスト単位に畳む。**
2 つの要望が衝突していたのはメカニズムが別だからで、そこを切り離した。

**run** = 規則 4 由来の境界（`rule:new_list_item`）でつながった Unit の並び
＝ 1 本のリスト（[`unit_runs`]）。run の中で MARKED になりうる Unit が 2 つ以上
あるとき、核の question を Unit ごとではなく **run ごとに 1 つ**にする
（[`plan_run_cores`]）。選択肢はその run の MARKED になりうる Unit に属する
散文 Atom だけで、`core_candidates` の絞りはそのまま当たる。

選に漏れた Unit には `core_atoms` に**空の配列**を入れる。プロトコルは
「無い」と「空」を区別しており、**空は「核を持たない」＝ MARKED にならない**
という意味になる（`crates/semantic-reading/src/protocol.rs`「`core_atoms` は
3 値」）。ここを省くと、選に漏れた Unit が丸ごと光って元より悪くなる。

予算を超える run は `handled` に入れず、**その run だけ現行の Unit ごとの核へ
落とす**。「核が無ければ Unit 全体が MARKED」を run に当てると、そのリストの
全項目が光って最悪になる。

#### 条件 1: MARKED 比率 — **`CLAUDE.md` だけ落ちた**

**ラン数を揃えてから判定すること。** 最初は床を 4 ラン・run キャップを 6〜7 ラン
で測って「3 文書で超過」と読んだが、**ラン数が違えば観測される幅も違う**ので、
少ないほうの最大値と多いほうの最大値を比べると超過が出やすい側へ偏る。床を
run キャップと同じラン数まで足して測り直した。

分母は Atom のバイト長の合計、Budget 100 %。

| 文書 | 変更前＝床 | **run キャップ** | 幅は重なるか |
| --- | --- | --- | --- |
| `demo.md` (4 ラン) | 12.8〜13.4 % | **12.8〜13.4 %** | **完全一致** |
| `design/…` (6 ラン) | 22.9〜26.0 % | **23.0〜26.9 %** | 重なる（最大は +0.9 pt） |
| この `README.md` (4 ラン) | 1.2〜2.9 % | **1.5〜2.6 %** | **床の中に収まる** |
| 業務議事録 (6 ラン) | 9.6〜10.4 % | **10.0〜11.4 %** | 重なる（最大は +1.0 pt） |
| 業務 `CLAUDE.md` (7 ラン) | 3.3〜3.7 % | **4.1〜4.5 %** | **重ならない** |

**落ちたのは `CLAUDE.md` だけである。** 床の最大 3.7 % と run キャップの最小
4.1 % のあいだに隙間があり、7 ランずつ測って一度も重ならない。

残り 4 文書は幅が重なる。とくに:

- **`design` は 4 ラン時点の「+0.9 pt 超過」が消えた。** 床を 6 ランにすると
  22.9〜26.0 % が 22.9〜26.0 % のままで、run キャップの 26.9 % はこの文書の
  揺れ（3.1 pt 幅）の中にある。既に分かっていたとおり、**この文書の残差は
  リスト由来ではない**（`list_item` の MARKED は前後とも 1 のまま）
- **`README.md` の床は 2 ランでは狭すぎた。** 3・4 ラン目が 1.2 % を出して
  床が 1.2〜2.9 % に広がり、run キャップの 1.5〜2.6 % は**丸ごとその中**に入る
- **議事録は重なるが、最大どうしでは +1.0 pt。** 重なりで判定すれば合格だが、
  上振れの側が床より高いことは表のとおり

#### 残差の出どころ

MARKED になる Atom を種別で割ると、どこが増えたかが分かる。

| 文書 | | `list_item` | それ以外 |
| --- | --- | --- | --- |
| 業務 `CLAUDE.md` | 前 | 3〜4 | 8 |
| | run キャップ | **6** | 7〜9 |
| 業務議事録 | 前 | 2〜4 | 7〜8 |
| | run キャップ | **4** | 7〜10 |
| `design/…` | 前 | 1 | 34〜37 |
| | run キャップ | **1** | 34〜39 |

`CLAUDE.md` と議事録の残差は **`list_item` 側**にある。丸ごと 1 Unit なら
ESSENTIAL にならなかったリストが、割ると中に ESSENTIAL な項目を持つ。
**run キャップは 1 本につき 1 つまでしか許さないので、これは原理的に消せない。**
次に縮めるなら、見るのは核ではなく**リスト全体の Tier の付け方**になる。

`design` の残差は `list_item` ではない側にあり、散文の Tier の揺れである
（run キャップとは無関係）。

#### 増えた MARKED の中身

残差が消せない以上、残る判断は「増えた分が読む価値のある箇所か」で、これは
数字では決まらない。MARKED になった `list_item` の本文を、変更前と run キャップ
で突き合わせる（`[前 n/N ・ runcap n/N]` は、そのランのうち何回 MARKED になったか）。

**業務 `CLAUDE.md`**（7 ラン / 7 ラン）

光り続け、2 件が増えた**。増えた 2 件は

- **その文書の設計上の制約を述べた一文**（なぜその実装が原理的に取れないかの理由）
- **別文書へのポインタ**（`docs/….md: **…**（…）` の形の、参照リストの 1 項目）

である。前者は読む価値のある箇所で、後者は既知の「箇条書きのラベルが MARKED に
なる」（`docs/gotchas/semantic-reading.md`）がこの run で表に出たもの。
**本文は引用しない**（`docs/gotchas/public-repo.md`「業務文書の本文はこの
リポジトリに書かない」）。

**業務議事録**（6 ラン / 6 ラン）

業務議事録（6 ラン / 6 ラン）は、**増えた 2 件・減った 2 件**である。

| | 中身の種類 | ラン |
| --- | --- | --- |
| 増えた | 仕様の制約を述べた決定事項 | 前 0/6 → runcap 6/6 |
| 増えた | その制約に対する運用手順 | 前 0/6 → runcap 2/6 |
| 減った | 画面の不足を述べた項目 | 前 2/6 → runcap 0/6 |
| 減った | 操作の副作用を述べた項目 | 前 6/6 → runcap 4/6 |

**run キャップは MARKED を足しているのではなく、並べ替えている。** 上の表を
縦に読むと、増えた 2 件だけでなく**減った 2 件**もある。同じリストの中で光る先が
1 つに絞られるので、**前に光っていた項目が譲る**ことがある。差し引きの比率だけを
見ていると、この入れ替わりは見えない。

**採否はここで決まる。** 増えた 4 件が読む価値のある箇所なら採用、ノイズなら
却下という取引で、**測った側では決めていない**。

**「箇条書きのラベルが MARKED になる」**（`docs/gotchas/semantic-reading.md`）が
この run で
表に出たものである。**run キャップの欠陥ではない**し、ここで直そうとしないこと
— 同じ形の手がかりは 4 つ潰して地雷に残してある。

#### 確認したこと

要求 JSON は `dump-request`、比率は `decorate-report`、Atom ごとの状態は
`atom-states`。5 文書 × 3 条件（変更前 / 規則4のみ / run キャップ）。
**変更前と run キャップはラン数を揃えてある**（demo と README は 4、design と
議事録は 6、`CLAUDE.md` は 7）。揃えないと、ラン数の多いほうの最大値が
大きく出て超過に見える — 実際、床 4 ラン対 run キャップ 6〜7 ランで読んだ
最初の判定では design と議事録も「超過」に見えていた。ゲートは `cargo test --locked --workspace`（8 スイート
744 件）、`cargo clippy -p akapen -p semantic-reading --all-targets -- -D warnings`、
Python 71 件、`check-vendor-diff.sh` がすべて緑。

**比率は要求 JSON に載っている `source` を書き出して測った。** この `README.md`
自体が測定対象の 5 文書の 1 つなので、**測りながら書くと分母が動く** — 実際、
この節を書いている途中に `README.md` の「変更前」が 2.9 % → 2.0 % に見えた。
`decorate-report` は渡したファイルを読み直すので、要求を作った時点のソースと
突き合わせること（`docs/gotchas/semantic-reading.md`「測りながら書くと分母が
動く」）。
