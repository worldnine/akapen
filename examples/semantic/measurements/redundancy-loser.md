### 負けは位置で決めない。核は奪わない（2026-09-22 の実測・第 2 版）

**結論から: 効き目のほとんどは (b) で、(c) は小さい。** 冗長な対 22 件のうち
21 件で負けが入れ替わり、表示が動いた延べ 70 側のうち 58 側が (b) だけによる。
(c) で新しく光る Unit は **冗長 ESSENTIAL 54 個のうち 17 個**しかない —
残る 37 個は run キャップに漏れて `core_atoms = []` になっており、一段目に
入らないからである。MARKED は **+0〜3 Unit**、Budget の下限は **+0〜2
ポイント**。単調性は 2,000 点で無違反。

#### 何を変えたか

文献調査（[`../../../docs/design/reading-research.md`](../../../docs/design/reading-research.md)
「冗長な対のどちらを残すか」）の候補のうち、**(c) の上に (b) を重ねた**。

- **(c) 核は奪わない。** `policy::bears_a_core` から `!is_redundant()` を
  外した。冗長と判定されても ESSENTIAL で核を持つなら一段目に入り MARKED に
  なる。読み手のモデルを持たないと決めている以上、読み手によって重要度が
  逆転する対（本文節 vs 末尾の決定事項リスト）でどちらか一方を切る規則は
  持てない
- **(b) 負けは位置で決めない。** `REDUNDANT_WITH` の**持ち主**を必ず
  `weakened()` していたのをやめ、対のうち **Tier が低い方、同 Tier なら
  長い方**を弱める。方向（相手は必ず前）は**対を見つけるため**に要るので
  変えていない

`Relation::RedundantWith` の読み方が「私は冗長」から「この 2 つは冗長な対」へ
半歩ずれる。**ワイヤの形は変わらないので版は上げていない**
（`crates/semantic-reading/src/protocol.rs`）。

#### 決めたこと 4 つ

| 論点 | 決めたこと | 理由 |
| --- | --- | --- |
| 引き分け（同 Tier・同長） | **前を勝たせる** | `REDUNDANT_WITH` は必ず後ろから前へ向くので、これは変更前の規則にそのまま退化する。変える理由の無い場合に変わらない。satisficing の「もう読んだ」とも整合する |
| 1 つの Unit が複数の対に入る | **1 つでも負ければ負け。弱まるのは 1 段まで** | 冗長な対の勝者は「その内容の代表」であり、どこかで代表の座を譲った Unit は代表ではない（MMR）。「全部で負けたときだけ」にすると、無関係な第 3 の対の有無で弱まるかが変わる |
| 単調性 | **崩れない** | 負けの集合は `relations` と生の Tier・長さ・位置だけから決まり、Budget を引数に取らない。`keep_order` が Budget 非依存であるかぎり、負けの決め方は証明のどこにも現れない |
| 関係の意味 | **版は上げない** | 判定器が書くものは同じ（相手の id）で、変わったのは akapen 側の読み方だけ。版が守るのは「同じフィールドを双方が違う意味で読み書きする」事故で、ここにそれは無い |

実装は `policy::losers` が `SemanticUnit::redundancies()` を全 Unit について
回して**対の両端に印を付ける**。持ち主の `redundant_with()` だけを見ると、
負けが相手側に来た対も、2 つ目以降の対も取り逃がす。

#### なぜ (c) の効きが小さいのか — run キャップが先に効いている

| | 数 |

1 Atom の Unit**（23〜54 バイト）だった。Unit が 1 Atom なら「全体」も
「その 1 つ」も同じなので、**丸ごと光る問題は起きていない**。

##### 分類器は作らない — DIM の色は 1 つではない

`Dim` は span の**実効**前景色をブレンドするので、沈んだ色は見出しと本文で
違う。「この RGB が DIM」と決め打つと、**見出しだけ NORMAL に見える**
（実際に一度そう読み違えた）。判断は、同じ画面に出ている**沈んでいない同種の
行**と見比べてする。`MARKED` だけは背景の SGR（`48;2;90;69;33`）なので一意に
判る。カーソル行は帯に隠れるので、カーソルを別の行へ置いてから数える
（`docs/gotchas/rendering.md`「カーソル行の MARKED は帯に隠れる」）。

#### 第 1 版から何が変わったか

第 1 版は `redundancy-choice` の前の応答（相手が bigram、冗長な Unit の核は
剥がされていた）で測っていた。**結論が 3 つひっくり返っている。**

| | 第 1 版 | 第 2 版 |
| --- | --- | --- |
| 冗長な対 | 7 件（議事録のみ） | **22 件**（議事録 17・`design` 3・`demo` 1・`gotchas` 1） |
| 負けが入れ替わった | 5 / 7 | **21 / 22** |
| MARKED の増加 | +4〜5 Unit | **+0〜3 Unit** |
| 下限の上がり方 | +4〜5 ポイント | **+0〜2 ポイント** |
| 表示が動いた側の内訳 | (b) だけ 2・(c) だけ 5・両方 11・間接 3（計 21） | **(b) だけ 58**・(c) だけ 0・両方 12（計 70） |
| MARKED バイト | 「丸ごと光る上限値」 | **実値**（`None` は 1 Atom の Unit だけ） |

第 1 版で MARKED が大きく増えて見えたのは、判定器が冗長な Unit から
`core_atoms` を剥がしていたせいで、一段目に入った Unit が**丸ごと**光って
いたからである。核が正しく付いたいま、増えるのは run キャップを勝ち抜いた
17 個だけになった。

#### 残っていること

- **順読みの読み手に本文節が沈んで見える問題は解けていない。** (b) は勝者の
  決め方を変えただけで、`reading-research.md` の (d)（「どちらが要約か」を
  Choice で 1 問聞く）が上位互換として残っている。第 2 版で対が 3 倍に増えた
  ぶん、この問題も 3 倍の場所で起きる
- **run キャップと (c) はまだ噛み合っていない。** 冗長 ESSENTIAL の 7 割が
  `core_atoms = []` で、「両方光ってよい」と決めたのに片方も光らない対が
  多い。run キャップは「1 本のリストで核は 1 つ」という別の理由の規則なので、
  これを冗長の側から動かしてよいかは測っていない
